# Phase 2.7 Context: Pronunciation Provider Dispatch

状态：✅ COMPLETE

## 来源

Phase 2.6 完成后的架构审计发现：5 层学习体验（发音标注、词发音查询、词时间轴、
chunk 分区、语流分析）全部写死英语。用户在测试中文视频时发现字幕下方无法显示拼音，
而英语可以显示 IPA，由此触发本阶段。

## 用户关键表述

> 目前英语已有的学习体验应该是所有语言都通用的...架构或者说相应的学习体验只是消费者，
> 核心的消费数据来自于不同不同语言的生产者。

> 中文没有不代表其他语言没有，这个部分也作为 provider 派发模式。
> （关于语流分析/弱读连读——法语有联诵 liaison，德语有 Auslautverhärtung，日语有連濁）

## 实现结果

### Tier 1 — Provider dispatch（发音/规则）
- `PronunciationProvider` trait 定义在 `crates/application/src/providers.rs`
- `EnglishPronunciationProvider`：包装 `speech_analysis` crate
- `ChinesePronunciationProvider`：基于 CC-CEDICT，产出拼音
- 消费端按 `sentence_language()` 路由，完全语言无关

### Tier 2 — 通用算法（timing/chunk）
- `estimate_word_timings`：按字符权重分配，语言无关算法
- 声学 chunk 检测（gap-based）：语言无关
- 文本 chunk 检测（COCA/PHRASE）：仅英语，其他语言门控跳过
- 中文 profile 声明 `word_timeline: Supported`、`chunk_timeline: Supported`

### 用户验证通过
- 中文视频：拼音显示 ✅、词级跳动 ✅、chunk 高亮 ✅
- 英文视频：IPA + 全部功能回归正常 ✅

## 关键设计决策

### 为什么不用一个大 trait 覆盖所有 5 层？
`SentenceChunkPartition`、`DisplayChunk` 等类型定义在 `speech_analysis` crate 中。
如果 trait 签名引用这些类型，所有实现者（包括 `dictionary-provider` crate 中的
中文拼音 provider）都必须依赖 `speech_analysis`。将这些类型迁移到 `domain` 工作量
大，且声学 chunk 和时间估算算法本身是语言无关的，无需 per-language provider。

### 为什么 `rule_catalog()` 返回 `serde_json::Value`？
避免将 `RuleDefinition`（含 `&'static str` 字段）迁移到 domain。API 消费者
最终序列化为 JSON，中间类型无额外价值。

### 为什么 chunk 门控只保留在 text_chunk？
实际验证发现：声学 chunk 和 partition 算法对中文能正常工作（只需词时间数据）。
仅文本级 chunk（COCA n-gram、PHRASE List）是英语特有数据源，对其他语言无数据，
需要门控跳过。

### analyze_pronunciation_track 为什么改为 filter_map？
中文句子如果全是标点（无 word token），provider 返回 None，导致整个 track
调用失败。改为跳过失败句子，不影响其余句子的正常标注。

## 遗留问题（移至 Phase 2.8）

1. **Whisper BPE → app token 时间对齐**：whisper 的词级时间戳绑定在 BPE token
   边界上，与 app 的 jieba/语言 tokenizer 边界不一致，导致中文词级跳动精度不足。
2. **韵律感知估算权重**：当前 `estimate_word_timings` 统一用字符权重，中文应为
   等权（syllable-timed），日语应按 mora 计数（mora-timed）。
3. **命名统一**：`WordTiming` → `TokenTiming` 等，反映 token 才是语言无关的正确抽象。
