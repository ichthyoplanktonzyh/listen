# Phase 2.18 Context: Codebase Architecture Refactor

状态：PLANNED

## Why This Phase Exists

2026-06-27 的架构复盘发现，项目主线能力推进很快，但架构护栏和事实源同步没有同等速度收口。
这些问题不直接新增学习能力，却会影响后续每个 phase 的可维护性、接手效率和契约稳定性。

用户随后明确希望在项目尚未变得庞大之前，借 Phase 2.18 进行一次代码层面的彻底整理：
重点审阅并重构当前实现、核心数据模型、持久化边界和 Flutter 状态机，而不是只修补契约和文档。

2026-06-27 15:38 CST 进一步确认：本阶段 **不需要考虑历史兼容性**。旧数据库、旧
LLTimeline 资源、旧 API/UI 路径和旧模型数据都可以抛弃；设计以最新、最清晰、最可维护的架构为准。

Phase 2.18 因此从 **Architecture Contract Hygiene** 升级为
**Codebase Architecture Refactor**，不混入 Phase 2.17 真实媒体声音线 QA：

```text
API 契约漂移
  + 主干格式 gate 失败
  + 文档事实源漂移
  + WordProfile / LexicalEntry / LexicalUnit 模型并存
  + 字幕 / timeline / pronunciation 仓储边界过宽
  + Flutter 编排层过重
  + 状态机缺少请求 generation / session 边界
  = 后续功能迭代成本与回归风险持续上升
```

本 phase 的目标是恢复“领域模型清晰、边界可维护、状态流可证明、契约可信、主干 clean”的工程底座。

## Inputs From Architecture Review

架构复盘确认的主要问题：

- `api-http` router 已实现 97 个 `/v1` 路径，OpenAPI 只记录 93 个路径。
- OpenAPI 缺少：
  - `/v1/languages`
  - `/v1/languages/{code}/profile`
  - `/v1/phonetic-analysis/jobs/clear`
  - `PATCH /v1/subtitles/{track_id}/language`
- `./scripts/validate-contracts.sh` 和 `cargo test -p api-http openapi` 仍通过，说明契约测试只做
  白名单 presence smoke，没有反向校验实现新增路径。
- `./scripts/test.sh --quick --low-memory` 失败点是 `cargo fmt --check`，而 clippy、
  Rust lib tests 和 `flutter analyze` 已通过。
- README 和 `.planning/codebase/*` 仍包含旧事实：不存在的 `docs/handoff/...` 链接、
  M2.0 Phase 0 active、`api-http` 直接依赖 `speech-analysis`、数据库名 `llplayer.db`、
  schema 迁移只到 0010 等。
- `apps/desktop/lib/main.dart` 仍是主要 orchestrator，承担 API lifecycle、播放、字幕资源、
  timeline、词汇、下载、设置和事件路由。
- `ui-analysis/05-recommendations.md` 已从 Statecharts 角度列出 sealed 状态、事件总线、
  请求序列号、拆分 orchestrator 和 speech enhancement 错误细粒度化等改进方向。

## Inputs From Code-Level Review

代码复查进一步确认，本 phase 需要作为代码重构阶段，而不是只做表层治理：

- 领域模型：
  - `WordProfile` / `WordOccurrence` / `WordStatusHistory` 与
    `LexicalEntry` / `LexicalOccurrence` / `LexicalStatusHistory` 并存。
  - `LexicalUnit` 已经提出更通用的跨语言身份模型，但还没有成为学习资产的权威模型。
  - `TimelineStatus` 是通用状态，`WordTimelineLifecycleStage` 又是 word timeline 专属 lifecycle；
    word/chunk/phone timeline 的生命周期语义没有统一建模。
  - `metrics_json` / `evidence_json` / LLTimeline artifact payload 允许扩展，但关键语义缺少 typed envelope。
- 持久化边界：
  - SQLite 同时有规范化 learning tables 和 `*_timeline_runs.timeline_json` 整体 JSON blob。
  - active timeline 语义靠事务更新实现，schema 侧没有唯一 active 约束。
  - `SqliteRepository` 使用单连接 `Mutex<Connection>`，当前本地 sidecar 可接受，但 repository
    边界过宽会放大阻塞和测试耦合。
- 应用层 / API：
  - `SubtitleRepository` 同时承载字幕、发音、word/chunk/phone timeline 和 LLTimeline resource。
  - `application::dto` 公开别名到 `speech_analysis` DTO，应用层契约仍被算法 crate 形状影响。
  - `api-http` router 是手工链式注册，route manifest / OpenAPI / generated client 缺少单一事实源。
- Flutter：
  - `main.dart` 仍是 3000+ 行 composition root + workflow orchestrator。
  - `PlayerController` / `SubtitleController` / `LearningController` 已有 `Store<T>` 基础，但状态仍大量使用
    `Map<String, dynamic>`，无法表达 loading/error/stale/session 等状态。
  - `_onPosition` 和 SSE event handler 会触发多个 unawaited async workflow，guard 只绑定 cue id 或 track id，
    没有统一绑定 media session / subtitle generation。

## Scope

本 phase 是代码架构重构 phase，允许触及：

- OpenAPI / generated local API client / contract validation scripts。
- `api-http` route contract tests。
- Rust formatting cleanup。
- README、`.planning/codebase/*`、必要的 `.planning/STATE.md` / `CHANGELOG.md`。
- Rust domain / application / persistence repository 边界。
- WordProfile / LexicalEntry / LexicalUnit 的权威模型收敛、旧模型删除和新 schema 设计。
- WordTimeline / ChunkTimeline / PhoneTimeline 的共同 resource lifecycle 抽象。
- Flutter app state machine、workflow coordinator、typed API models 和 async generation guard。
- 生产管线脚本的模块化清理，只限于被核心 timeline/domain 重构影响的部分。

## Non-Goals

- 不新增声音线模型能力。
- 不新增真实媒体 QA case；那属于 Phase 2.17。
- 不更换 Rust / Flutter / Python 技术栈。
- 不推倒重写所有 UI；重构必须保持可运行、可验证、可逐步落地。
- 不改变用户可见学习语义，除非修复明确 bug 或模型命名漂移。
- 不为旧 SQLite 数据、旧 LLTimeline JSON、旧 API/UI adapter 保留兼容路径。
- 不要求数据迁移；允许创建全新 SQLite schema / LLTimeline schema / API contract。

## Product Rule

本 phase 的产品价值是降低后续学习体验迭代的失真和回归风险：

- 先冻结当前行为，再重构内部边界。
- 学习资产必须有一个权威身份模型，旧模型可以直接删除，不再作为兼容层长期存在。
- timeline resource 必须有统一生命周期语义，active/candidate/archive 不靠分散约定。
- 新 API 不能绕过 OpenAPI 契约。
- 新状态流不能依赖过时异步结果。
- 新 agent / 新维护者必须能从入口文档得到真实项目位置。
- 清理应保持行为不变，除非修复的是明确 bug。
