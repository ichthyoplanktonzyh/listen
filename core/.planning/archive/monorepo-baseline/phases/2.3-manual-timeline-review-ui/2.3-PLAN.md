# Phase 2.3 Plan: Manual Timeline Review UI

更新时间：2026-06-20 23:14:44 CST

状态：⏳ 待实现。

## Objective

完成 app 端人工校正闭环：用户能在当前句检查、微调、试听 WordTimeline 边界，保存为
非破坏性的 `user_adjusted` WordTimeline revision，并立即作为 active timeline 驱动播放
高亮和后续资源生成。

## Design Principle

Phase 2.3 先交付可信、可验证、低风险的句子级 inspector。波形和拖拽只是边界微调的
交互增强，不是本阶段必须依赖的底座。

```text
Production candidate remains immutable
  -> User edits a full cloned draft
  -> User saves adjusted revision
  -> Adjusted revision becomes active
  -> Export keeps both production and user timelines
```

阶段优先级：

1. **必须完成**：句子级 inspector、数字/步进微调、试听、保存 user revision、自动激活。
2. **可选增强**：Prev/Next 连续校对、更多 suspicious gap/overlap 提示。
3. **明确推迟**：波形渲染、波形拖拽、语谱图、音素级编辑。

## Recommended Workflow

```text
Subtitle Resources / Timeline Resource Summary
  -> Manual Review
  -> Load active WordTimeline
  -> Open inspector at current playback sentence
  -> Clone full source words into draft
  -> Edit current sentence boundaries
  -> Play sentence / word from draft boundaries
  -> Save full draft as user_adjusted WordTimeline
  -> Backend activates saved revision
  -> App reloads summaries and trackWordTimings()
  -> Player highlight consumes new active timeline
```

## Work Breakdown

### Step 1: Contract And Current-State Audit

- Confirm existing Rust contracts:
  - `GET /v1/word-timelines/{timeline_id}` can return full source timeline.
  - `POST /v1/subtitles/{track_id}/word-timelines` can create user revision.
  - `status=active` create path saves and activates the new timeline.
  - `word_timings_for_track` returns active WordTimeline before legacy timings.
- Confirm existing lifecycle semantics:
  - `parent_timeline_id` points to source timeline.
  - `created_by=user` marks the revision as human-created.
  - edited words use `timing_source=user_adjusted`.
  - `metrics_json.review` records review metadata.
- Identify Flutter gaps:
  - `ApiService` needs full timeline read and create methods.
  - Flutter `WordTiming` model needs complete fields needed for editing/saving.
  - Controller needs review draft state or a dedicated review controller.

Exit criteria:

- No backend schema change is required for the first implementation.
- The exact create payload for user-adjusted timeline is documented.
- Any API/client gaps are listed before UI work starts.

### Step 2: Flutter Timeline Models And API Client

- Extend Flutter timeline models:
  - `WordTiming`: `sentenceId`, `tokenIndex`, `text`, `start`, `end`, `confidence`,
    `source`, `provider`, `providerVersion`.
  - `WordTimeline`: `id`, `trackId`, `mediaId`, `algorithmId`, `algorithmVersion`,
    `configHash`, `parentTimelineId`, `createdBy`, `status`, `metricsJson`, `words`.
- Add API client methods:
  - `wordTimeline(timelineId)`.
  - `createTrackWordTimeline(trackId, payload)`.
- Keep existing `trackWordTimings(trackId)` path unchanged for playback highlight.
- Add serialization helpers for create payloads so draft words can be submitted losslessly.

Exit criteria:

- Flutter can load a full active WordTimeline by id.
- Flutter can submit a full WordTimeline create request.
- Existing summary/activate/import/export client methods still work.

### Step 3: Manual Review Draft State

- Create a dedicated review state object/controller or extend `SubtitleController` with:
  - source timeline id.
  - source active track id.
  - full `draftWords`.
  - current sentence id/index.
  - dirty word keys: `(sentence_id, token_index)`.
  - validation errors.
  - save status/error.
- Initialize draft from the full active WordTimeline.
- Filter current sentence rows from `draftWords`.
- Preserve unedited words exactly as inherited from the parent timeline.
- When a word boundary changes:
  - update draft start/end.
  - mark the word dirty.
  - set edited word `source=user_adjusted`, `provider=user`,
    `providerVersion=llplayernext-manual-review-v1`.

Exit criteria:

- A review draft can be created, edited locally, reset, and inspected in tests.
- Dirty tracking distinguishes inherited words from user-edited words.
- Draft state survives sentence navigation until save/cancel.

### Step 4: Local Validation Rules

- Implement local validation aligned with backend `validate_word_timeline_words`:
  - non-empty words.
  - each edited word belongs to a valid sentence.
  - `end_ms > start_ms`.
  - word start/end remains inside sentence start/end.
  - current sentence words do not overlap.
  - token order remains monotonic.
- Enforce timestamp precision:
  - review draft stores `start_ms` / `end_ms` as integer milliseconds.
  - UI display formatting must not change the stored millisecond value.
  - save payload must contain absolute media timeline milliseconds, not relative offsets.
  - no second-level rounding is allowed when editing, playing, saving, or exporting.
- Add warnings, not blockers, for suspicious cases:
  - very short duration.
  - large gap between adjacent words.
  - large edit delta compared with parent boundary.
- Disable Save while blocking errors exist.
- Surface backend validation errors without clearing the current draft.

Exit criteria:

- Invalid boundaries cannot be saved from the UI.
- Draft/save/export preserve millisecond-level `start_ms` / `end_ms` precision.
- Backend rejection leaves the draft intact and shows a clear message.
- Tests cover valid edit, overlap, inverted boundary, and sentence boundary overflow.

### Step 5: Sentence Word Timing Inspector UI

- Wire the existing Manual Review entry to open the inspector.
- Initial sentence selection:
  - prefer current playback sentence if available.
  - otherwise use first sentence with word timings.
- Inspector layout:
  - sentence text/header.
  - Prev/Next sentence controls.
  - word rows with text, start, end, duration, source/provider, confidence.
  - step controls for start/end: `-50`, `-10`, `+10`, `+50` ms.
  - numeric input for start/end.
  - dirty/edited indicator per word.
  - validation and warning area.
  - Save, Reset sentence, Cancel.
- Keep controls dense and operational; avoid turning this into a marketing or tutorial page.

Exit criteria:

- User can open inspector from a visible resource entry.
- User can edit current sentence word boundaries without leaving the app.
- UI clearly shows inherited vs edited state.

### Step 6: Playback Verification Controls

- Add controls:
  - Play current sentence.
  - Play selected/current word.
  - Optional replay / loop current word if simple with existing player adapter.
- Playback should use draft boundaries before save.
- Stop or return to prior playback state cleanly after segment playback.
- Keep existing main player highlight unchanged until save activates the user timeline.

Exit criteria:

- User can hear the exact edited word/句 segment before saving.
- Editing draft boundaries changes review playback immediately.
- Main playback highlight updates only after save/activation.

### Step 7: Save, Activate, Refresh

- Build full create payload:
  - `parent_timeline_id = sourceTimeline.id`
  - `created_by = user`
  - `status = active`
  - `algorithm_id = manual-review`
  - `algorithm_version = llplayernext-phase-2.3`
  - `config_hash` can be omitted unless a deterministic review hash is added.
  - `metrics_json.review.edited_word_count`
  - `metrics_json.review.reviewed_sentence_ids`
  - `metrics_json.review.parent_timeline_id`
  - `metrics_json.lifecycle.human_reviewed = true`
  - `words = draftWords`
- Submit via `POST /v1/subtitles/{track_id}/word-timelines`.
- Rely on backend `status=active` path to activate saved revision.
- After success:
  - reload WordTimeline summaries.
  - reload LLTimeline export/document snapshot if currently shown.
  - reload `trackWordTimings(trackId)` / speech enhancements.
  - keep inspector on the same sentence using the newly saved source timeline.

Exit criteria:

- Save creates a new user timeline with parent link.
- New timeline is active immediately.
- Player highlight and timeline summary reflect the saved revision without app restart.

### Step 8: Export And Resource Regression

- Verify `GET /v1/subtitles/{track_id}/lltimeline/export` includes:
  - original production candidate timelines.
  - new user-adjusted timeline.
  - active timeline id pointing to the user revision.
  - persisted metadata/artifacts from the imported resource.
- Verify users can still activate another candidate after saving a user revision.
- Verify no-resource fallback remains unchanged.

Exit criteria:

- Exported LLTimeline can round-trip without losing the user revision.
- Production candidate activation still works.
- Legacy/estimated word timing behavior remains intact when no LLTimeline is present.

### Step 9: Documentation, Audit, And Closeout

- Update `2.3-ACCEPTANCE.md` with actual verification results.
- Add `2.3-CLOSEOUT.md` when implementation is complete.
- Update `.planning/STATE.md` with shipped behavior and deferred items.
- Update changelog if user-facing UI changed.
- Document Phase 2.4 handoff:
  - ChunkTimeline generation should prefer active user-adjusted WordTimeline.
  - `human_reviewed` can be inferred from active user timeline and/or metrics.
  - estimated timings remain lower-confidence input for chunk generation.

Exit criteria:

- Phase 2.3 closeout is written.
- Phase 2.4 has a stable active WordTimeline dependency.
- Verification commands and manual QA notes are recorded.

## Testing Plan

Rust/API:

- Create user-adjusted WordTimeline with parent id.
- `status=active` create activates the saved timeline.
- Activation refreshes compatibility `word_timings`.
- Export includes production candidates and user revision.
- Candidate activation still works after a user revision exists.

Flutter unit/widget:

- `ApiService` serializes full timeline create payload.
- Review draft marks edited words dirty and preserves inherited words.
- Validation catches inverted boundaries, overlap, and sentence boundary overflow.
- Manual Review entry opens inspector.
- Save success refreshes summaries and speech enhancements.
- Save failure keeps draft state and displays an error.

Regression:

- Existing subtitle resource import/activate/archive/export UI still works.
- Existing `trackWordTimings()` highlight path still works.
- No LLTimeline resource fallback remains unchanged.
- Stale sidecar/migration guardrail from Phase 2.2 remains valid.

Manual QA:

- Import a LLTimeline resource with at least one candidate WordTimeline.
- Open Manual Review on current playback sentence.
- Adjust one word by `+10ms` or `-10ms`.
- Play current word and current sentence from draft.
- Save and confirm timeline summary shows a user-adjusted active timeline.
- Resume playback and confirm word highlight uses the adjusted boundary.
- Export LLTimeline and confirm both parent and user revision exist.

## Acceptance Criteria

- The user can complete `发现问题 -> 微调 -> 试听 -> 保存 -> 自动激活 -> 播放验证`
  without leaving the app.
- The production candidate remains available and unmodified.
- The user-adjusted timeline has a valid parent chain and is exportable.
- The app can switch between production candidate and user revision after save.
- Invalid edits are blocked before save and also protected by backend validation.
- Tests cover the save/activate/export path and main UI state transitions.

## Deferred

- Waveform rendering and word boundary overlay.
- Drag-to-adjust boundaries on waveform.
- Zero-crossing snap.
- Spectrogram.
- Text edit -> automatic realignment -> manual review workflow.
- Multi-user or CRDT review history.
- PhoneTimeline / phoneme-level inspector.

## Open Questions

- 是否允许在同一个 user-adjusted timeline 上继续编辑，还是每次保存都创建新的 revision？
  - 初版建议：每次保存创建新的 revision，保持历史简单且非破坏。
- `human_reviewed` 是只从 active user timeline 推断，还是同步写入 LLTimeline metadata？
  - 初版建议：timeline summary 可推断；export metadata 可在后续统一。
- Save 后 inspector 是否立即切换 source timeline 到新 user revision？
  - 初版建议：是。后续编辑基于最新 active revision，parent chain 保留历史。
