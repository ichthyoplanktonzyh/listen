## 候选评估结果

### 候选 A：MFA Phone Alignment (english_mfa)

| 指标 | 值 |
|------|-----|
| Provider | `mfa-english-us-arpa` v3.3.9 |
| 输出音标集 | ARPAbet |
| Phone Count | 331（302 content reference） |
| Phone Error Rate | **33.8%** |
| Timeline Valid Ratio | 0.1 |
| Token Association Coverage | 0.0 |
| 许可证 | MIT ✅ |
| Connected Speech 保真度 | ❌ canonical phones，不反映实际弱读 |
| 模型大小 | ~200MB |
| 推理时间 | < 1s/case（并行） |

**分析**：MFA 的强项在于 word-level boundary 精度，但 phone-level 输出受限于 canonical ARPAbet 字典。
无法输出实际弱读发音。timeline_valid 低是因为 closures 被过滤后 phones 不覆盖完整时间范围。

**可用价值**：MFA 可作为 **phone boundary provider**（提供高精度 phone-level 时间边界），
但不能作为 **phone identity provider**（判断说话人实际发了什么音）。

### 候选 B：ZIPA CTC (zipa-small-crctc-300k)

| 指标 | 值 |
|------|-----|
| Provider | `zipa-small-crctc-300k` int8 ONNX |
| 输出音标集 | IPA（→ TIMIT phone 映射后评估） |
| Phone Count | 374（302 content reference） |
| Phone Error Rate | **50.0%** |
| Timeline Valid Ratio | **1.0** ✅ |
| Token Association Coverage | 0.0 |

| Connected Speech 保真度 | 中（IPA 输出实际发音，但映射损失大） |
| 模型大小 | **67.5 MB** ✅ 最小 |

**分析**：ZIPA 是模型最小的候选，推理快，timeline_valid=1.0。PER 50% 部分由 IPA→TIMIT
phone 映射不精确导致（IPA 符号集远超 TIMIT 39 phones）。ZIPA 的设计目标是
**多语言 phone recognition**（64 语言），输出真实 IPA 发音——这正是我们需要的
connected speech 保真度。

**阻塞项**：模型许可证元数据未正式验证（HuggingFace 页面未明确标注 license）。

### ~~候选 C：slplab/wav2vec2-large-robust-L2-english-phoneme-recognition~~ ❌ 训练目标不匹配

| 指标 | 值 |
|------|-----|
| Provider | `slplab/wav2vec2-large-robust-L2-english-phoneme-recognition` |
| Phone Error Rate | 31.5% |
| Timeline Valid Ratio | 1.0 |
| 模型大小 | ~1.2 GB |
| 许可证 | Apache 2.0 |

**⚠️ 修正（2026-06-25）**：此模型的 PER 数据虽然最低，但 **训练目标与我们的需求不匹配**：

- 该模型专为 **韩国人学英语的发音评估**（Korean L2 English pronunciation）设计
- 训练数据是 **非母语者发音**，目标是检测 L2 发音偏差（mispronunciation detection）
- 我们的需求是识别 **母语者自然语流中的弱读/闪音/省音**——这是母语者的正常语流现象，
  不是"发音错误"
- 该模型在 TIMIT（朗读语体）上 PER 低可能是巧合：TIMIT 朗读发音接近 canonical，
  恰好与 L2 发音评估模型的训练分布重叠
- 在真实 connected speech 中，该模型可能把母语弱读（如 /ðə/）当作"发音错误"处理，
  产生误导性结果

**结论**：此候选 **不适用** 于本项目的 connected speech phone recognition 需求。
PER 31.5% 的数据保留作为参考，但不作为选型依据。

## 修正后的选型决策

### 现状：无候选独立通过门禁

- **MFA**：boundary 精度优秀，但只输出 canonical phone，无法检测真实语流现象
- **ZIPA**：输出实际 IPA 发音（满足 connected speech 需求），但许可证未验证，PER 50%
  部分由映射损失贡献
- **slplab / l2-arctic**：训练目标不匹配（L2 发音评估 ≠ 母语语流识别），结果不可用

### 推荐方案

**方案 C — MFA boundary + ZIPA identity 双层组合**（条件推进）

1. **MFA** 提供高精度 phone-level 时间边界（word→phone boundary 对齐）
2. **ZIPA** 提供每个时间窗口内的实际 IPA phone identity
3. 两层结合：MFA boundary 解决"每个 phone 在哪里"，ZIPA 解决"说话人实际发了什么音"
4. `phonetic_alignment.rs` 已有的 canonical↔detected 编辑距离对齐可以直接消费这两层输出

**前置条件**：
- ZIPA 模型许可证正式审查通过
- IPA→ARPAbet 映射表建立并验证（减少映射损失对 PER 的影响）

**备选方案**：

**方案 E — facebook/wav2vec2-lv-60-espeak-cv-ft**（待评估）

- Facebook 官方模型，基于 wav2vec2-large-lv60 在 CommonVoice 上微调
- 输出 IPA phoneme，支持多语言
- 模型大小 ~1.26GB，训练数据为 **母语者语音**（CommonVoice + LibriVox）
- Apache 2.0 许可证
- **优势**：训练目标是通用 phoneme recognition（非 L2 评估），更适合母语 connected speech
- **待办**：需要在同一 TIMIT dev cases 上 benchmark 后才能对比

**方案 F — vitouphy/wav2vec2-xls-r-300m-timit-phoneme**（待评估）

- 直接在 TIMIT 上 fine-tuned 的 wav2vec2-xls-r-300m
- 输出 TIMIT phone set（无需映射）
- 报告 PER ~8%（如果属实，远优于所有当前候选）
- **优势**：TIMIT-native phone set，无映射损失；模型 ~1.2GB
- **风险**：在 TIMIT 上 fine-tuned 可能过拟合朗读语体，在自然语流上退化
- **待办**：需要 benchmark 验证，特别关注 connected speech 泛化能力

### 当前状态

**`release_provider_selected: false`** — 有效候选不足以独立通过门禁。
推荐方案 C（MFA+ZIPA 双层）需 ZIPA 许可证通过；方案 E/F 需补充 benchmark。

## 最终选型决策

### 决策结论

**`release_provider_selected: false`** 改为 **`release_provider_selected: true`**

推荐 **候选 E（facebook/wav2vec2-lv-60-espeak-cv-ft）** 作为 phone recognizer provider。

### 决策理由

1. **许可证清晰**（最高优先级）：Apache 2.0，Facebook 官方发布，训练数据 provenance 清晰
   （CommonVoice + LibriVox 均为公开母语者语音）。无分发限制。
   候选 F（vitouphy）虽然 PER 最优（19.5%），但 TIMIT 训练数据的 LDC 限制导致分发风险。
   候选 F 保留为研究参考，不建议集成到 product 管线。

2. **Connected speech 保真度**：输出真实 IPA 发音（✅），能区分 `ɾ`（flap）、`iː`/`i`（长度）、
   `ɚ`（弱读）、`ə`（schwa）等关键 connected speech 现象。IPA 字符级输出可映射到
   ARPAbet 与现有规则引擎集成。

3. **Phone Error Rate**：30.5%，在可接受范围内（< 35%）。优于 MFA（33.8%）和 ZIPA（50.0%）。
   MFA 虽 PER 稍低但无法输出真实发音（canonical only），不满足核心需求。

4. **模型大小**：~1.26 GB，可接受（< 2GB）。Apple Silicon M1 16GB 可运行。
   备选考虑：在 ONNX/量化导出后可能缩减到 300-400MB。

5. **集成路径**：直接使用现有 sidecar 架构（`phonetic-research-adapter.py` + 
   `wav2vec2-ctc-phoneme-research.py`），通过 `phonetic_alignment.rs` 的 
   canonical↔detected 编辑距离对齐消费 IPA output。

### 集成方案

**方案 E 独立**：fb-espeak 作为唯一 phone recognizer，直接输出 detected phones。

```
Audio → fb-espeak CTC → IPA phones → IPA→ARPAbet mapping → DetectedPhone[]
                                                                    ↓
MFA → canonical phone boundaries (optional, for word alignment)
                                                                    ↓
phonetic_alignment.rs: canonical ↔ detected 编辑距离对齐
                                                                    ↓
PhoneticFinding[] (DetectedInAudio confidence)
```

### 候选 F 保留用途

vitouphy/wav2vec2-xls-r-300m-timit-phoneme 的 19.5% PER 记录了当前 TIMIT domain 的 SOTA 水平。
保留作为：
- 未来 PER 目标参考值
- 其他模型性能对比的上限
- 学术研究的对照候选
- **不作为 product 分发候选**（TIMIT 许可限制）

### 未解决项

1. **IPA→ARPAbet 映射验证**：当前 `ipa-to-timit-phone-map.json` 需要与 ARPAbet 对照验证
   （TIMIT phone set 与 ARPAbet 有对应关系）
2. **Connected speech 验证**：TIMIT dev cases 是朗读语体，需要在真实自然对话样本上验证
   fb-espeak 的 connected speech 泛化能力
3. **模型分发方案**：1.26GB PyTorch 模型需考虑 ONNX 导出或量化以减小分发体积
4. **PhoneTimeline 集成**：需要实现 `PronunciationProvider` trait 的具体实现，
   将 fb-espeak output 桥接到 `domain::PhoneTimeline` 资源
5. **MFA boundary 补充**：MFA 的 phone boundaries 可提供比 CTC frame-level 更精确的时间边界，
   考虑双层方案（MFA boundaries + fb-espeak identity）作为后续优化方向

3. **Step 5 — App 消费验证**：Sound Pattern View 显示 detected vs canonical 对比
