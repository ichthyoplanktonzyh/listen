## 一、项目背景

LLPlayerNext 是一个多语言听力学习媒体播放器。用户导入英文视频后，系统提供逐词时间轴、
字幕分析和语流规则诊断（弱读 / 省音 / 闪音 / 连读 / 同化 / 缩约）。

**现状**：所有英语语流分析都是纯文本规则推断（`speech-analysis` crate，6555 行）。
规则引擎有 11 条弱读规则 + 6 类连接语流规则，输出置信级别为 `LikelyByContext`（文本预测）
或 `PossibleByRule`（规则匹配），没有真实音频层证据。

**目标**：选出一个 phone-level provider，让置信级别可以升级到 `DetectedInAudio`——
"说话人实际说了 /ðə/"，而不是"这里可能有弱读"。

### 2.6 质量门禁（Phase 2.5 定义）

进入默认 product path 的前提条件：

1. **数据量**：至少 10 条 development cases 通过 `validate-inputs`
2. **时间轴有效性**：phones 单调、位于音频范围内、可映射到 sentence/token
3. **语流诚实**：不能把弱读/省音/闪音规范化回字典发音后仍声称 detected
4. **量化指标**：记录 PER、timeline validity ratio、token association coverage、failure rate、RTF、peak RSS、model size
5. **诊断精度**：高置信 findings 需人工 precision review
6. **来源可追溯**：provider/model revision、checksum、许可证、训练数据 provenance 明确
7. **产品分层**：低置信 / canonical-only / fixture 结果不标成 `detected_in_audio`

### Phase B：候选 Provider Benchmark（~4 小时）

对每个可用候选，在同一组 development cases 上运行，记录统一指标。

#### B1. MFA Phone Alignment 评估

**运行方式**：

```bash
# 对每条 development case，准备 audio segment + transcript，然后：
python3 scripts/forced-align/mfa-align-cli.py < request.json
```

MFA 输出 TextGrid → 解析为 `{ timings: [...] }` → 通过 `phonetic-research-adapter.py run` 转为评估 JSONL。

**记录指标**：
- RTF（real-time factor）
- Peak RSS
- TextGrid 解析成功率
- Phone boundary 精度（与 reference 对比的 PER）
- Timeline validity ratio
- Token association coverage

**关键限制**：MFA 对齐的是 **canonical phone**（字典发音），不是说话人实际发音。
例如 "the" 的 MFA 输出是 `DH IY` 或 `DH AH`（取决于字典条目），但说话人可能实际弱读为 `DH AX`。
MFA 不能直接产生 `DetectedInAudio` 结论——它只提供 phone boundary。

#### B2. ZIPA CTC Phone Recognition 评估

**运行方式**：

```bash
# ZIPA 研究环境需要的 Python 是 ZIPA venv 的 python
research_root="${LLPLAYERNEXT_ZIPA_RESEARCH_DIR:-$HOME/Library/Caches/LLPlayerNext/research/zipa}"

python3 scripts/phonetic-research-adapter.py run \
  --case-id <case_id> \
  --audio <audio_path> \
  --audio-start-ms <start> \
  --audio-end-ms <end> \
  --license-id <license> \
  --provider-id zipa-small-crctc-300k \
  --model "$research_root/model/model.int8.onnx" \
  --model-revision 9a8d85ba0d2adcbafe7087b82180d0e65c6f3426 \
  --phone-set ipa \
  --output <output.jsonl> \
  --metrics <metrics.jsonl> \
  -- "$research_root/venv/bin/python" scripts/zipa-ctc-onnx-research.py \
     --model "$research_root/model/model.int8.onnx" \
     --tokens "$research_root/model/tokens.txt" \
     --audio <audio_path> \
     --audio-start-ms <start> \
     --audio-end-ms <end>
```

**记录指标**：
- RTF
- Peak RSS
- model size（int8: ~67MB）
- Phone Error Rate（与 reference 对比）
- CTC frame→phone timestamp projection 精度
- Connected speech 保真度：弱读/闪音/省音是否被正确识别为实际发音（不被规范化回 canonical）

**关键问题**：
- ZIPA 输出的是 IPA 符号，需要映射到 ARPAbet 或建立 IPA↔ARPAbet 对照表来与 MFA 和 reference 对比
- CTC timestamp projection 基于 frame 级别，精度取决于 frame step（通常 20ms）
- `phonetic-research-adapter.py derive-ctc-timeline` 已实现 frame→phone 投射

#### B3. Wav2IPA / Wav2Vec2Phoneme 可行性调研

**不要求完整 benchmark**，仅做可行性评估：

1. 搜索 HuggingFace 上可用的英语 phoneme recognition 模型
2. 记录每个候选的：model ID、revision、训练数据、许可证、模型大小
3. 评估 Apple Silicon 兼容性（是否支持 CoreML / ONNX / PyTorch MPS）

**重点考察**：
- 模型是否在 connected speech / conversational speech 上训练过（vs 仅朗读语体）
- 输出是否包含 per-phone timestamp（不仅是 phone sequence）
- 训练数据 provenance 是否清晰（Buckeye 有使用限制）

### Phase C：选型决策（~1 小时）

基于 Phase B 结果，在三种方案中选择：

#### 方案 A — Canonical Alignment + 声学偏差推断

- **架构**：MFA 提供 phone boundaries → 用 formant/energy 分析推断真实弱读
- **优势**：MFA 已验证、MIT 许可、boundary 精度高
- **劣势**：需要额外声学分析层，复杂度高；formant 分析本身有噪声
- **适合场景**：MFA benchmark 结果明显优于 ZIPA，且 ZIPA 许可证不通过

#### 方案 B — Direct Phoneme Recognition

- **架构**：ZIPA（或 Wav2IPA）直接输出 detected phones with timestamps
- **优势**：端到端，输出就是实际发音
- **劣势**：timestamp 精度可能不如 MFA；模型许可证风险
- **适合场景**：ZIPA 的 connected speech 保真度明显好，许可证审查通过

#### 方案 C — 双层组合

- **架构**：MFA alignment 提供 boundaries + ZIPA/recognizer 提供 phone identity
- **优势**：各取所长（MFA 的 boundary 精度 + recognizer 的发音保真度）
- **劣势**：管线复杂，运行时成本翻倍
- **适合场景**：单一候选不能同时满足 boundary 精度和发音保真度

**决策标准**（按优先级排序）：

1. **许可证清晰**：模型 + 代码 + 训练数据 license 必须允许桌面 app 分发
2. **Connected speech 保真度**：能区分弱读 vs 全读发音（最核心指标）
3. **Phone boundary 精度**：与 reference 对齐的 PER
4. **Runtime 成本**：RTF < 0.5，peak RSS < 500MB（Apple Silicon M1 8GB 可用）
5. **集成复杂度**：优先复用已有 sidecar 架构

**如果所有候选均未通过门禁**：记录原因，以 "no release provider selected"
收口（与 Phase 2.5 相同），并推荐后续调查方向。这是合法结论——不要为了选出
provider 而降低标准。
