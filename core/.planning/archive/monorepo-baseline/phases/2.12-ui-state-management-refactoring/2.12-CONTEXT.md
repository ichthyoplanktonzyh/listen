# Phase 2.12 Context: UI State Management Refactoring

更新时间：2026-06-25 CST

## Background

LLPlayerNext 前端 (Flutter) 自 Milestone 1 至今的 UI/UX 体验较差，主要原因之一是**状态管理粒度不足**。

当前架构使用 `ChangeNotifier + Immutable State` 模式，每个 Controller 管理一个含 15–30 个字段的 State 对象。当一个字段变更时，`notifyListeners()` 触发所有监听者重建，即使 Widget 只关心其中一个字段。

与此同时，大量数据以 `Map<String, dynamic>` 形式传递（wordProfiles、diagnosis、phraseCandidates 等），缺乏类型安全，IDE 无法提供补全和编译期检查。

主页面 `_PlayerScreenState.build()` 方法约 600 行，承担了布局构建、数据编排和本地 UI 状态管理的多重职责，难以维护。

## Problem

1. **ChangeNotifier 全量通知**：PlayerState 有 15 个字段，SubtitleState 有 30 个字段，任何字段变更都会触发所有监听者重建。
2. **缺少 Selector 模式**：Widget 无法只监听特定的状态切片。
3. **大量 `Map<String, dynamic>`**：wordProfiles、pronunciationBySentence、phraseCandidates、diagnosis 等核心数据类型使用 `Map`，无类型安全。
4. **布局与逻辑耦合**：`_playerSurface()` 和 `_sidePanel()` 等大型布局方法嵌入在 `_PlayerScreenState` 内。
5. **状态碎片化**：本地 UI 状态（如 `status`、`dragging`、`connectingApi`）与业务状态混在一起。

## Prior Work

- Phase 2.2 建立了 Timeline Resource 的消费端能力。
- Phase 2.3/2.4/2.5 在 app 端新增了大量 UI 功能但没有改状态管理层。
- Phase 2.3.5 在 Rust 端做了巨型文件拆分，但 Flutter 前端的状态管理技术债未处理。

## Design Decisions

1. **Store\<T\>**：引入与 ChangeNotifier 兼容的通用状态容器。保留 ChangeNotifier 接口以保证现有代码不做大改。
2. **select()**：通过 ValueNotifier 暴露细粒度状态切片，Widget 只监听需要的数据。
3. **typed models**：新增 `models/types.dart`，提供 typed 类替代 `Map<String, dynamic>`。
4. **按需提取布局**：先提取 `SubtitleOverlay` 和 `SidePanel` 两个最大块，后续逐步拆分。
