# Phase 3.19.3 Context: Frontend / Core Repository Separation

Status: PLANNED

Date: 2026-07-28

Parent phase: Phase 3.19 Product Validation & Release Closeout

Decision: ADR 0031

## Why this belongs under Phase 3.19

This is engineering governance for the retained product, not a new product
feature. It does not add a new journey, fallback or capability. It makes the
existing Flutter + Rust sidecar product independently developable while
preserving the Phase 3.19 correction gate and the rule that no release is
claimed before owner acceptance.

## Current product topology

```text
Flutter desktop process
  ├─ local player, cursor, high-frequency playback behavior
  ├─ starts api-http and reads api.started { address, token }
  └─ REST + SSE over loopback
          |
          v
Rust api-http sidecar
  ├─ application/domain/persistence modules
  ├─ local jobs and optional providers
  └─ SQLite + filesystem/keychain/runtime assets

Final macOS package
  = Flutter executable
  + api-http
  + whisper-cli / ffmpeg / ffprobe
  + player framework
  + entitlements / notices / signatures
```

The repository seam and the deployed process seam are different. Moving source
directories does not remove the runtime relationship.

## Coupling inventory

### Frontend dependencies on repository root

- `apps/desktop/pubspec.yaml` resolves `fvp` through
  `../../third_party/flutter/fvp`.
- Flutter contract tests read `../../contracts/**` and
  `../../testdata/**`.
- development sidecar discovery walks ancestor directories for
  `target/debug/api-http` and `target/release/api-http`.
- the desktop README and functional-testing docs assume Cargo and Flutter share
  one checkout.
- the architecture guard inspects both Rust and Flutter source trees.

### Product assembly dependencies

- `scripts/build-macos-mvp.sh` builds Cargo and Flutter in one checkout;
- it copies `api-http` and `third_party/runtime/macos-arm64` into the app;
- it copies runtime manifests and notices;
- it sanitizes the player framework and signs the combined app;
- `scripts/verify-mvp.sh` consumes shared generated media and subtitle fixtures.

### Contract dependencies

- `contracts/openapi/v1.yaml` is included directly in Rust tests;
- current OpenAPI parity compares documented and implemented path names;
- SSE examples are produced by Rust and parsed by Flutter from the same file;
- several Flutter DTO tests document OpenAPI schema expectations without
  consuming a versioned external artifact;
- `contracts/generated/local-api-v1.ts` is a historical handwritten experiment,
  not the Flutter client authority.

### Governance dependencies

- root `CHANGELOG.md`, `.planning/**`, issue templates and one CI workflow cover
  both tracks;
- phase commits commonly change frontend, backend and contract paths together;
- Actions issue #75 means the migration must preserve exact local validation
  evidence without treating an unstarted remote job as green.

## Artifact shapes

### Contract release

Minimum manifest fields:

```json
{
  "manifest_version": 1,
  "contract_version": "1.0.0",
  "core_git_sha": "<full sha>",
  "openapi_sha256": "<sha256>",
  "events_schema_version": 1,
  "events_sha256": "<sha256>",
  "examples_sha256": "<sha256>"
}
```

The archive contains the OpenAPI document, event/resource schemas and canonical
examples. File order and timestamps are normalized so identical input produces
the same hash.

### Runtime bundle

Minimum manifest fields:

```json
{
  "manifest_version": 1,
  "runtime_version": "0.7.0",
  "contract_version": "1.0.0",
  "core_git_sha": "<full sha>",
  "platform": "macos",
  "arch": "arm64",
  "files": {
    "api-http": "<sha256>",
    "whisper-cli": "<sha256>",
    "ffmpeg": "<sha256>",
    "ffprobe": "<sha256>"
  }
}
```

The bundle also includes runtime notices and any libraries required by those
executables. The app verifies the bundle before copying it into the product.

### Frontend lock

`backend.lock` pins the core commit, contract artifact, runtime artifact,
download location and hashes. It never contains credentials. Normal CI and
local builds do not resolve a moving branch or tag.

## Compatibility rules

- current `/v1` remains the protocol-major namespace;
- runtime and contract versions are additive fields in `api.started` and
  `/v1/health`;
- an app starts normal use only when its locked compatibility rule accepts the
  running sidecar;
- optional response fields and new optional endpoints are additive;
- removed fields/endpoints, newly required input, narrowed enum values or
  changed authority semantics are breaking;
- a breaking change must provide an explicit app migration and cannot enter a
  supposedly compatible runtime bundle.

## Test layers

| Layer | Adapter / input | Purpose |
|---|---|---|
| Schema mock | locked OpenAPI artifact | stateless layout and decode smoke |
| Stateful frontend test | in-memory `ApiTransport` adapter | jobs, errors, retry, cancellation and ordered scenarios |
| Consumer contract | locked canonical examples | typed Dart parsing and mapper behavior |
| Backend contract | real router and response validation | implementation conforms to canonical contract |
| Product integration | locked runtime bundle | handshake, REST, SSE, files, SQLite and lifecycle |
| Packaged smoke | signed assembled app | actual shipped topology |

Prism or an equivalent schema mock does not replace stateful or packaged tests.

## Code generation checkpoint

The spike selects a small stable endpoint family and records:

- pinned generator and configuration;
- deterministic regeneration and zero dirty diff;
- compilation under the pinned Flutter/Dart toolchain;
- OpenAPI 3.1 nullable, `anyOf` and `oneOf` behavior;
- bearer injection and error mapping;
- absence of unjustified `dynamic` wire fields;
- explicit wire-to-UI mapper;
- fixture parity with the handwritten client;
- generated diff size and review usability.

Timeline compatibility parsing and SSE event assembly are outside the spike.
Failure does not block repository separation.

## Migration safety

- no source directory is deleted from the current repository during artifact
  preparation;
- history-preserving repository creation is performed from a verified commit;
- every artifact is reproducible from its recorded core commit;
- split repositories run in parallel until integration and packaged smoke pass;
- archiving the current repository is a separate owner-authorized operation;
- rollback before archive means returning `backend.lock` and product assembly to
  the last validated monorepo build, not rewriting source history.

## Out of scope

- remote deployment of the local backend;
- changing localhost bearer authority or keychain semantics;
- changing learning domain authority;
- replacing SQLite;
- rewriting the production pipeline;
- full Dart model generation;
- mobile or Windows/Linux delivery;
- product feature work hidden inside migration changes.
