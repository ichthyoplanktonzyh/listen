# Phase 3.19.3 Plan: Versioned Frontend / Core Repository Separation

Status: PLANNED

Date: 2026-07-28

Parent phase: Phase 3.19 Product Validation & Release Closeout

Upstream inputs: ADR 0031, `3.19.3-CONTEXT.md`, current `ARCHITECTURE.md`,
`STACK.md`, `TESTING.md`, ADR 0014 and the Phase 3.19 product-correction gate.

## Objective

Create independently developable frontend and core repositories without
changing product semantics or pretending the bundled local sidecar is an
independently deployed backend.

Success means:

- `listen-core` can validate contracts and publish a reproducible contract
  release and macOS arm64 runtime bundle;
- `listen-app` can build, test and package from pinned artifacts without a core
  source checkout;
- frontend and backend implementations can proceed in parallel after a contract
  release;
- one final product release manifest proves exactly which two commits and
  artifacts shipped;
- the current repository remains recoverable until all cutover gates pass.

## Slice 0 — Decision, inventory and baselines

Deliverables:

- accept ADR 0031;
- record all frontend dependencies on root contracts, fixtures, `fvp`, Cargo
  targets, runtime assets and packaging scripts;
- classify scripts and fixtures by `listen-core`, `listen-app` or historical;
- record current contract path/operation counts, artifact file lists, hashes,
  build commands and packaged smoke behavior;
- define repository names, hosting visibility and artifact retention before
  creating remote repositories;
- create a migration ledger mapping every top-level path to its target.

Acceptance:

- every tracked top-level path has an owner or explicit archival disposition;
- no secret, local credential, user media or ignored build output enters an
  artifact;
- the baseline identifies the existing sidecar handshake, REST, SSE, shutdown,
  SQLite and packaged-app lifecycle;
- no product behavior changes.

## Slice 1 — Versioned contract release interface

### 1.1 Contract structure

- separate canonical contract files from generated experiments;
- add a machine-readable contract manifest and deterministic packaging command;
- pin an OpenAPI validator/linter version;
- validate paths and HTTP methods, not just path strings;
- add representative request/response validation through the real router;
- retain and package SSE/resource schemas and canonical examples;
- add compatibility comparison against the previous released contract.

### 1.2 Runtime negotiation

- add `runtime_version` and `contract_version` to the `api.started` handshake
  and health response without exposing credentials;
- teach Flutter to verify a supported contract range before normal startup;
- render an actionable incompatibility failure instead of allowing later decode
  errors;
- keep the existing address/token authority and lifecycle unchanged.

### 1.3 Publishing

- build the contract archive from a clean recorded commit;
- normalize archive metadata;
- emit SHA-256 and manifest;
- make local publication testable without GitHub Actions;
- define immutable release naming.

Acceptance:

- rebuilding the same contract commit produces the same content hashes;
- a route-method mismatch fails;
- representative real responses validate against their documented schemas;
- a known breaking fixture fails compatibility classification;
- both current Flutter and Rust tests consume the packaged canonical examples;
- no CI step fetches `main` as a build dependency.

## Slice 2 — Reproducible runtime bundle interface

### 2.1 Core bundle builder

- split `build-macos-mvp.sh` into core runtime production and app assembly;
- package `api-http`, required runtime executables/libraries, manifests and
  notices;
- record platform, architecture, core commit, runtime version, contract version
  and per-file hashes;
- verify executable architecture and dynamic-library resolution;
- make output paths independent of the frontend checkout.

### 2.2 Runtime verification

- add an isolated temporary-home smoke that starts the bundled sidecar;
- validate handshake versions, authentication, health, graceful shutdown and
  parent reaping;
- run focused REST/SSE lifecycle smoke against the bundle;
- prove the bundle contains no database, key, user path or local configuration.

Acceptance:

- the runtime bundle is reproducible from its manifest commit;
- it starts outside the source tree;
- contract version in the bundle matches the packaged contract;
- all files pass recorded hash verification;
- the bundle is sufficient for app assembly without Cargo.

## Slice 3 — Frontend external-dependency mode and codegen spike

### 3.1 Repository-root independence

- move/copy the `fvp` fork into the future frontend-owned layout and update the
  path dependency;
- replace `../../contracts` and `../../testdata` reads with frontend-local,
  provenance-bearing locked fixtures;
- remove ancestor `target/**/api-http` discovery from the default development
  path after a locked runtime launcher exists;
- retain explicit `LLPLAYERNEXT_API_URL`, token and binary overrides for
  focused development/testing;
- add `backend.lock` and tools to fetch, verify and unpack exact artifacts;
- make Flutter analyze/test/build work from a standalone frontend staging
  directory.

### 3.2 Codegen decision checkpoint

- pin one generator toolchain and configuration;
- generate a small stable wire-client family into a replaceable staging module;
- map generated DTOs into existing handwritten UI/domain models;
- run the checkpoint recorded in `3.19.3-CONTEXT.md`;
- write the result as a short decision note or follow-up ADR before expanding.

Expansion is allowed only if:

- regeneration is deterministic;
- types are no weaker than the handwritten wire types;
- nullable/union behavior matches fixtures;
- auth and errors remain explicit;
- generated code requires no manual edits;
- the mapper preserves compatibility behavior;
- review and build cost is acceptable.

Otherwise delete the spike output and proceed with handwritten transport DTOs
plus stronger generated guards.

Acceptance:

- frontend tests and release build run without a core source checkout;
- a tampered contract or runtime artifact is rejected before use;
- changing the locked dependency produces an explicit reviewable diff;
- codegen outcome is recorded and is not a hidden prerequisite for cutover.

## Slice 4 — History-preserving repository materialization

### 4.1 Prepare filtered histories

- select one verified cut commit after Slices 1–3;
- create filtered histories in temporary local repositories;
- preserve relevant commits, authors and timestamps;
- relocate `apps/desktop` to the frontend root and frontend-owned third-party
  paths to their final locations;
- retain canonical contracts and runtime sources in core;
- partition planning documents and provide cross-repository ADR references;
- replace obsolete root-relative documentation.

### 4.2 Verify before remote creation

- compare tracked path ledgers with both outputs;
- scan for secrets and unintended local artifacts;
- build/test both filtered repositories;
- verify commit ancestry and tag mapping;
- prepare repository descriptions, default branch rules, PR templates and issue
  migration policy.

No remote repository is made authoritative until the owner confirms names and
visibility.

Acceptance:

- every intended source file exists in exactly the right repository;
- no canonical contract has two writable authorities;
- frontend and core pass their standalone local gates;
- old history needed to explain retained code remains reachable;
- the original repository is unchanged and usable.

## Slice 5 — Independent CI and coordinated release flow

### 5.1 `listen-core` CI

- Rust format, Clippy, tests, coverage, supply-chain and architecture gates;
- contract validation and compatibility gate;
- deterministic contract artifact build;
- platform runtime bundle build and smoke;
- artifact provenance and checksum publication.

### 5.2 `listen-app` CI

- verify `backend.lock` and artifact hashes;
- verify generated wire code or handwritten contract guards;
- Flutter analyze/test/build;
- frontend scenario tests;
- integration against the locked runtime bundle;
- final app assembly and packaged smoke on release workflow only.

### 5.3 Dependency update flow

- contract-first core pull request merges and publishes an immutable artifact;
- app dependency-update pull request changes `backend.lock`, fixtures/mappers
  and code as needed;
- backend implementation may proceed after the contract release;
- final app release pins a non-prerelease runtime artifact;
- release notes link both repositories and exact validation evidence.

Acceptance:

- ordinary frontend CI never checks out core source;
- ordinary core CI never checks out frontend source;
- cross-repository integration uses only published interfaces;
- pending/failed/unstarted Actions are reported honestly under issue #75;
- duplicate push/pull-request workflows are avoided.

## Slice 6 — Dual-run integration, packaged smoke and cutover

Run both old and split build paths from the same cut commit/artifacts and compare:

- contract and runtime manifests;
- executable architectures and bundled file lists;
- handshake and compatibility behavior;
- representative REST and SSE flows;
- database creation/migration and persistence restart;
- local media/subtitle import and playback integration;
- provider configuration/keychain non-disclosure;
- graceful shutdown and crash/parent-exit cleanup;
- final app signing structure and packaged smoke.

Cutover gates:

1. core and app standalone local strict gates pass;
2. required remote CI is green, or the owner records the explicit issue #75
   exception allowed by project policy;
3. dependency update from one released contract/runtime version to the next is
   demonstrated;
4. one release candidate is built solely from pinned split-repository artifacts;
5. owner executes the retained Phase 3.19 packaged journeys and records the
   result;
6. rollback instructions are tested;
7. repository URLs, issue ownership and release ownership are documented.

Only after all gates:

- make split repositories authoritative;
- freeze new changes in the old repository;
- tag the final integrated commit;
- archive the old repository read-only in a separate owner-authorized action.

## Validation matrix

### Documentation/planning slice

```sh
git diff --check
git status --short
```

### Contract slice

```sh
./scripts/validate-contracts.sh
cargo test -p api-http openapi
```

Plus the new document validator, response-schema and compatibility commands
introduced by Slice 1.

### Core/runtime slice

```sh
./scripts/test.sh --rust --strict
python3 scripts/check-architecture-coupling.py
```

Plus isolated runtime-bundle smoke and hash reproduction.

### Frontend slice

From a standalone frontend staging directory:

```sh
flutter pub get
flutter analyze
flutter test
flutter build macos --release
```

Plus lock verification, consumer contracts and locked-runtime integration.

### Final cutover

```sh
./scripts/test.sh --full --strict --low-memory
./scripts/validate-contracts.sh
./scripts/verify-mvp.sh
git diff --check
```

Equivalent standalone repository commands replace the monorepo commands before
cutover is accepted.

Paid/live model tests are excluded unless separately authorized. No credential
is read, printed or persisted by this phase.

## Exit signals

- frontend development no longer requires a backend source checkout;
- backend development no longer requires Flutter;
- contract changes are immutable, versioned and explicitly adopted;
- final packaging can identify and verify every backend input;
- generated-client adoption is evidence-based and compatibility parsers retain
  their semantics;
- the old repository can be archived without losing the ability to build,
  test, diagnose or roll back the shipped product.
