# Phase 3.12.2 Closeout: Studio LLM Feedback Wiring

状态：COMPLETE — owner 真实 provider QA 通过（2026-07-16）。
完成时间：2026-07-16 CST

## Outcome

3.12 就绪的 LLM provider（judge + rubric 两个 application seam）已真正接入三个 Studio 的
任务流。用户配置自有 provider 后可以「AI 生成理解题 → 复核编辑 → 落库 → 作答 → AI 逐点
判定 → 纠正」，Speaking retelling 与 Writing 内容/组织判定走同一 SemanticJudgeProvider。
全程保持显示诚实边界：LLM 输出是可纠正的辅助反馈、可 adjudicate、evidence_class 保持
`heuristic_proxy`、零 observation/projection 写入。manual rubric + 自评路径保持一等公民，
无 provider / provider 失败时诚实降级、不阻塞任务。本 phase 取代已取消的 3.12.1
留出集资格门（产品裁决见上游 discuss §7/§10）。

## Delivered

- **Slice 1（Reading judgment 显示，纯 Flutter）**：typed provider 列表 + `judgeViaLlmProvider`
  API；`ReadingTaskController.requestLlmJudgment` / `adjudicateLlm`；task sheet 在 assessing/done
  提供「请求 AI 反馈」与逐点 LLM 判定（可纠正）；无 judgment-capable provider 时整块隐藏。
- **Slice 2（Reading rubric 生成，后端 + Flutter）**：`POST /v1/llm/providers/{id}/rubric` 只返回
  内容草稿、不落库；身份/版本/快照 hash 仍只在用户保存已审阅 rubric 时服务端铸造（守 ADR
  0021 四层分离）；保存时记录诚实 `llm` provenance（含 model_id/prompt/schema 版本）。
- **Slice 3（复制到 Speaking + Writing，零后端改动）**：judge 用例按 attempt_id +
  response_revision 取存量作答、purpose 无关。三 Studio 共用抽取出的 `LlmJudgmentAssist`
  widget（第三住户出现后才抽取）与 `pickLlmProviderId`/`preferredLlmProviderId` 选择逻辑。
  Writing 判定最新 attempt 的最新 revision，提交修订稿后旧判定清空、不跨 revision 冒充；
  与 Harper 表面 finding 明确分离。
- 途中修复：OpenAI 兼容适配器改用 `json_object` 结构化输出（schema 内嵌 prompt），兼容
  DeepSeek 等仅支持 `json_object` 的端点；语义层后校验不放松（SchemaInvalid 不写 judgment）。

## Evidence Boundary

- LLM 判定永不冒充用户自评，也不改写 manual judgment；两者并存、各自 provenance。
- 纠正走 append-only adjudication，引用 LLM judgment id；原判定行永不改写。
- 显示诚实边界不因跳过 3.12.1 而放松：仍不写能力层（负向测试钉住零 observation/projection）。
- provider 失败（离线/认证/拒绝/截断/schema 无效）结构性不落 judgment（provider 返回 Err
  于 draft 存在之前），错误如实浮出、manual 路径不受影响。
