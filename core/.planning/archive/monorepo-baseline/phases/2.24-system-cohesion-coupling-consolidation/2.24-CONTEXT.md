# Phase 2.24 Context: System Cohesion & Coupling Consolidation

> 建档：2026-07-14
> 来源：2026-07-14 全系统耦合审核；复核 `AGENT.md`、Cargo 依赖、Rust 公共接口、
> Flutter HTTP client、Python production pipeline 与 Phase 2.23 历史结论。

## 触发背景

Phase 2.23 和 2026-07-14 大文件治理已解决 god file、状态双轨、fat
`SubtitleRepository`、Dart/Rust 巨型文件等明显结构问题。当前依赖图仍然单向且健康：

```text
domain <- core engines <- application <- adapters / api-http composition root
```

本轮审核确认，剩余风险不再主要来自文件大小，而来自接口和 seam 的形状：

1. `api-http` 同时承担 HTTP 适配、模型/资源下载、文件系统、子进程、任务队列、状态机和
   事件发布；运行时能力改变会迫使传输 crate 一起变化。
2. `application` 合法依赖 `speech-analysis` 核心引擎，但若干公共方法直接暴露
   `speech_analysis::*` 实现类型；`speech-analysis` 又把 17 个实现模块全部公开。
3. `AppServices` 持有 21 个依赖并承载约 169 个公开方法；部分 repository trait 按存储位置
   聚合多个变化原因，而不是形成深模块。
4. Flutter `LocalApi` 已有真实 transport seam，但约 147 个资源方法中约 97 个仍返回
   `Map<String, dynamic>` / `dynamic`，JSON 解析责任泄漏到 controller。
5. Rust wildcard import、`persistence-sqlite/src/subtitles.rs` 和 Python
   `production_pipeline.py` 仍扩大隐式依赖与修改半径。

## 对前次审核的校正

- `application -> speech-analysis` 是架构文档明确允许的应用用例到核心引擎依赖，不是违规。
- 纯 in-process 算法只有一个实现时，不为“可能替换”机械创建 provider trait。
- `speech-analysis` 先收窄外部 interface，再根据独立依赖/发布/所有权需求决定是否拆 crate。
- `domain` 先治理扁平 re-export 和 wildcard import，不因模块数量直接拆成多个 crate。
- `SqliteRepository` 可继续同时实现多个窄 trait；问题在 trait 是否聚合了多个变化原因，
  不在 concrete adapter 数量。

## 设计词汇与裁决标准

本 phase 统一使用 deep-module 词汇：Module、Interface、Implementation、Seam、Adapter、
Depth、Leverage、Locality。

每个拟新增 seam 必须先回答：

1. 删除该 module 后，复杂度会消失还是散回多个 caller？
2. 生产与测试是否至少需要两个合理 adapter？
3. caller 是否只需学习稳定结果、错误与不变量，而无需理解实现步骤？
4. 测试能否只通过 module interface 观察行为？

只有一个 adapter 且没有真实变化轴时，默认不建 trait。纯计算优先直接形成深 module；
本地进程、文件系统和网络等 true external/local-substitutable 依赖可建立内部 seam，生产使用
真实 adapter，测试使用 in-memory/fake adapter。

## 与相邻 Phase 的关系

- **2.23**：本 phase 是其语义级后继。2.23 解决机械结构和安全网，本 phase 解决 interface
  深度与 seam 位置；不修改冻结的 2.23 文档。
- **3.12.1 / 3.13**：产品主线不被重新编号。本 phase 是独立治理线，P0/P1 slice 建议在
  3.13 大规模扩展 HTTP、application 和 Flutter DTO surface 前完成。
- **2.19/2.20/2.21**：算法质量线继续搁置。本 phase 不改算法语义，只收窄算法 interface。
- **4.0**：未来下载管理器应复用本 phase 抽出的 runtime/download module，不在
  `api-http` 再造第二套队列和下载状态机。

## Phase 原则

1. 不改用户可见行为、HTTP/OpenAPI contract、SQLite schema、LLTimeline contract 或算法语义。
2. 先替换旧 interface 再删除旧路径；禁止长期保留“新 module + 旧 pass-through wrapper”双层。
3. 每个 slice 独立可验证、可回滚；结构迁移与行为变化不得混在同一 commit。
4. 新增 trait 必须在设计记录中列出至少两个合理 adapter；否则使用 concrete deep module。
5. 不用行数比衡量 depth；验收以 caller 知识量、公开类型泄漏、依赖方向和测试 surface 为准。
6. Phase 完成时同步 `ARCHITECTURE.md`、`STACK.md`（如新增 crate/依赖）和必要 ADR。

## 非目标

- 不重写播放器、HTTP 协议、数据库或生产算法。
- 不引入微服务、事件总线框架、通用 DI 容器或新的 Flutter 状态框架。
- 不自动生成 Dart DTO；继续遵守 ADR 0014 的手写 typed model + fixture contract test 机制。
- 不以“每个文件/算法一个 trait”作为解耦结果。
- 不承诺在本 phase 拆分 `domain` 或 `speech-analysis` crate。
