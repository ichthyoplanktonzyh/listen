## Core Product Target

Phase 2.20 的核心目标不是预测一句话“通常应该怎么读”，而是在字幕上让用户看见：

```text
this speaker's actual audible structure in this utterance
```

也就是当前音频里真实可听到的：

- prominence / stress anchors;
- weak groups and reductions;
- compressed spans / fast packed regions;
- phrase or thought-group boundaries;
- learner-facing hotspots explaining why written words differ from what was heard.

因此，“actual” 是本阶段的关键约束。文本可以提供 prior，但不能单独证明真实
delivery。

## Route Review

Theoretical routes:

| Route | Signal Source | Can Measure Actual Prominence? | Role |
|---|---|---|---|
| A text prediction | transcript, POS/function words, dictionary stress, syntax | no; predicts default reading | fallback / prior |
| B acoustic prosody direct measurement | alignment + F0 + energy/intensity + duration | yes | production-side target |
| C CTC phone-derived rhythm | CTC phones, phone duration/count, phone mismatch | weak; mostly segmental evidence | downgrade to evidence layer |
| D forced-aligned duration/rate | WordTimeline/phone alignment + duration + local rate | partial; good timing skeleton | immediate main skeleton |
| E end-to-end prosody model | waveform -> prominence/break labels | yes, but black-box/heavy | future research candidate |
| F layered hybrid | text prior + D/B acoustic confirmation or override | yes, with provenance | Phase 2.20 target architecture |

## Decision

Keep the `RhythmFrame` contract and subtitle-layer UI direction.

Change the generator route:

```text
from:
  text-predicted anchors + CTC-derived token timing

to:
  forced-aligned WordTimeline skeleton
  + local duration/rate evidence
  + RMS energy/loudness evidence
  + optional F0/pitch evidence after calibration
  + CTC phone evidence only for segmental phenomena
```

This is a D -> F migration:

- D gives the stable timing skeleton: word boundaries, duration, rate, final
  lengthening.
- B contributes measured acoustic prominence and boundary cues, starting with
  RMS energy because it is cheaper and more robust than F0.
- F combines text priors and acoustic evidence with explicit provenance.

## Current Implementation Reclassification

What remains correct:

- `sound_analysis.rhythm_frame` resource shape.
- Flutter subtitle-layer rhythm ribbon, rhythm/phones toggle, expected
  pronunciation reference, cue loop.
- RhythmFrame QA scorer, Helsinki/LibriTTS weak-label scorer, benchmark role
  manifest, and evidence-class policy.

What is reclassified:

- Current `stress_anchors` are mostly `text_predicted`, not true observed
  prominence.
- Current CTC phone evidence should support flapping, deletion, weak-form and
  phone-mismatch explanations, but should not be the rhythm skeleton.
- `pre_boundary_lengthening` in `speech-analysis::sound_analysis` is useful as a
  research-backed `heuristic_proxy` and fallback, but it is still computed from
  the current sound-analysis timing path. It must not be treated as the final
  production route.

## Required Provenance Model

Future RhythmFrame items should carry evidence such as:

```text
text_predicted
forced_alignment_timing
duration_supported
rate_supported
energy_supported
pitch_supported
ctc_segmental_evidence
manual_product_qa
```

UI can keep this mostly hidden, but confidence and report output must preserve
it. The user-facing claim should differ between:

- “this is likely important from the text”
- “the timing supports this as a real anchor”
- “the audio energy/pitch supports this as actually prominent”

## Immediate Next Experiment

Before adding more production code, run a small comparison on 5-10 real
sentences:

1. Current CTC-derived RhythmFrame.
2. Forced-aligned WordTimeline + duration/rate skeleton.
3. WordTimeline + RMS energy prominence evidence.
4. Optional F0/pitch reset prototype if energy+duration is not enough.

Manual labels should judge:

- actual prominent words;
- weak/reduced groups;
- compressed regions;
- phrase boundaries;
- whether each displayed hotspot is `correct`, `useful_but_incomplete`,
  `unclear`, `misleading`, or `unsupported`.

The goal is to decide whether duration+energy is sufficient for Phase 2.20
closeout, and where F0 is necessary.

## Production Architecture Boundary

Heavy acoustic extraction belongs in the local production pipeline, not the
Flutter consumer app.

The consumer app should render precomputed `RhythmFrame` values from
`.lltimeline.json`. It does not need `librosa`, Praat, Parselmouth, torch, or an
F0 model at runtime.

Therefore, missing local Python packages or consumer-app lightness are not valid
reasons to exclude production-side RMS energy or F0 extraction. They are setup
tasks and architecture decisions, not product-science constraints.
