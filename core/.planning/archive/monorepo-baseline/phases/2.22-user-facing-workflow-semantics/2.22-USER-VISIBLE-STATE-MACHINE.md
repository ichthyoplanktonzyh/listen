# Phase 2.22 User-Visible State Machine

状态：AUTHORITATIVE MODEL (verified against current `main`)

日期：2026-07-01

## Why This Document Exists

`2.22-PLAN.md` Step 0 promised a "current user-visible state map for AppBar,
playback overlay, side panel, bottom controls, task centers and status
feedback." The Step 0 audit (`2.22-STEP0-UI-AUDIT.md`) delivered a prose region
table with a "current visible states" column, but no states-as-nodes, no events,
no transitions and no guards. That is an inventory, not a state machine.

This document is the missing state machine. It is modeled on
`worktree-ui-feature-semantic-mapping/ui-analysis/07-user-visible-state-machine.md`,
but every region here is re-verified against the current `apps/desktop` code, and
each region is wired to the Phase 2.22 capability-readiness semantics instead of
the older `sound pattern` vocabulary.

It is the source of truth for:

- what the user can actually see on screen at any moment;
- which event moves the UI between those visible states;
- which guards gate each transition;
- which visible-state defects remain, and which have already been fixed.

Read `2.22-FEATURE-SEMANTICS-MODEL.md` for the capability vocabulary and
readiness enum. This document reuses that vocabulary; it does not redefine it.

## Notation

```
Region {
  State {
    entry: what the user sees on entering this state
    on EVENT(guard): -> TargetState / side effect
  }
}

Marks:
  ✅ FIXED    a defect from ui-analysis/07 that current main already resolves
  ⛔ BUG      a defect still present in current main
  ⚠️ RISK     a fragile design point, not yet a hard bug
  → OWNER     Phase 2.22 step (or a later phase) that should own the fix
```

Two kinds of state machine live here and must not be confused:

1. **Surface regions** (Sections R0–R8): what is drawn on screen. Orthogonal —
   they run concurrently.
2. **Capability readiness lanes** (Section C): the lifecycle of each learning
   capability (`unavailable → generating → available/degraded/...`). These are
   *derived* from data, and they *drive* what several surface regions render.

The whole point of Phase 2.22 is that the surface regions should stop being
driven by free strings and start being driven by lane state.

## R0 — Backend / Core Shell

Top-level gate. Verified: `main.dart` starts the local core and only enters the
player once the API is connected.

```
CoreShell {
  Starting {
    entry: centered progress + "Starting local core..."; AppBar disabled
    on CORE_CONNECTED:        -> Connected
    on CORE_START_FAILED(e):  -> StartupError(e)
  }
  Connected {
    entry: full player shell mounts; AppBar enabled
    // all other regions (R1..R8) only exist inside Connected
  }
  StartupError {
    entry: startup error copy + retry affordance
    on RETRY: -> Starting
  }
}
```

✅ FIXED (07 had no explicit model here): backend startup failure is a distinct
top-level state, so the user cannot confuse "core failed to start" with "media
failed to open".

```
SubtitleOverlay {
  NoTrack { entry: no subtitle text on the video }
  Hidden  { entry: track exists but overlay toggled off }
  Visible {
    PrimaryOnly   { entry: interactive TokenLine only }
    Dual          { entry: TokenLine + secondary line }

  on SECONDARY_TRACK_LOADED: PrimaryOnly -> Dual
```

Orthogonal sub-layers inside `Visible` (each independently gated):

```

  wordHighlight:  current word styled while playing   (lane: Word Sync)
  statusStyles:   per-word learning-status colors      (toggle: Word Styles)

PhonemeRibbon        { Hidden | Visible; empty data -> not drawn }

  Hidden
```

```
DownloadBar {
  Hidden { entry: no download UI }
  Downloading { entry: progress bar + Cancel + "downloading in background N%" }
  Completed   { entry: full bar + "Download complete" + Open + Dismiss (x) }
  Failed      { entry: full bar + "Download failed: <e>" + Dismiss (x) }

```

✅ FIXED (07 P0 #1 partial / audit Step 5): the bar is now a typed
`DownloadStatusSnapshot`; cancel/dismiss invalidate the active download

✅ FIXED (SM-03, refactor increment 2): the split state is gone. A single
`DownloadController` (`controllers/download_controller.dart`) owns the whole

`downloadGeneration`, and `PlayerController` no longer holds
`downloadProgress`/`downloadedMediaPath`. The controller depends only on
`Stream`/`Future` primitives (not the download service), so it is unit-tested in
`test/download_controller_test.dart`; `flutter analyze` + full `flutter test`
(131) green.
✅ FIXED (SM-04): UX decision landed. `Failed` auto-dismisses after a configurable
delay (`DownloadController.failedAutoDismiss`, default 10s) since it has no useful

`test/download_controller_test.dart`; `flutter analyze` + full `flutter test`

## Section C — Capability Readiness Lanes (the real learning state machine)

This is the part the capability model (`2.22-FEATURE-SEMANTICS-MODEL.md`) names
but does not yet model as a *machine*. The readiness enum is a set of nodes; the
transitions between them are what a user experiences as "the app got smarter".

Shared lane shape (states from `CapabilityReadinessState`):

```
Lane<capability> {
  unavailable   // no input for this layer
  generating    // a job/refresh is producing it
  available     // ready, audio-backed where relevant
  degraded      // usable but estimated / predicted-only / lower quality
  stale         // exists but may not match active media/subtitle
  unsupported   // this media/language/path cannot support it
  error         // last attempt failed
}
```

### C.1 Word Sync lane (modeled in code)

```
unavailable --IMPORT_SRT/VTT--> unavailable        // plain text has no timing
unavailable --RUN_WHISPER--> generating
generating  --WHISPER_DONE(has word timings)--> available   // audio-backed
generating  --WHISPER_DONE(no word timings)--> unavailable
unavailable --ATTACH_LLTIMELINE(active WordTimeline)--> available|degraded
available/degraded --ACTIVATE_OTHER_SUBTITLE--> stale --REFRESH--> recompute
*           --TIMELINE_LOAD_FAILED--> error
```

Guard `audio-backed`: timing source ∈ {forced_aligned, asr_aligned, asr_reported,
user_adjusted} ⇒ `available`; else (estimated) ⇒ `degraded`.
Implemented: `capability_readiness.dart _wordSyncReadiness`.

### C.2 Chunk Replay lane (modeled in code)

```
unavailable --(no track)--> unavailable
unavailable --(track, no word sync)--> unavailable("needs word timing")
has-word-sync --GENERATE_CHUNKS / ATTACH(active ChunkTimeline)--> available
*             --TIMELINE_LOAD_FAILED--> error
```

Depends on Word Sync lane. Implemented: `_chunkReplayReadiness`.

### C.3 Listening Structure lane (modeled in code)

```
unavailable --(no track | no word sync)--> unavailable
has-word-sync --document rhythm_frames present, audio-supported--> available
has-word-sync --frames present, text-prior only--> degraded (PredictedOnly)
has-word-sync --no frames--> unavailable
*             --TIMELINE_LOAD_FAILED--> error
```

`available` requires audio-backed word sync AND at least one frame with an
audio signal source (timing/energy/pitch/phone_segmental). This is the honesty
guard: predicted-only frames stay `degraded`. Implemented:
`_listeningStructureReadiness` + `_rhythmFrameHasAudioSupport`. This lane state
IS what R3.ListeningLayer.Mode.Structure should render.

### C.4 Phone Evidence lane (modeled in code)

```
unavailable --(no track | no active PhoneTimeline)--> unavailable
unavailable --RUN_AUDIO_ANALYSIS--> generating   // NOT yet wired to readiness
generating  --ANALYSIS_DONE(phones>0)--> available
*           --TIMELINE_LOAD_FAILED--> error
```

Implemented: `_phoneEvidenceReadiness`. ⛔ the `generating` transition is not
wired — audio-analysis job state (`UserTaskStatus`) and this lane are separate;
they should converge. → OWNER Step 4 / Step 5.

### C.5 Lanes named in the model but NOT modeled as readiness

`2.22-FEATURE-SEMANTICS-MODEL.md` Capability Stack lists Media source, Playback,
Transcript/overlay, Vocabulary, Diagnosis, Practice/Review and System/tasks. None
of these have a `CapabilityReadiness` lane in code today
(`UserCapability` enum = {subtitles, wordSync, chunkReplay, listeningStructure,
phoneEvidence}). `2.22-PLAN.md` Step 1 explicitly required readiness for
media/playback, transcript/overlay, vocabulary, diagnosis, downloads/jobs and
practice/review. → OWNER frontend refactor stage; and → OWNER accounting: do not
report Step 1 readiness as complete.

### C.6 Where each lane is surfaced today

| Lane | Surfaced in | Missing surfaces |
|---|---|---|
| Word Sync | Resources tab strip, subtitle resource tiles | overlay word highlight does not read the lane; post-Whisper completion summary |
| Chunk Replay | Resources tab strip, tiles | bottom chunk controls do not read the lane |
| Listening Structure | Resources tab strip | R3 overlay re-derives audio support instead of reading the lane |
| Phone Evidence | Resources tab strip, tiles | diagnosis card, audio-analysis job convergence |
| media/playback, vocabulary, diagnosis, downloads, practice/review | — | not modeled |

Discovered reality (2026-07-01, deeper audit for SM-07 — corrected after reading
the code, not the model's assumption):

1. `SubtitleResourceManagerPanel` per-tile `_CapabilityChip` rows
   (`~277-318`) are driven by per-resource backend `SubtitleResourceCapabilities`
   counts, NOT by `CapabilityReadinessSnapshot`. This is a legitimately DIFFERENT
   data source (per-resource content) and purpose. It is not a duplicate and
   should not be naively merged into the active-resource readiness snapshot.
2. `TimelineResourceSummaryPanel` (`SubtitleResourceManagerPanel:161`) recomputes
   `CapabilityReadinessSnapshot.fromResources(...)` for its readiness strip using
   `visibleWordTimingCount` (which has a resource-count fallback when no
   per-sentence timings are loaded, `subtitle_resource_manager_panel.dart:80`).
3. `main._currentCapabilityReadiness()` computes it again for the generated-
   subtitle status text, using `_activeWordTimingCount()` WITHOUT that fallback.

So (2) and (3) are NOT identical: they can disagree on the word-timing count when
nothing is loaded yet. "Collapse into one" is therefore a small semantic
reconciliation (whose word count is canonical) plus an entanglement with the
panel's `hasWordSync` derivation — not a pure mechanical dedup. The overlay
listening layer and bottom chunk controls still read none of these and re-derive
from raw `rhythmFrame`/chunk state.

Revised SM-07 plan: the low-value dedup of (2)/(3) is deprioritized (they can be
made merely consistent). The high-value work is SM-07b: feed the overlay listening
layer from the `listeningStructure` lane and show a `predicted` badge (with a
"text-predicted, not measured audio" tooltip) when the current frame lacks an
audio signal source. → OWNER frontend refactor stage.
