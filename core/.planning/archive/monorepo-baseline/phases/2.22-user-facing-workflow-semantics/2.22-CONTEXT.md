# Phase 2.22 Context: User-Facing Workflow Semantics

状态：ACTIVE

日期：2026-07-01

## Why This Phase Exists

LLPlayerNext 现在已经有一整套用户功能，而不只是最近几个 phase 的新增能力：

- 媒体打开、URL 解析、在线下载、拖拽导入和播放控制；
- 主/副字幕导入、内嵌字幕提取、OpenSubtitles、本机 Whisper 生成字幕和转录中心；
- 字幕资源、LLTimeline 导入导出、WordTimeline / ChunkTimeline / PhoneTimeline 资源生命周期；
- transcript、字幕叠加、词级高亮、chunk replay、单句/区间循环和手动时间线审查；
- 词汇面板、词汇书、词汇导入导出、短语候选、lemma 校正和学习资源页面；
- 诊断卡、phone evidence、listening structure、document-level `rhythm_frames` 和音频分析任务；
- settings、工具路径、ASR 配置、日志导出、媒体归档、下载状态和全局任务反馈；
- practice/review backend foundation 已存在，但前端入口和状态仍需要收敛。

Phase 2.21 的 `rhythm_frames` 端到端追踪只是把一个更高层的问题暴露得更清楚：

```text
功能已经存在，但用户不知道该从哪里打开、何时可用、为什么不可用、下一步该做什么。
```

这不是单个 `rhythm_frames` 开关的问题，也不只针对 Phase 2.18-2.21。它说明当前 Flutter 前端仍混合了多套历史语义：

- 媒体、下载、字幕、资源、词汇、诊断、分析任务和设置各自有入口，但缺少统一的用户路径；
- subtitle resource 与 timeline resource 的关系不够清楚；
- WordTimeline、ChunkTimeline、PhoneTimeline、RhythmFrame 以内部名散落在 UI 中；
- `sound pattern`、`phonetic analysis`、`listening rhythm`、`phone evidence` 的层级混乱；
- 本机 Whisper 生成字幕后的自动资源链路没有被产品化表达；
- 用户看到的状态大多来自自由字符串，不能稳定表达 loading / ready / degraded / error；
- settings 里有许多能力开关，但它们不是用户完成任务的清晰入口；
- 侧面板、底部控制栏、下载栏、任务中心和字幕叠加层各自有局部状态，缺少统一的用户可见状态机。

Phase 2.22 因此单独成立，目标不是继续增加模型能力，而是把当前所有已存在的用户功能变成用户可理解、可发现、可验证的端到端工作流。

## Input From UI Worktree

`worktree-ui-feature-semantic-mapping` 中的两份草稿提供了重要输入：

- `ui-analysis/06-feature-interaction-map.md`
- `ui-analysis/07-user-visible-state-machine.md`

这些文档建立了两个关键视角：

1. 每个功能必须写清楚用户意图、触发方式、位置、视觉反馈、配置项和关联功能。
2. 前端需要建模用户可见状态，而不只是 controller/store 的内部状态。

Phase 2.22 会使用这些功能描述作为 Step 0 审计的种子清单。`2.22-CURRENT-FEATURE-INVENTORY.md`
先按该 worktree 的模块划分列出当前功能，再由后续代码审计校正触发入口、可用状态和真实行为。

该 worktree 早于 Phase 2.21，不能直接合并，也不能当作当前事实源。Phase 2.22 会吸收其方法和部分描述，但以当前 `main` 的事实为准，尤其是：

- `rhythm_frames` 已经是 document-level LLTimeline resource 的优先消费路径；
- CTC phone evidence 只属于 L4 segmental explanation；
- 本机 Whisper + WordTimeline 是当前最常见用户路径；
- energy-backed audible structure 仍需要生产端 artifact 或后续校准，不应在 UI 中伪装为必然可用。

## Product Reframe

Phase 2.22 把产品从“功能列表”重组为“用户任务路径”。范围覆盖当前全产品功能，而不是只覆盖最新的 audible-structure 相关功能。

核心路径：

```text
Open media
  -> Generate, import, search, extract, or attach subtitles/resources
  -> Get word-level timing when available
  -> Learn with synchronized words/chunks
  -> Inspect listening structure when available
  -> Open phone evidence only as detail
  -> Click words, diagnose, practice, review
```

用户不应该需要理解以下内部事实才能使用产品：

- 哪个菜单里藏着生成字幕、提取内嵌字幕、字幕资源、时间线资源或音频分析；
- `rhythm_frames` 在 JSON 的哪个字段；
- 当前 frame 来自 document-level LLTimeline 还是 `sound_analysis` fallback；
- WordTimeline 是 imported、ASR aligned、forced aligned、user adjusted 还是 estimated；
- ChunkTimeline 与 WordTimeline 的生成依赖；
- PhoneTimeline 是否存在；
- 某个开关为什么开了但没有显示任何东西。

用户需要看到的是：

- 这条字幕现在有哪些学习能力；
- 哪些能力正在生成；
- 哪些能力因为缺少输入而不可用；
- 不可用时下一步应该做什么；
- 当前屏幕显示的是 predicted reference、audio-supported listening structure，还是 low-confidence evidence。

## Definition Of Done For A Feature

Phase 2.22 重新定义“功能完成”。

一个已完成功能必须同时满足：

1. **Discoverable**：用户能在合理位置发现入口，不依赖隐藏设置或开发者知识。
2. **Actionable**：入口文案说明它能做什么，前置条件不足时说明下一步。
3. **Stateful**：loading、ready、degraded、unsupported、error 都有明确 UI 状态。
4. **Composable**：功能与媒体、字幕、timeline、学习状态、诊断等依赖关系清晰。
5. **Honest**：预测、估计、音频支持和人工校对结果不能混同。
6. **Recoverable**：失败后用户知道如何重试、刷新、切换资源或关闭该层。
7. **Tested End To End**：至少覆盖一条真实或 fixture 驱动的用户流程，而不是只测字段解析。

## Canonical User Journeys

Phase 2.22 首先固定以下验收路径。前五条是 P0，后续路径用于确保旧功能也被纳入本 phase。

### Journey A: Open And Play Media

```text
Open local file / URL / downloaded media
  -> playback surface and controls enter the right state
  -> drag/drop, URL resolve, download, audio track and error states are understandable
```

### Journey B: Subtitle Acquisition

```text
Import SRT/VTT
  or generate with local Whisper
  or search OpenSubtitles
  or extract embedded text subtitles
  -> primary/secondary track state is clear
  -> transcript and overlay update
```

### Journey C: Local Whisper Default Path

```text
Open local video/audio
  -> Generate subtitles with local Whisper
  -> Generated subtitle track loads
  -> active WordTimeline exists when Whisper JSON has word timings
  -> transcript and word highlight work
  -> listening structure layer can render document-level rhythm_frames
  -> missing energy/phone evidence is clearly represented
```

这是当前最重要的 learning path，也是本 phase 的 P0。

### Journey D: Existing SRT/VTT Path

```text
Open media
  -> Import SRT/VTT
  -> Text subtitles work
  -> word/chunk/listening layers show unavailable or estimated states honestly
  -> user can still do vocabulary and sentence diagnosis
```

### Journey E: LLTimeline Resource Path

```text
Open media
  -> Import or attach .lltimeline.json
  -> user sees subtitle resource capabilities
  -> active WordTimeline drives word sync
  -> document-level rhythm_frames drive listening structure
  -> PhoneTimeline, if present, is exposed as phone evidence
```

### Journey F: Learning And Diagnosis Path

```text
Click subtitle word
  -> word panel opens with lexical entry
  -> user changes learning status
  -> subtitle/transcript styles update
  -> diagnosis updates
  -> practice/review readiness is visible when available
```

### Journey G: Degraded Evidence Path

```text
Current sentence lacks WordTimeline / rhythm_frames / phone evidence / energy
  -> UI says exactly which layer is missing
  -> UI offers the nearest next action
  -> no predicted-only claim is displayed as measured audio
```

### Journey H: Vocabulary And Asset Management

```text
Open vocabulary / learning assets
  -> search/filter/edit/export/import
  -> source sentence and missing-media states are understandable
  -> word status changes remain consistent with subtitle/transcript styles
```

### Journey I: System And Task Feedback

```text
Download / transcription / audio analysis / import / export / archive task
  -> user sees working, success, degraded, error and next action states
  -> transient and persistent statuses do not fight each other
```

## Non-Goals

This phase does not:

- change the Phase 2.21 audible-structure algorithm or W8 manual QA standard;
- make RMS/energy calibration a release gate before manual evidence exists;
- add production-heavy Python/PyTorch/MFA/WhisperX runtime to the Flutter consumer app;
- solve Phase 3.0 practice/review product design beyond making backend-ready surfaces discoverable;
- preserve historical UI labels when clearer product language is available.

## Relationship To Phase 2.21

Phase 2.21 remains responsible for the correctness and quality of audible-structure data.

Phase 2.22 is responsible for the consumer experience around that data:

```text
2.21 answers: what is the correct structure and provenance?
2.22 answers: how does a user actually get to it, understand it, and trust its state?
```

The two phases can overlap. W8 manual listening labels may continue in 2.21 while 2.22 fixes how the feature is surfaced.
