# Phase 3.0.1 Architecture: Learning Loop Foundation

状态：BACKEND FOUNDATION COMPLETED

> 2026-06-28 更新：Practice / Review / LearningEvent 的 domain、application、SQLite 与
> API foundation 已落地。Corpus / Difficulty / LearnerProfile / Recording 目前有 domain
> shape 和 application seam，持久化/API 留给后续 slice。

## Architecture Goal

建立 Phase 3.0 学习闭环的领域边界：

```text
Existing learning assets and timelines
  -> Practice
  -> Observation / Review / Learning Event
  -> Corpus recall / Difficulty / Stats / L1-aware specialty
```

本文件描述目标架构，不表示当前 codebase 已经实现。

## Core Domain Areas

### 1. Practice

Practice 记录用户在真实音频语境中做的一次主动练习。

推荐核心模型：

```text
PracticeSession
  id
  started_at_ms
  ended_at_ms?
  mode                 # intensive / extensive / review / specialty
  media_id?
  track_id?
  source               # user_started / recommendation / review_queue / specialty

PracticeItem
  id
  session_id?
  kind                 # cloze / dictation / subtitle_fade / shadowing
  target               # lexical / sentence / chunk / segment / connected_speech
  prompt               # stable prompt snapshot
  expected_answer      # stable expected text/units, not necessarily shown to user
  anchors              # lexical ids, sentence ids, timeline refs, phone refs
  created_at_ms

PracticeAttempt
  id
  item_id
  submitted_at_ms
  input                # text / token sequence / recording ref / rating
  result               # correct / partial / incorrect / skipped
  score?
  evaluation           # token diff, missing words, timing deltas, etc.
  generated_observations[]
  generated_review_items[]
```

Key rules:

- `PracticeAttempt` is historical evidence. Do not mutate it when lexical status changes later.
- `PracticeItem.prompt` and `expected_answer` should preserve enough snapshot data to remain understandable
  even if media or subtitle rows are later missing.
- Practice failure may generate `LexicalObservation`, but it must not silently change global
  `LearningStatus`.
- Shadowing can reuse the same practice model, but recording-specific metadata should remain separate.

### 2. Review

Review is scheduling over learning evidence. It is not the same thing as lexical identity.

推荐核心模型：

```text
ReviewItem
  id
  source               # lexical_entry / practice_failure / chunk / sentence / connected_speech
  anchors              # lexical ids, sentence ids, chunk refs, phone refs
  prompt_snapshot
  status               # active / suspended / archived
  created_at_ms

ReviewSchedule
  item_id
  algorithm            # simple_box / fsrs_like / sm2_like
  due_at_ms
  stability?
  difficulty?
  interval_days?
  lapse_count

ReviewAttempt
  id
  item_id
  reviewed_at_ms
  rating               # again / hard / good / easy or local equivalent
  practice_attempt_id?
  next_due_at_ms?
```

Key rules:

- `LexicalEntry` remains the durable learning asset.
- `ReviewItem` points to lexical entries, chunks, sentences or connected-speech findings; it does not replace them.
- Anki export / AnkiConnect should adapt from `ReviewItem`, not define `ReviewItem`.

### 3. Learning Event Ledger

Learning events provide a stable fact source for stats and dashboard.

推荐核心模型：

```text
LearningEvent
  id
  occurred_at_ms
  kind                 # listening_started / listening_completed / practice_completed / review_completed / status_changed
  subject              # media / sentence / chunk / lexical_entry / review_item
  payload              # typed envelope with extra
  session_id?
```

Key rules:

- The event ledger is append-mostly.
- Dashboard should aggregate from events and durable attempts, not from transient Flutter state.
- Existing lexical status history can remain the source of truth for status transitions; a learning event may mirror
  it for analytics if needed.

### 4. Corpus Search

Corpus search indexes user-owned media and learning resources for YouGlish-like recall.

推荐核心模型：

```text
CorpusOccurrence
  id
  language
  kind                 # lexical / phrase / chunk / sound_pattern / connected_speech
  normalized_key?
  display_text
  media_id?
  track_id?
  sentence_id?
  timeline_ref?
  start_ms
  end_ms
  source_snapshot

PlayableSegment
  media_id?
  start_ms
  end_ms
  label
  subtitle_snapshot
  availability         # available / missing_media / missing_timeline
```

Key rules:

- Corpus index is derived and rebuildable; it should not become the authority for lexical status.
- `lexical_occurrences` remains valuable source data, but corpus search needs broader indexing for phrases,
  chunks and sound-pattern cases.
- Missing media must degrade to source snapshots rather than deleting learning history.

### 5. Difficulty And Input Fit

Difficulty is a derived profile used to decide whether content is suitable for extensive or intensive listening.

推荐核心模型：

```text
ContentDifficultyProfile
  subject              # media / sentence / segment / chunk
  language
  unknown_density
  known_not_recognized_density
  speech_rate_wpm?
  chunk_complexity?
  connected_speech_density?
  resource_quality?
  fit                  # too_easy / comprehensible / challenging / too_hard
  computed_at_ms
  input_fingerprint
```

Key rules:

- Difficulty is not identity. It should be recomputed when lexical status or timeline resources change.
- Keep the first algorithm explainable; avoid black-box recommendation early.
- Store enough provenance to explain why a segment was marked difficult.

### 6. Learner Profile And L1-L2 Diagnosis

Learner profile separates UI language from language background and target language.

推荐核心模型：

```text
LearnerProfile
  id
  ui_language
  l1_language?
  active_l2_language?
  created_at_ms
  updated_at_ms

L1L2DifficultyProfile
  l1
  l2
  difficulty_kinds[]   # weak_form, schwa, final_consonant, stress_timed_rhythm, ...
  explanation_templates
  specialty_query_rules

DiagnosisExplanationLayer
  base_reason
  connected_speech_explanation?
  l1_transfer_hint?
  practice_suggestion?
```

Key rules:

- L1-aware diagnosis must be data/profile driven, not hard-coded UI text.
- The first concrete profile is Mandarin -> English.
- L1 hints should be short and actionable, and should link back to real audio practice.

### 7. Recording And Shadowing

Recording supports shadowing and A-B comparison without forcing pronunciation scoring into v1.

推荐核心模型：

```text
RecordingAsset
  id
  file_path
  created_at_ms
  duration_ms
  media_ref?
  practice_attempt_id?
  target_segment

ShadowingComparison
  attempt_id
  reference_segment
  recording_id
  duration_delta_ms?
  pause_alignment?
  waveform_summary?
```

Key rules:

- Recording metadata belongs to practice/shadowing, not to lexical entries.
- Audio files should live in app support storage with explicit cleanup policy.
- First version compares duration and pauses; phone-level scoring is future work.

## Repository Boundaries

Recommended Rust application repository traits:

| Trait | Responsibility |
|---|---|
| `PracticeRepository` | sessions, items, attempts, generated observation/review links |
| `ReviewRepository` | review items, schedules, attempts |
| `LearningEventRepository` | append/read learning events and aggregates |
| `CorpusIndexRepository` | query/rebuild derived corpus index |
| `DifficultyRepository` | cache/read computed difficulty profiles |
| `LearnerProfileRepository` | learner profile and L1/L2 preferences |
| `RecordingRepository` | recording metadata and cleanup references |

These should be narrow traits owned by `application`, implemented by `persistence-sqlite`.

## Application Services

Recommended application modules:

| Module | Responsibility |
|---|---|
| `application::practice` | build practice items, evaluate attempts, emit observations/events |
| `application::review` | create review items, schedule attempts, Anki export adapter later |
| `application::learning_events` | event ledger writing and aggregate helpers |
| `application::corpus_search` | query personal corpus and produce playable segments |
| `application::difficulty` | compute input fit signals |
| `application::learner_profile` | manage UI language/L1/L2 settings |
| `application::shadowing` | recording metadata and comparison orchestration |

domain and repository shape are ready.

## Flutter Boundaries

Recommended controllers:

| Controller | Responsibility |
|---|---|
| `StudyModeController` | intensive/extensive/review/specialty mode and subtitle fading mode |
| `PracticeController` | current practice item, attempt input, evaluation state |
| `ReviewController` | review queue and review attempt state |
| `CorpusSearchController` | personal corpus queries and playable segment selection |
| `LearningStatsController` | dashboard aggregates and next-action suggestions |
| `ShadowingController` | recording lifecycle, playback comparison and waveform state |
| `LearnerProfileController` | UI language/L1/L2 preferences if not folded into settings |

Controllers should keep typed state and generation guards, following the Phase 2.18 direction.

## First Vertical Slice

The first implementation slice should prove the architecture with minimal surface area:

```text
current cue/chunk
  -> build cloze or chunk dictation PracticeItem
  -> user submits text
  -> evaluate token diff
  -> persist PracticeAttempt
  -> generate LexicalObservation for failed lexical anchors
  -> optionally create ReviewItem
  -> append LearningEvent
  -> show result in UI
```

This slice exercises:

- practice model;
- lexical observation integration;
- review item creation;
- learning event ledger;
- token/timeline anchors;
- typed Flutter practice state.

It intentionally does not require:

- recording;
- Anki export;
- dashboard UI;
- connected-speech marker QA;
- complex recommendation.

## Data Ownership Rules

- `LexicalEntry` owns durable lexical status and user notes.
- `LexicalObservation` owns sentence/context-specific recognition evidence.
- Timeline resources own timing and sound evidence.
- `PracticeAttempt` owns what the user tried and how it was evaluated.
- `ReviewItem` owns scheduling targets, not lexical identity.
- `LearningEvent` owns analytics-friendly historical facts.
- Corpus index and difficulty profiles are derived and rebuildable.
- Recordings are local assets referenced by practice attempts.

## Guardrails

- Do not silently change `LearningStatus` from practice failure.
- Do not make Anki the internal review model.
- Do not store practice-only data in `LexicalEntry`.
- Do not make corpus index authoritative for vocabulary history.
- Do not hard-code Mandarin explanations in Flutter widgets.
- Do not use raw CTC labels as teaching labels.
- Do not build dashboard metrics from transient UI state.
