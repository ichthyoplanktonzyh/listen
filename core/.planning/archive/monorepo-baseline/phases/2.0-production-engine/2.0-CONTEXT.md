## 2. 核心决策

### 决策 1：生产端与消费端分离（2026-06-18 14:50）

**背景**：Milestone 1 完成后，原计划是"做移动端或普通 ASR 增强"。经过讨论，意识到主线应该是"先把时间轴资源做准，再让消费端稳定消费"。

**决定**：
- 本地重装生产引擎（Python + GPU + Whisper Large-v3/WhisperX/MFA）负责生成精准时间轴
- 轻量消费端（Rust + Flutter）不内置重型模型，只读取 `.lltimeline.json`
- 两者通过 LLTimeline JSON v1 契约解耦

**影响**：
- 生产端可以使用任何本地可控技术（Python、GPU、大型模型），不约束于消费端的 Rust/Flutter 栈
- 消费端保持轻量，不引入 PyTorch/WhisperX 运行时
- 移动端计划延后到生产资源闭环稳定后

### 决策 2：LLTimeline JSON v1 作为交换契约

**背景**：需要一个版本化、可验证的数据格式，兼容 OpenAI/WhisperX 的 segment/word 骨架，同时扩展 LLPlayerNext 所需元数据。

**决定**：
- Schema: `llplayer.timeline.v1`
- 包含：metadata / segments / word_timelines / phone_timelines / chunk_timelines / artifacts
- 兼容策略：不兼容字段变化必须提升 schema 版本
- word type 支持：word / silence / breath / noise / music / speaker_change

### 决策 3：WhisperX 作为首个生产对齐路径

**背景**：需要选择第一个可用的生产级强制对齐方案。

**决定**：
- WhisperX 作为首个实用候选（Python、GPU、支持 word-level alignment）
- torchaudio MMS_FA 作为研究模式的替代/增强选项
- MFA/BFA 作为英语新闻类参考候选（后续评估）
- 对齐失败不得破坏已有 transcript

### 决策 4：多候选 Timeline + 人工选择

**背景**：不同的对齐方法产生不同的时间边界，没有单一"正确"答案。

**决定**：
- 系统保存多个候选 WordTimeline（DTW / WhisperX / MFA / pause-refined / user-adjusted）
- 人工校对后选择 active timeline
- 每个候选具有 provider/version/config_hash 可追溯性
- 人工修正优先级高于算法候选

### 决策 5：强制对齐研究模式

**背景**：MMS_FA 的准确性在新闻类材料上未经充分验证。

**决定**：
- `align-cli.py` 作为研究工具，通过 Rust transcription coordinator 调用
- 仅当 forced-align venv 存在时才尝试
- 失败时安全回退到 Whisper DTW 时间戳
- 不阻塞正常 ASR 流程

## 4. 当前阶段与后续

### 已完成（M2.0 Phase 1-2）
- LLTimeline JSON v1 核心契约 + 导入导出 round-trip
- 版本化 WordTimeline 资源生命周期管理

### 进行中（Phase 3）
- WhisperX 生产管线 V1（`produce-whisperx` 端到端命令）

- 人工校对 UI
- 消费端 `.lltimeline.json` 导入与播放

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| WhisperX 在快速新闻语音上对齐精度不足 | 保留 MFA/BFA 作为后续增强候选，建立 gold benchmark 量化评估 |
| Python 管线运维复杂 | 统一 CLI entrypoint，封装 venv 管理为 Rust ProductionToolManager |
| 人工校对工作量过大 | 优先优化新闻类（固定格式），自动化 chunk 划分减少人工 |
| 消费端导入后的词级高亮体验 | 消费端已有 `estimate_word_timings()` 降级能力 |
