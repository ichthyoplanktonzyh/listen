# Phase 2.3.5 Plan: Rust Module Decomposition

更新时间：2026-06-20 23:25 CST

## Objective

解决 Milestone 2 当前最明显的 Rust 架构债：将 `persistence-sqlite`、
`application` 和 `api-http` 的巨型 `lib.rs` 拆成可导航、可测试、可继续扩展的模块，
为 Phase 2.4 ChunkTimeline 和 Phase 2.5 PhoneTimeline 降低实现风险。

## Design Principle

Phase 2.3.5 只做 **mechanical decomposition**：

```text
move code
  -> preserve public surface
  -> run tests
  -> repeat
```

关键原则：

- **行为不变**：不改业务逻辑，不改 API，不改 schema。
- **小步验证**：每搬一个 repository / use case / route group 就跑测试。
- **对外透明**：`lib.rs` 负责 `mod` 和 `pub use`，减少外部 crate import 变更。
- **独立域优先**：先搬低耦合模块，最后处理 vocabulary↔lexical、chunk↔phrase 等
  已知耦合。
- **产品阶段隔离**：不把 ChunkTimeline 或 PhoneTimeline 新功能混入本阶段。

## Work Breakdown

### Step 1: Baseline And Guardrails

- 记录当前大文件行数。
- 跑完整基线测试：
  - `cargo test -p persistence-sqlite`
  - `cargo test -p application`
  - `cargo test -p api-http`
- 确认当前未提交产品改动不会混入本阶段提交。

Exit criteria:

- 明确拆分前基线。
- 若已有测试失败，先记录为已知状态，不在拆分中顺手修业务。

### Step 2: Split `persistence-sqlite`

按 repository / 表域拆分 `crates/persistence-sqlite/src/lib.rs`。

建议模块：

- `connection.rs`：`SqliteRepository`、open、backup、transaction 基础能力。
- `migrations.rs`：migration runner 和历史 DB 升级测试。
- `json.rs`：JSON 序列化 helper。
- `media.rs`
- `subtitles.rs`
- `transcription.rs`
- `word_timelines.rs`
- `lltimeline_resources.rs`
- `vocabulary.rs`
- `lexical.rs`
- `dictionary.rs`
- `pronunciation.rs`
- `phonetic_analysis.rs`
- `learning_resources.rs`
- `backup.rs`

Exit criteria:

- 每个 repository impl 进入对应模块。
- `lib.rs` 保留 module declarations / re-export / 必要 shared glue。
- `cargo test -p persistence-sqlite` 通过。

### Step 3: Split `application` First Layer

先搬不依赖具体业务顺序的公共层。

建议模块：

- `error.rs`：`ApplicationError`。
- `repositories.rs`：Repository traits。
- `providers.rs`：Dictionary / transcription / phonetic provider traits。
- `dto.rs`：输入输出 DTO。
- `util.rs`：`now_ms`、`require_text`、`clean_*`、`normalize_phrase` 等 helper。
- `pipelines.rs`：已有 pipeline struct / orchestration helpers。

Exit criteria:

- `application/src/lib.rs` 通过 `pub use` 保持对外兼容。
- `cargo test -p application` 通过。
- 下游 crate import 尽量无需修改；必须修改时只做机械路径调整。

### Step 4: Split `application` Use Cases

按独立域优先顺序拆 `impl AppServices`。

建议顺序：

1. `media.rs`
2. `progress.rs`
3. `dictionary.rs`
4. `pronunciation.rs`
5. `word_timelines.rs`
6. `timeline_resources.rs`
7. `subtitles.rs`
8. `transcription.rs`
9. `phonetic_analysis.rs`
10. `lexical.rs`
11. `vocabulary.rs`
12. `chunk.rs`

已知耦合处理：

- vocabulary ↔ lexical：跨域编排方法可暂留 `lib.rs`，或归入主域并显式引用另一域。
- chunk → phrase_candidates：先保留清晰依赖，不在本阶段改算法。

Exit criteria:

- `application/src/lib.rs` 不再是主要 use case 承载文件。
- `cargo test -p application` 通过。

### Step 5: Continue Splitting `api-http`

`api-http` 已经拆出部分模块，本阶段继续按 route group 搬 handler。

建议模块：

- `routes/media.rs`
- `routes/subtitles.rs`
- `routes/lltimeline.rs`
- `routes/timeline_resources.rs`
- `routes/vocabulary.rs`
- `routes/dictionary.rs`
- `routes/pronunciation.rs`
- `routes/phonetic_analysis.rs`
- `routes/transcription.rs`
- `routes/learning_resources.rs`
- `routes/settings.rs`

`lib.rs` 保留：

- router assembly。
- `ApiState`。
- auth / error response glue。
- module re-export。

Exit criteria:

- route handlers 不再集中在 `api-http/src/lib.rs`。
- `cargo test -p api-http` 通过。

### Step 6: Documentation And Closeout

- 更新 `.planning/codebase/CONCERNS.md` 巨型单文件状态。
- 更新 `.planning/codebase/STRUCTURE.md` / `ARCHITECTURE.md` 如有必要。
- 更新 `STATE.md`，标记 Phase 2.3.5 收口。
- 记录未处理项：
  - `speech-analysis` crate 拆分。
  - `domain/src/lib.rs` 进一步拆分。
  - forced-align monotonicity 消融。

Exit criteria:

- 文档反映新的模块结构。
- Phase 2.4 可以基于新模块结构开始。

## Testing

每个 step 至少运行：

```sh
cargo test -p persistence-sqlite
cargo test -p application
cargo test -p api-http
```

最终收口建议运行：

```sh
cargo test --workspace
$HOME/.local/share/flutter/bin/flutter analyze
$HOME/.local/share/flutter/bin/flutter test
```

如果 Flutter 测试与 Rust 拆分无关但失败，需记录失败原因，不在本阶段混入 UI 修复。

## Commit Strategy

建议拆成多笔机械提交：

1. `Split persistence sqlite modules`
2. `Split application shared contracts`
3. `Split application use case modules`
4. `Split api http route modules`
5. `Update architecture docs for module decomposition`

每笔提交只包含一个层级，方便回滚。

## Open Questions

- `SqliteRepository` 结构体和 migration runner 是否继续放在 `lib.rs`，还是移到
  `connection.rs` 后由 `lib.rs` re-export？
- `ApplicationError` 是否应保持 `application::ApplicationError` 路径稳定？
- vocabulary↔lexical 的跨域编排方法最终归属哪个模块？
- api-http route modules 是否使用 `routes/mod.rs`，还是直接顶层模块？
- 是否要在本阶段顺手加入 `cargo clippy`，还是保持测试范围克制？
