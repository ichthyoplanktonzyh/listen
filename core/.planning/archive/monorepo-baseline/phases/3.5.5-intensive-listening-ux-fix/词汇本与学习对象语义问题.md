# 词汇本与学习对象语义问题

> Phase 3.5.5 子项，来源于 2026-07-09 UX 讨论
> 日期：2026-07-09

---

## 问题 1：词汇本界面仍为旧设计

### 1.1 未融入 Phase 3.35 工作台设计语言

`VocabularyScreen` 是独立的全屏页面（通过 `Navigator.push` 跳转），使用独立的 `Scaffold` + `AppBar`，没有融入 Phase 3.35 工作台的 `ListenTheme` 和统一布局体系（参见 [3.35-PLAN.md](../../3.35-listening-workbench-ui-redesign/3.35-PLAN.md)）。

### 1.2 过滤方式仍为旧 LearningStatus 三态

```dart
static const statuses = [
  'unknown_meaning',
  'known_not_recognized',
  'known_recognized',
];
```

用户只能按旧的单值线性状态筛选词汇，无法按四通道能力维度（如"只看 listening `not_acquired` 的词"）筛选。

### 1.3 列表项不展示能力信息

`VocabularyBookView` 只显示 `display_form` 和首条来源句子快照，不展示任何 reading / listening / speaking / writing 四通道状态摘要。

### 1.4 详情弹窗使用 AlertDialog

词汇详情以 `AlertDialog` 弹出，而非融入工作台右侧面板或独立页面的布局，限制了信息展示空间（当前固定 700×650）。

| 明细 | 当前状态 |
|------|---------|
| 列表页视觉风格 | 独立 Scaffold，未用 ListenTheme |
| 过滤维度 | 旧三态 (unknown_meaning / known_not_recognized / known_recognized) |
| 列表项信息 | 仅 display_form + 来源快照 |
| 详情展示 | AlertDialog 弹窗 |

## 问题 2：四通道能力模型在词汇列表层未落地

Phase 3.4.1 已将 `LexicalEntry` 的 capability 模型从单值 `LearningStatus` 升级为四通道（reading / listening / speaking / writing）`LexicalCapabilityProfile`，并实现了 evidence / projection / override 分层（参见 [3.4.1-PLAN.md](../../3.4.1-learning-capability-model-v2/3.4.1-PLAN.md)、[3.4.X-SHARED-CONTEXT.md](../../3.0-english-listening-learning-loop/3.4.X-LEARNING-DOMAIN-V2-SHARED-CONTEXT.md)）。但词汇列表层未同步迁移：

### 2.1 列表 API 不支持能力维度查询

```dart
// api_service.dart — listVocabulary 仍只接受旧 status
Future<List<Map<String, dynamic>>> listVocabulary(
  String status,  // 旧单值 status
  {String? language, String? search}
) async { ... }
```

没有按 capability 维度（如 `listening: not_acquired`）过滤的端点。

### 2.2 列表页状态筛选 Chip 未更新

`VocabularyScreen` 顶部的三个 `ChoiceChip` 仍绑定旧 statuses 列表，没有 capability 维度选择器。

### 2.3 列表项不展示 capability 摘要

`VocabularyBookView` 的 `ListTile` 不显示四通道能力状态，用户无法在列表中快速了解一个词的 capability 全貌。

### 2.4 已迁移 vs 未迁移组件对比

| 组件 | 文件 | 迁移状态 |
|------|------|---------|
| 词汇详情弹窗 (WordLearningPanel) | `widgets/panels/word_learning_panel.dart` | ✅ 四通道 grid + override |
| 字幕 token 行 (TokenLine) | `widgets/subtitle/token_line.dart` | ✅ 读取 capabilityProfiles |
| 学习控制器 | `controllers/learning_controller.dart` | ✅ profile store |
| 复习结束页 | `screens/review_queue_screen.dart` | ✅ listening 文案 |
| **词汇列表页** | **`screens/vocabulary_screen.dart`** | **❌ 未迁移** |
| **词汇列表视图** | **`widgets/vocabulary/vocabulary_book_view.dart`** | **❌ 未迁移** |
| **列表 API** | **`services/api_service.dart`** | **❌ 未迁移** |

## 问题 3：学习对象语义散

Phase 3.4.x 系列在概念层面确立了"学习对象 / 能力画像 / 观测证据 / 素材标注"四层框架（详见 [词汇状态与意群建模复核](../../../discuss/vocabulary-status-and-sense-group-modeling-review.zh.md) §十），但在实现层面学习对象的语义是散的——不同对象在不同阶段以不同模型引入，缺乏统一的抽象层。

### 3.1 各学习对象实现状态

以下对比基于项目讨论文档中的概念定义与当前代码实现。

**Word / Phrase / Collocation 粒度讨论**：原始讨论 [词汇状态与意群建模](../../../discuss/vocabulary-status-and-sense-group-modeling.zh.md) §三/六 提出了 word → collocation → phrase → sentence 的粒度层级和四通道能力模型。复核文档 [词汇状态与意群建模复核](../../../discuss/vocabulary-status-and-sense-group-modeling-review.zh.md) §七 进一步明确了 Collocation 是 multiword expression 的词汇属性（`lexical_class`），不是独立粒度（`granularity`），建议将粒度轴改为 `word | multiword` + 独立的 `lexical_class` 分类。

**Sentence / Construction 讨论**：原始讨论 [词汇状态与意群建模](../../../discuss/vocabulary-status-and-sense-group-modeling.zh.md) §五 提出 Sentence 作为学习对象的两层结构（具体句子 exemplar + 抽象句式 construction）。复核文档 [词汇状态与意群建模复核](../../../discuss/vocabulary-status-and-sense-group-modeling-review.zh.md) §八/九 进一步区分了 `SentenceExemplar`、`Construction`、`ConstructionOccurrence`、`UserSentencePattern` 四个概念，并指出 Construction 的身份归并是比 CRUD 更基础的问题。Phase 3.4.3 的 spike（参见 [3.4.3-PLAN.md](../../3.4.3-construction-modeling-spike/3.4.3-PLAN.md)）验证了这些身份问题，但未进入生产 schema。

**SenseGroup 定位**：复核文档 [词汇状态与意群建模复核](../../../discuss/vocabulary-status-and-sense-group-modeling-review.zh.md) §五/六 明确了 SenseGroup 是句子上下文中的 occurrence（素材标注），默认不是全局学习资产，不应拥有二值能力画像。Phase 3.4.2（参见 [3.4.2-CLOSEOUT.md](../../3.4.2-semantic-prosodic-group-separation/3.4.2-CLOSEOUT.md)）已按此定位落地。

**用户活动路径中的资产层**：产品讨论 [listen 用户学习活动路径](../../../discuss/listen-learning-activity-path.zh.md) 的"资产流转总表"将学习资产定义为"词 / phrase / chunk / 句子 / 语流现象 / 卡点 / 语料锚点"，但当前代码只将 `LexicalEntry`（词 + phrase）实现为有能力画像的持久化资产。

| 学习对象 | 讨论文档定义 | 代码实现 | 持久化 | 状态 |
|---------|------------|---------|--------|------|
| **Word** | 最小词汇单元，R/L/S/W 四通道 | `LexicalEntryKind::Word` | ✅ schema v22 | 生产 |
| **Phrase** | 固定多词单元，R/L/S/W 四通道 | `LexicalEntryKind::Phrase` | ✅ schema v22 | 生产 |
| **Collocation** | 词汇属性（搭配），建议为 `lexical_class`，不是独立粒度 | ❌ 无独立身份，`LexicalEntryKind` 无此枚举值 | ❌ | 未实现 |
| **Sentence（作为学习资产）** | 具体句子，可收藏、回听、练习的素材 | ❌ `SubtitleSentence` 是字幕资源概念，非学习资产概念 | ❌ | 未实现 |
| **Construction** | 规范化抽象构式，recognition/production | ⏸ Phase 3.4.3 spike 完成，未进生产 schema | ❌ | Spike |
| **SentenceExemplar** | 具体句子实例，关联 Construction | ⏸ Phase 3.4.3 spike 完成，未进生产 schema | ❌ | Spike |
| **SenseGroup** | 句内 token span 标注，**非学习资产** | `SenseGroupAnalysis` + `SenseGroup` | ✅ schema v25 | 生产 |

### 3.2 缺少统一的"学习对象"抽象

当前没有统一的 trait、enum 或抽象类表达"一个可以拥有能力画像的学习对象"：

- `LexicalEntry` 有自己的 `LexicalCapabilityProfile`
- Sentence 没有 capability profile（它甚至不是学习资产）
- Construction 有自己独立的 `ConstructionCapability`（recognition/production），与 `LexicalCapabilityProfile` 不同
- Collocation 无任何身份，既不能挂 profile 也不能挂证据

不同学习对象的能力模型不统一。精化评审（[learning-domain-model-v2-refinement-review](../../../discuss/learning-domain-model-v2-refinement-review.zh.md) §四）已指出"四个能力通道就硬编码四个，不做可插拔 capability registry"是审慎的，但不同对象类型有不同的能力维度（LexicalEntry 四通道 vs Construction 两通道），这一差异尚未被统一处理。

| 对象 | 能力维度 | 维度值 |
|------|---------|-------|
| LexicalEntry | reading / listening / speaking / writing | unassessed / not_acquired / acquired |
| Construction（概念） | recognition / production | 未定 |
| Sentence（概念） | 无 | — |
| Collocation（概念） | 无 | — |

### 3.3 学习对象关系未建模

概念上存在的对象间关系在代码中不存在或只有隐式关联：

- **LexicalEntry ↔ Sentence** — `LexicalOccurrence` 通过 `sentence_id` 引用 `SubtitleSentence`，但 Sentence 本身不是持久学习资产
- **LexicalEntry ↔ Collocation** — 无模型表达"heavy rain 是由 heavy 和 rain 组成的搭配"
- **Construction ↔ SentenceExemplar** — Phase 3.4.3 spike 有原型但未进生产
- **Sentence ↔ SenseGroup** — `SenseGroup.sentence_id` 引用正确，但 SenseGroup 明确不是学习资产
- **无统一查询路径** — 无法用一个接口查询"我的所有学习对象"（词 + phrase + sentence + construction）

### 3.4 词汇本列表的查询范围不完整

当前 `listVocabulary` API 只查询 `LexicalEntry`，不包括：
- 用户收藏的句子（不存在 Sentence 学习资产）
- 构式学习对象（不存在生产 schema）
- Collocation 标记对象（不存在独立身份）

用户无法在一个统一的"词汇本"视图中看到自己的全部学习对象。

## 问题关系总结

```
问题 1（词汇本 UI 旧）
    └── 表层表现：视觉、交互、信息展示过时

问题 2（能力模型未完全落地）
    └── 中间层：API、列表页未同步 3.4.1 模型升级
            └── 根因：3.4.1 只在详情层迁移，列表层遗漏

问题 3（学习对象语义散）
    └── 深层根因：不同 phase 引入的不同对象，
         各有各的身份/能力/持久化策略，
         缺少统一抽象和关系建模
```

三个问题互相关联：即使把词汇本的 UI 和 API 修好、补齐四通道过滤，只要学习对象语义仍然是散的（句子不是资产、collocation 无身份、construction 在 spike），词汇本的信息边界和能力表达就始终是残缺的。
