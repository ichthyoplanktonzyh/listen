# Phase 2.6 后续：派遣层证伪与加固（第三语言 spike）

> 日期：2026-06-23
> 触发：Phase 2.6 收口后的「第三语言证伪 spike」——用一门与既有语言**共享脚本**的远端样本
> （日语，与中文共享 Han）实测 ROADMAP §14.11 退出条件。
> 状态：证伪已实验确认；派遣层已加固使主张成真；en/zh 回归基线不变。

## 1. 被证伪的主张

ROADMAP §14.11 退出条件：

> **新增主流语言主要是 provider + profile 工作，不需改动既有语言代码。**

结论：**数据模型层成立，行为派遣层不成立**。日语精确撞破后者。根因不是抽象错，而是
**zh 是唯一的非英语样本、且与抽象同期共同设计**——n=1 时「脚本捷径」与「真正按语言/能力派发」
行为上无法区分，只有第二门**共享脚本**的语言出现才暴露。2.5.5 的 ja/ar 是纸面证伪，无代码，
抓不到。这正是「对照不能暴露 bug 的样本做了验证」的陷阱。

## 3. 漏的（被迫改既有共享代码）+ 已实施的修法

证伪当时用一次性 reproducer 实跑现有代码确认（跑后即删，未入库）：

```
[LEAK 1]  tokenize(ja, "私は学生です") word tokens = ["私は学生です"]   ← 整句塌成 1 个 token
[LEAK 1b] same text — zh segmenter words=5, ja words=1               ← 派发是封闭 match
[LEAK 2]  undeclared Japanese detected as: "zh"                      ← 未声明日语判成中文
```

| # | 泄漏 | 位置 | 严重度 | 修法 |
|---|---|---|---|---|
| 1 | `tokenize()` 是写死 match，`Tokenizer` trait 装饰性；ja 落 `_` → 空格分词 → 1 token | `subtitle-core/lib.rs` | 高·中心 | 新增 `tokenizer_for(strategy)` 注册表（strategy→tokenizer 单一注册点，profile_for 的 tokenizer 类比）+ 始终可用的 `CharacterTokenizer`（`core.char`）。ja 声明 `core.char` 复用之，**零新分词代码、零派发编辑** |
| 2 | `detect_language` 用脚本判语言，Han 无法区分 zh/ja | `subtitle-core/lib.rs` | 高·中心 | declared-first（已优先）+ kana 存在性 → ja，否则 Han → zh，否则 en。kana 中文绝不出现，是可靠日语信号。保留 provider-swap seam |
| 3 | 逐字拼音按 Han **脚本**门控，非按语言/能力 | `word_learning_panel.dart` | 中 | 改按学习语言门控（`profile['language']=='zh'`，逐字拼音本是 pinyin 发音系统属性，零新 API；`WordProfile.language` 已在面板内）。删 `_isHan` |
| 4 | `normalize_lemma`（英语 lemma）在 tokenizer/词典查询里写死，无视 profile 声明的 `lexical_normalization` | `subtitle-core` + `application/dictionary.rs` | 低·潜在 | 在 **profile-aware 接缝** 路由：`tokenize()` 出口按 `baseline_normalized_key(profile.norm, text)` 重算 word token 归一；词典查询同改。en=lemma 不变；zh/ja=surface 不再被静默小写 |

## 4. 真正危险的不是单点，是**静默误路由**（compounding）

```
未声明日语「私は学生です」
 └─[泄漏2] detect_language → "zh"
   └─[泄漏1] jieba 当中文切
     └─ CC-CEDICT 查 kanji（形同词大量命中，如「学生」就是 CEDICT 词条）
       └─[泄漏3] region==zh 拼音 → 面板把「学生」标 xué-shēng（实为 gaku-sei）
         └─ 套用中文声调诊断
```

不是崩溃，是**自信地把日语当中文、产出看起来正确的错误输出**——比报错更隐蔽。Fix 2 从源头
切断（ja 被正确识别为 ja），Fix 1/3/4 各自独立加固，构成纵深。

## 5. ja profile 的定位

`LanguageLearningProfile::japanese`（`profile_for("ja")`）**仅作证伪守卫 fixture**，不是上线日语：
- `tokenization: core.char`（复用字级 tokenizer，记为「形态分析 provider 落地前的基线」）
- `pronunciation: core.none` / `dictionary_providers: []`（无 kana 读音 / JMdict provider → 干净降级，
  绝不借用中文）
- 声明自身轴：`ja.mora` 听觉单位、`ja.pitch_accent` 等 sound feature、`pitch_accent`/`mora_boundary`
  等诊断理由（验证 §2 诊断派发确实开放）
- 听觉时间轴 Unsupported（非英语音频生产属后续 production-engine program）

## 6. 关于 Fix 4 的范围纪律（刻意不大包大揽）

grep 全部 `normalize_lemma` 用点发现：**持久词汇 identity 在仓储边界形成**（`vocabulary.rs:61`、
`util.rs:40`、`pronunciation.rs:20`、`lexical.rs`、`persistence` 等约 6 处都对入参 lemma 再做
`normalize_lemma`）。因此 tokenizer 的 `normalized` 字段会被下游**重归一**——
对 en/zh/ja 而言 `normalize_lemma`（trim+小写）与 profile-surface **行为等价**（en 要 lemma；zh/ja
无大小写，小写是 no-op）。

故**没有**去重构那 6 个 identity 边界点：那是零行为变化、却动到 identity 模型的 churn，正是要避免的
过度扩张。只在两个 **profile-aware 接缝**（tokenizer 出口、词典查询）路由归一，并把 identity 边界的
英语-lemma 硬编码**记为潜在 seam**（仅当未来加入「带大小写且非 lemma」的语言才会咬人，如土耳其语
点 i），不盲改。

## 7. 残留 / 刻意延后（非缺陷）

- **真日语形态分词**（lindera/vibrato）+ **JMdict** + **kana 读音 provider**：本 spike 不拉重型依赖；
  ja 现为字级基线。届时 ja profile 把 `core.char → ja.morphological` 并注册对应 tokenizer = profile+provider
  改动，不动派发。
- **纯 kanji、无 kana 的日语行**仍会被 `detect_language` 判成 zh（kana 是当前唯一廉价信号）。真实字幕几乎
  必带 kana（助词/送り仮名），故影响小；彻底解决需真正的 language-id provider（seam 已留）。
- **能力矩阵暴露给 client**：Fix 3 现按 `language=='zh'` 门控（逐字拼音本就 zh 专属）；完全一般化需把
  profile 能力 flag 暴露给 client——仍是收口里那个 **Open Question**。
- **identity 边界 profile 化**：见 §6，潜在 seam，延后。
