# Phase 3.9.2 Context: Syntax Provider Qualification Correction and Product Activation

日期：2026-07-13

## 为什么需要纠偏

Phase 3.9.1 已冻结并完成 neutral `SyntacticAnalysis`、Stanza/spaCy sidecar、token mapping、
validator、Reference B、syntax-aware SenseGroup 和 dependency matcher seam。但其资格结论把
`Which team do you want to win?` 标成唯一句法真值：`which team` 必须是 `win` 的 understood
subject，并据此将 provider 的另一分析记为高风险假阳性。

Owner 复核指出，该无上下文表面句存在语义/论元歧义。产品在歧义处选择 block/abstain 是合理
政策，但不能把这个政策标签当成 parser attachment gold。因此 3.9.1 的原始报告保持冻结历史，
3.9.2 以新的 fixture/version 和预登记重新评估；不得回写旧 validation output。

## 当前可复用资产

- provider-neutral artifact、application finalizer 和 domain validator 已完成。
- spaCy/Stanza 已过同一 sidecar contract，mapping、资源、failure taxonomy 已有报告。
- B 已有 qualified syntax context seam；SenseGroup 已有独立 syntax-aware provider/version；
  Construction 已有只产候选、不铸造 canonical identity 的 matcher。
- 无模型、invalid tree、低 coverage 时的 B/rule SenseGroup fallback 已有测试。

因此消费者算法不是本阶段主要工程量。主要风险是：修正资格证据、选择一个产品候选，并在不让
Python/model 成为轻量消费者硬依赖的前提下建立 capability/composition/lifecycle。

## 候选选择

首选 spaCy `en_core_web_sm`：现有测量显示冷/热启动、吞吐、RSS 均显著优于 Stanza，模型
metadata 与许可记录也更完整。Stanza 保留为质量对照；其 transitive charLM/pretrain training
provenance 未补齐前不得随产品分发。

首选不等于预先授予资格。spaCy 仍须通过修正版 locked holdout、真实字幕和部署边界 gate。

## 边界

- parser 负责 lemma/POS/dependency evidence；B 规则仍负责教学预测，不直接展示 parser label。
- 模糊句以 `ambiguous_policy_abstain` 评估产品行为，不计为唯一 attachment gold。
- 一句字幕只生成一份 artifact，B、SenseGroup、Construction candidate matcher 共享消费。
- syntax 永不填充 C，不替代 ChunkTimeline，不铸造 Construction/capability identity。
- provider 缺席、未安装、损坏、超时、invalid tree 或低 coverage 时，现有路径逐项不回归。
- 本阶段默认把 owner 所说的 “collection” 解释为 Construction candidate matcher。
