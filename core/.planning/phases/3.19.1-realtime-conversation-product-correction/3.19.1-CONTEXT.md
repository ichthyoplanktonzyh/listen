## Why This Is A 3.19 Correction Slice

Phase 3.15.7 已冻结为历史事实：它交付了 provider-neutral realtime 协议、OpenAI/Qwen adapter、
本地 loopback WebSocket、音频桥、session/turn schema 与第一个内容锚定 surface。Issue #7 与真实
Qwen provider QA 证明底层连接可用，但上层产品只在整场结束时保存一个 learner turn，因此不能完成
原 Manual QA 中的多轮目标，也不能作为真正的对话功能使用。

本阶段是 Phase 3.19 已保留 Realtime Conversation 后的产品纠偏，不是绕过 LOOP-024 硬门的新功能
扩张。3.15.7 文档保持冻结；新发现、设计和后续实现只进入 3.19.1。

## Problem Statement

当前链路把“一个 socket session”“一段连续麦克风录音”“一个 learner turn”错误地合并成同一
生命周期：

```text
Start
  -> continuous microphone capture + provider conversation
  -> Finish
  -> one local WAV
  -> one Whisper job
  -> learner-1 / sequence=1
  -> one Production Corpus document
```

真实多轮对话需要区分至少四层：

```text
conversation session
  -> ordered provider conversation items
  -> repeated learner/assistant turns
  -> per-learner-turn local audio + local-authoritative transcript
  -> learner-only Production Corpus projection
```

## Confirmed Current Facts

- Rust domain、application repository seam、SQLite schema 已支持 ordered multi-turn session；无需因为
  Flutter bug 重建整套持久化模型。
- provider-neutral event 已包含 `speech_started`、`speech_stopped`、`turn_committed`、provider
  transcript、assistant transcript/audio 与 `response_done`；Flutter 控制器目前忽略其中的 turn
  boundary 事件。
- 修复前 Flutter controller 只维护三个 session-level 字符串，并在 `finish()` 中硬编码
  `learner-1 / sequence=1`；当前已改为 typed ordered turn assembler。
- 修复前 macOS realtime audio bridge 只生成一份 session-level 16 kHz WAV；当前已增加带 pre-roll
  的逐 learner turn artifact，session WAV 仅用于兼容清理。
- `POST /v1/realtime/turns` 已经通过
  `ProductionCorpusUseCases.record_realtime_turn_and_index()`：只要每个 finalized learner turn 被正确
  保存，它们就会分别进入 spoken Production Corpus，现有 Gap Review 会自然读到聚合结果。
- assistant turn 应保存为 conversation fact，但绝不能进入 learner Production Corpus。
- 当前 `main` 已包含 Qwen International / China (Model Studio / 百炼) 两类 endpoint 配置与 workspace
  ID 引导；Issue #7 的该项已部分修复，后续只需回归测试和错误引导审计。

## Product Decision To Carry Forward

Realtime Conversation 的保留目标从“Speaking 内的单轮内容练习”纠正为真正的连续对话：

- **自由对话**：从稳定主入口开始，不要求媒体或内容选区；
- **话题锚定**：以用户明确选择的完整句段/话题作为可见 context，不把当前播放位置或整篇内容
  静默发送给 provider；
- 两种 surface 复用 session/turn/audio/transcript/corpus 深模块，但不要求共享所有导航布局；
- provider caption 只服务即时体验；本地 Whisper 成功的 learner transcript 才是个人产出权威；
- conversation history 保存 learner 与 assistant 的完整有序事实；Production Corpus 只投影 finalized
  learner turns；
- Gap Review 保持只读，不新增 capability、observation、proposal、review 或 rubric writer。
- 旧 Role Reply 以字幕下一句作为预设应答，并不构成真实角色对话；3.19.1 将其创建面、领域类型和
  全部既有数据删除，不保留兼容。Retelling、Shadowing、Personal Expression 继续保持各自任务语义。

## Research Questions

1. 成熟 realtime voice 项目如何把 provider 增量事件组装成稳定的多轮 transcript？
2. user speech boundary、assistant response boundary、barge-in 与 session close 如何分层？
3. 哪些 history 可以直接用于 UI，哪些必须在本地重新建立权威？
4. Flutter ChatGPT-like surface 最小需要哪些状态与交互？
5. 哪些外部实现可借鉴模式，但不应成为新的重依赖？

答案见 `3.19.1-RESEARCH.md`。

## Guardrails

- 不修改已冻结的 Phase 3.15.7 文件。
- 不把 provider transcript 提升为 learner-output authority。
- 不把 assistant 文本索引进个人 Production Corpus。
- 不引入 LiveKit/Pipecat 等服务端框架作为产品依赖；调研只提取已验证的状态边界与测试模式。
- 调研阶段不落实现代码；当前实现是在 ADR 0027 与 domain glossary gate 完成后单独启动。
- 不新增 rubric/self-assessment/capability writer；它们不是 Issue #7 的当前验收范围。
