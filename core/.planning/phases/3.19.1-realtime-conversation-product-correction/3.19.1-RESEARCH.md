# Phase 3.19.1 Research: Multi-turn Realtime Voice Conversation

状态：COMPLETE — DESIGN INPUT

日期：2026-07-22

证据类型：`public_source_review` + `codebase_audit` + Issue #7 `manual_product_qa`

## Executive Finding

GitHub 上的成熟方案在一个关键点上高度一致：**session、user turn、assistant turn、增量 transcript
和持久 history 是不同对象**。当前 LLPlayerNext 的 domain/schema 已经接近这一形状，问题主要在
Flutter controller 与 audio bridge 把整场 session 压成了一轮。

推荐保留现有 Rust provider-neutral 深模块和 SQLite facts，新增一个本地 turn assembler：它以本地
单调 sequence 为 identity，以 provider item id 只做 correlation，逐轮维护 streaming/final/
interrupted 状态，并把 learner 音频送入本地 Whisper。UI 从 ordered conversation items 投影消息
时间线；session 结束只关闭 transport，不能再承担“把整场录音制造成一轮”的职责。

不建议把 LiveKit、Pipecat 或 OpenAI Agents SDK 引入产品。它们证明了状态机模式，但会带来 WebRTC、
服务端 Python/Node 或 provider-specific SDK，违背轻量 Flutter + Rust sidecar 的现有边界。

## Reference 1 — OpenAI Realtime Agents

Relevant source:

- [`useHandleSessionHistory.ts`](https://github.com/openai/openai-realtime-agents/blob/94c9e9116b581052655cff7b756cc5e02771cda1/src/app/hooks/useHandleSessionHistory.ts#L88-L158)
- [`useRealtimeSession.ts`](https://github.com/openai/openai-realtime-agents/blob/94c9e9116b581052655cff7b756cc5e02771cda1/src/app/hooks/useRealtimeSession.ts#L85-L111)
- [`TranscriptContext.tsx`](https://github.com/openai/openai-realtime-agents/blob/94c9e9116b581052655cff7b756cc5e02771cda1/src/app/contexts/TranscriptContext.tsx)

### Observed Pattern

- `history_added` creates one transcript item keyed by `itemId` and role;
- `history_updated` replaces the current item content instead of overwriting a session-level string;
- transcript delta/completed events update the same item by `item_id` and mark it `DONE`;
- provider history, tool breadcrumbs and UI transcript are separate projections;
- PTT start clears the input buffer; PTT stop commits the buffer and requests a response.

### Adopt

- transcript state must be an ordered list keyed by stable item identity;
- delta and final events update a single item idempotently;
- live UI status (`IN_PROGRESS/DONE`) belongs to an item, not the whole session;
- manual and server-VAD turn modes can share the same downstream item assembler.

### Do Not Copy

- the example keeps transcript history in React memory and does not provide LLPlayerNext-style durable local facts;
- provider input transcription is displayed as the user message, while LLPlayerNext requires a distinct local Whisper
  authority before learner output enters Production Corpus;
- OpenAI SDK item IDs cannot become cross-provider domain identity.

## Reference 2 — LiveKit Agents

Relevant source:

- [`voice/events.py`](https://github.com/livekit/agents/blob/21a43ececae8b478110fb08ccafc1fbe17b6cade/livekit-agents/livekit/agents/voice/events.py#L315-L336)
- [`voice/events.py` conversation item](https://github.com/livekit/agents/blob/21a43ececae8b478110fb08ccafc1fbe17b6cade/livekit-agents/livekit/agents/voice/events.py#L410-L413)
- [`llm/chat_context.py`](https://github.com/livekit/agents/blob/21a43ececae8b478110fb08ccafc1fbe17b6cade/livekit-agents/livekit/agents/llm/chat_context.py#L286-L294)
- [`llm/chat_context.py` serialization](https://github.com/livekit/agents/blob/21a43ececae8b478110fb08ccafc1fbe17b6cade/livekit-agents/livekit/agents/llm/chat_context.py#L600-L627)

### Observed Pattern

- `UserStateChangedEvent` expresses speaking/listening independently from message creation;
- `UserInputTranscribedEvent` carries `is_final` and an optional provider item id;
- `ConversationItemAddedEvent` emits a typed chat item separately;
- `ChatMessage` has its own id, role and `interrupted` flag;
- `ChatContext` orders insertions by creation time and can serialize without audio payloads;
- session close exposes a bounded wait for the final STT transcript rather than assuming all text is already final.

### Adopt

- distinguish audio activity, transcript finalization and durable conversation item creation;
- represent interruption on the affected turn/item;
- keep ordered textual history serializable without embedding raw audio;
- session finish needs a bounded drain phase for the last provider response/transcript.

### Do Not Copy

- LiveKit's room/WebRTC/server job architecture is far broader than LLPlayerNext's localhost sidecar requirement;
- its provider/server transcript can be the chat context, but it cannot replace the app's local learner-output
  authority;
- cloud recording and telemetry are not prerequisites for this correction.

## Reference 3 — Pipecat

Relevant source:

- [`turn_tracking_observer.py`](https://github.com/pipecat-ai/pipecat/blob/08e871599904080cedad7ce5683676ab8481fa59/src/pipecat/observers/turn_tracking_observer.py#L29-L193)
- [`user_turn_processor.py`](https://github.com/pipecat-ai/pipecat/blob/08e871599904080cedad7ce5683676ab8481fa59/src/pipecat/turns/user_turn_processor.py#L27-L61)
- [`persistent-context-openai-realtime.py`](https://github.com/pipecat-ai/pipecat/blob/08e871599904080cedad7ce5683676ab8481fa59/examples/persistent-context/persistent-context-openai-realtime.py#L34-L105)

### Observed Pattern

- user turn start/stop detection is a strategy boundary, not hard-coded into conversation storage;
- whole conversational turn tracking observes both user and bot speaking frames;
- interruption ends the current turn and starts a new one;
- delayed bot speech uses a short end timeout instead of prematurely closing a turn;
- frame IDs are deduplicated before changing state;
- pipeline end/cancel flushes an active turn explicitly;
- persistent context serializes the ordered message list and reloads it independently from live transport state.

### Adopt

- introduce a small explicit turn assembler with transition tests;
- make repeated/out-of-order provider events idempotent;
- treat barge-in, provider timeout and user cancel as distinct terminal outcomes;
- separate “user utterance ended” from “user+assistant exchange fully drained”;
- persist history from typed items, never by concatenating UI strings at Finish.

### Do Not Copy

- Pipecat's Python processor pipeline and provider ecosystem are not suitable consumer-app dependencies;
- its generic LLM context includes assistant/tool messages that must not be projected into LLPlayerNext's learner
  Production Corpus;
- JSON message persistence is an example, not a replacement for the existing SQLite identities and invariants.

## Reference 4 — LiveKit Flutter Starter

Relevant source:

- [`agent_screen.dart`](https://github.com/livekit-examples/agent-starter-flutter/blob/c0f38a6501c114772d24f1005a5bbbe2d867e6ad/lib/screens/agent_screen.dart#L151-L228)

### Observed Pattern

- a conversation screen consumes `session.messages` as an ordered list;
- user and agent messages are rendered as different bubbles;
- an empty listening state and connected/disconnected controls remain visible;
- text and voice can share one timeline.

### Adopt

- ChatGPT-like message timeline is a better primary surface than three accumulating transcript text blocks;
- keep connection/listening/thinking/speaking/post-processing state visible without replacing the history;
- free conversation may support typed input later without changing the turn/history model.

### Do Not Copy

- the starter delegates state, identity and transcript semantics to LiveKit `Session`;
- it has no local-authority badge, per-turn transcription processing state, source context contract or durable corpus
  handoff;
- visual layout is reference material, not a design to reproduce.

## Current LLPlayerNext Gap Matrix

| Concern | Existing Capability | Missing / Incorrect |
|---|---|---|
| Provider transport | OpenAI/Qwen adapters, localhost WS | none proven by Issue #7 |
| Session facts | durable provider-neutral session | UI conflates session finish with one turn finalization |
| Turn facts | durable ordered learner/assistant type | controller saves only `learner-1` |
| Event vocabulary | speech start/stop, commit, transcript, response done | Flutter ignores turn boundary/correlation events |
| Local audio | continuous 16 kHz session WAV | no per-learner-turn artifact |
| Transcript UI | three session-level strings | no ordered item timeline; earlier rounds overwritten |
| Local authority | local Whisper job exists | only one whole-session job; partial per-turn outcome impossible |
| Conversation history | schema can store turns | assistant turns and earlier learner turns never written |
| Production Corpus | per-authoritative-turn projection already implemented | only one turn reaches it because controller drops the rest |
| Gap Review | spoken read model already aggregates corpus | insufficient data is upstream loss, not a missing gap pipeline |
| Product entry | anchored inside Speaking Task | no stable free-conversation entry |
| Qwen region | intl/CN endpoint + workspace UI exists on `main` | needs regression coverage and actionable validation |

## Recommended Target Model

```text
ConversationSurface (free | topic_anchored)
  -> RealtimeSessionLifecycle
       connecting -> live -> draining -> post_processing -> done/partial/failed/interrupted
  -> TurnAssembler
       local sequence + provider correlation ids
       learner: streaming -> audio_closed -> local_asr -> finalized/failed/interrupted
       assistant: streaming -> finalized/interrupted
  -> ConversationTimeline
       ordered role items + live/final/error provenance
  -> Durable conversation facts
       session + learner turns + assistant turns
  -> learner-only projection
       finalized local learner transcript -> Production Corpus -> existing Gap Review
```

`done/partial` above is a product need, not yet an approved schema change. The design slice must decide whether to add
an explicit post-processing status or derive it from per-turn terminal states. It must not mark an otherwise valid
multi-turn session wholly failed because one learner turn's local ASR failed.

## Audio Boundary Spike Required Before Implementation

External projects prove the state separation but do not answer LLPlayerNext's local-authority audio requirement. The
current native bridge records one continuous 16 kHz WAV while sending 24 kHz PCM to the provider. Before choosing an
implementation, compare these bounded options with real three-turn audio:

1. native per-turn files controlled by provider speech events;
2. a local PCM ring buffer with pre-roll/post-roll sliced by provider events;
3. local VAD-derived boundaries correlated with provider item ids.

Selection criteria: no clipped first phoneme, no assistant playback leakage, deterministic sequence, barge-in safety,
bounded memory, cancel cleanup, and Whisper transcript quality. Provider event arrival time alone must not be assumed
sample-accurate without measurement.

## Design Decisions Still Required

1. durable representation of `free` vs `topic_anchored` surface kind;
2. local turn identity and mapping of zero/one/many provider item ids;
3. per-turn audio boundary strategy after the spike;
4. session terminal semantics when some learner turns fail local ASR;
5. whether local ASR runs after each turn or in a bounded queue during/after the session;
6. stable free-conversation entry and history revisit location;
7. topic selection size/copy under LOOP-022;
8. retention/delete semantics for conversation audio and transcripts.

Items 1, 2, 4 and 8 may require a new ADR because they change durable lifecycle semantics. No ADR is created by this
research document alone.

## Research Conclusion

The correct correction is not “make `finish()` loop over some strings.” It is to make turn assembly a first-class
client/application boundary while preserving the already-correct provider-neutral Rust facts. The smallest coherent
vertical slice is:

1. typed ordered timeline and turn assembler;
2. measured per-turn local audio capture;
3. save both roles, locally transcribe every eligible learner turn;
4. project only finalized learner turns through the existing Production Corpus use case;
5. expose free and explicit topic-anchored entry modes;
6. verify three-turn, barge-in, partial-ASR, cancel, Qwen CN/intl and rebuild behavior.
