## Route Correction: 2026-06-30

Phase 2.20 的路线复盘结论：

- `RhythmFrame` resource/UI/QA direction is correct.
- The current generator source is not sufficient for the product promise of
  actual audible structure.
- Text-predicted anchors are useful priors, but they are not observed
  prominence.
- CTC phone evidence should remain as segmental detail for flapping, deletion,
  weak forms and phone mismatch; it should not be the main rhythm skeleton.
- The generator path should migrate to D -> F:

```text
forced-aligned WordTimeline skeleton
  + duration/rate evidence
  + RMS energy/loudness evidence
  + optional F0/pitch evidence after calibration
  + text priors with explicit provenance
```

See `2.20-ROUTE-CORRECTION.md` for the handoff decision.

## Non-Goals

- 不在本 phase 承诺替换 CTC phone model。
- 不把 phone-level PER 修到发布级作为本 phase 的退出条件。
- 不做完整 intonation model。
- 不要求 consumer app 运行 pitch/F0/RMS extraction；重声学特征应在 production pipeline
  预计算进 `.lltimeline.json`。
- 不做复杂发音打分或用户录音评分。

## Step 0: Product Semantics Lock

Deliverable:

- Define learner-facing labels and internal data terms.
- Decide which concepts are default UI and which are expandable details.

Default UI concepts:

| Concept | User-facing meaning |
|---|---|
| stress anchor | this is a sound/meaning anchor to catch |
| weak group | these words are backgrounded or compressed |
| compressed span | this part is fast/packed and easy to miss |
| phrase boundary | the sentence naturally breaks here |
| hotspot | this is why the written form does not match what you hear |

Internal-only or advanced concepts:

| Concept | Reason |
|---|---|
| CTC insertion/deletion/substitution | too model-specific for default UI |
| raw phone label | can be wrong; use only as evidence |
| PER | evaluation metric, not product language |

Acceptance:

- Phase docs clearly state rhythm-first priority.
- Phone-level output is recorded as long-term evidence work, not the main product surface.

## Step 1: RhythmFrame Algorithm v0

Build a deterministic baseline from existing data:

Inputs:

- transcript words and timings
- expected pronunciation / syllables / lexical stress where available
- pause/gap between words and learning phones
- duration per word/syllable/phone
- connected-speech markers from Phase 2.16
- CTC phone confidence/evidence coverage when available

Outputs:

- stress anchors
- weak groups
- compression spans
- phrase boundaries
- listening hotspots
- per-item confidence and evidence type

Baseline rules:

1. Content words and primary-stress syllables become initial anchor candidates.
2. Function words attach to neighboring anchors unless pause/timing evidence separates them.
3. Long gaps create phrase boundaries.
4. Short duration + many expected syllables/phones creates compression spans.
5. Connected-speech markers inside weak/compressed spans become hotspots.
6. Phone-level mismatch can strengthen a hotspot but cannot alone create a high-confidence
   learner-facing explanation.

Implementation target:

- `crates/speech-analysis` algorithm module, likely near `sound_analysis`.
- Keep structs mapped through `domain`/`application` rather than leaking speech-analysis structs
  directly into API or Flutter.

Acceptance:

- Pure unit tests cover deterministic fixtures.
- Existing sound-analysis generation can include rhythm frame without breaking older fields.
- Algorithm changes after the v0 baseline should cite a documented feature family from
  `2.20-ALGORITHM-METRICS-RESEARCH.md` rather than only optimizing current smoke scores.

## Step 2: UI Surface

Goal:

Make the UI answer “how should I actually hear this sentence?” before showing phones.

Suggested first screen:

```text
Sentence
Expected pronunciation reference
Rhythm frame
  [anchor] weak weak [anchor] compressed [anchor]
Hotspot chips / markers
Expandable phone evidence
```

UI rules:

- Stress anchors should be visually primary.
- Weak groups should be visually secondary and grouped, not hidden.
- Compression spans should be visible as a listening-risk area.
- Phrase boundaries should be readable at a glance.
- Phone detail should be behind expansion/hover/advanced panel.
- Do not expose raw CTC labels as default teaching labels.

Implementation target:

- Flutter model parsing for `rhythm_frame`.
- New or refactored widget beside/above the existing sound-pattern ribbon.
- Keep existing phoneme ribbon as an expandable evidence surface.

Acceptance:

- Current sentence can show expected pronunciation and rhythm frame together.
  **Subtitle-layer expected pronunciation reference landed in rhythm mode.**
- Missing `rhythm_frame` degrades to current sound-line/phone UI with a clear unavailable state.
- Widget tests cover grouping, empty state, confidence state and hotspot rendering.
- Subtitle-layer rhythm cue chips now request source-loop playback for the selected timing span,
  with widget coverage for the loop callback path.
- The subtitle-layer sound pattern surface now has an inline icon toggle for switching
  rhythm-first listening cues and phone evidence without opening settings.

|---|---|---|---|
| Transcript/timing | TED-LIUM, product media | STM / manual transcript | text exact, word/segment timing |
| Phone evidence | TIMIT, Buckeye | `.PHN` / `.phones` | PER, coverage, boundary offset |
| Public weak prosody regression | Helsinki Prosody / LibriTTS labels | automatic prominence/boundary labels | anchor precision/recall, boundary F1 trend |

| Weak/compressed spans | Buckeye, TED-LIUM, product media | manual QA sheet | span precision, compression overlap, explanation usefulness |

## Step 4: Benchmark And QA Material Expansion

Use each dataset for the thing it can honestly answer:

| Dataset | Use |
|---|---|
| TIMIT | evidence-layer phone/timing sanity only; not the primary rhythm benchmark |
| Helsinki Prosody / LibriTTS | public large-scale weak-label regression for prominence/stress anchors and prosodic boundaries |
| BU Radio Speech / Boston University Radio News | optional licensed human prosody gold for pitch accents and phrase boundaries |
| Rhythm and Pitch Corpus (RaP) | optional licensed rhythm/pitch sanity set with TextGrid-style annotations |
| Aix-MARSEC / ProPOSEC | optional British English prosody/tonic-stress comparison if local access terms allow it |
| Buckeye | natural connected speech, reductions, weak forms, rhythm/compression examples and manual QA windows |
| TED-LIUM | long-form transcript/timing and product-like speech; manual rhythm QA where needed |
| local product media | real user-facing listening explanation QA and release gate |

Minimum sample targets:

- TIMIT: at least 50 utterances for evidence-layer phone/timing sanity.
- Helsinki/LibriTTS prosody: first adapter smoke with at least 100 labeled utterances before
  using thresholds; scale up after label mapping is validated.
- Human prosody gold corpora: start with 20-50 locally available utterances/windows per corpus,
  only storing metrics/reports in the repo.
- Buckeye: at least 30 clean windows selected from lexical speech, excluding long noise/lead-in spans.
- TED-LIUM: at least 10 dev/test segments for transcript/timing and rhythm UI smoke.
- Product media: at least 10 manually scored listening hotspots.

Acceptance:

- New manifest or extension records rhythm-evaluation role per case.
  **Landed** as `testdata/rhythm-prosody-benchmarks/benchmark-roles.json` for Phase 2.20
  role/evidence-class convention; per-case manifests can reference these roles.
- Manual QA template exists before more cases are generated.
- Public weak-label and optional human-gold corpora are treated as benchmark tiers, not as

## Step 5: Pipeline Diagnosis From Results

Use evaluation results to identify blockers by layer:

| Symptom | Likely layer |
|---|---|
| bad transcript or wrong words | ASR/transcript |
| anchor on wrong word | lexical stress / POS / salience model |
| phrase boundary misplaced | word timing / pause detection / segmentation |
| compression span missed | duration normalization / syllable count |
| weak group wrong | function-word attachment / grammar context |
| useful hotspot absent | connected-speech classifier |
| misleading phone explanation | CTC phone model / symbol mapping / alignment |

Acceptance:

- Phase closeout reports which layer most blocks product usefulness.
- Follow-up phase is based on measured bottleneck, not intuition.

## Success Criteria

Phase 2.20 is successful when:

1. The default design target is rhythm-first, not phone-first.
2. A `RhythmFrame` or equivalent resource shape is specified and implemented enough for UI.
3. UI can display expected pronunciation, observed rhythm frame, mismatch/hotspot explanation
   and optional phone detail.
4. Evaluation includes stress/rhythm/listening-explanation quality, not just phone PER.
5. Existing phone-level benchmarks continue to run as evidence-layer regression.
6. The closeout can answer: “Does this help explain why the sentence was hard to hear?”
