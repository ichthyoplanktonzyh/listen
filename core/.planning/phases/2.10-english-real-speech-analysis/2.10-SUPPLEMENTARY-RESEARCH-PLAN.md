## 一、背景与动机

### 1.1 项目上下文

LLPlayerNext 是一个多语言听力学习媒体播放器。Phase 2.10 的目标是选出 phone-level
provider，让英语语流分析从"文本预测"升级为"音频检测"（`DetectedInAudio`）。

### 1.2 第一轮 Benchmark 结论（已完成，见 `2.10-BENCHMARK.md`）

第一轮评估了 4 个候选，在 10 条 TIMIT development cases 上运行：

| 候选 | PER | 状态 | 问题 |
|------|-----|------|------|
| MFA (english_mfa) | 33.8% | ✅ 可用 | 只输出 canonical phone，不检测真实发音 |
| ZIPA (small-crctc-300k) | 50.0% | ⚠️ 待许可证 | IPA→TIMIT 映射损失大；许可证未验证 |
| slplab W2V2 | 31.5% | ❌ 失效 | **韩国人学英语 L2 发音评估模型**，非母语语流识别 |
| l2-arctic W2V2 | 97.0% | ❌ 失效 | L2 非母语训练数据，输出空间完全不匹配 |

**关键发现**：slplab 和 l2-arctic 的训练目标是 **L2 发音错误检测**（mispronunciation
detection），不是母语 connected speech phone recognition。它们的结果不可用于选型。

### 1.3 本次研究目标

在同一组 10 条 TIMIT dev cases 上，补充评估两个新候选：

1. **候选 E**：`facebook/wav2vec2-lv-60-espeak-cv-ft` — Facebook 官方多语言 phoneme 模型
2. **候选 F**：`vitouphy/wav2vec2-xls-r-300m-timit-phoneme` — XLS-R 在 TIMIT 上 fine-tuned

评估完成后，结合第一轮有效候选（MFA / ZIPA），做出最终选型决策。

## 二、候选详情

### 2.1 候选 E：facebook/wav2vec2-lv-60-espeak-cv-ft

| 属性 | 值 |
|------|-----|
| HuggingFace ID | `facebook/wav2vec2-lv-60-espeak-cv-ft` |
| 基座模型 | wav2vec2-large-lv60 (LibriVox 60k hours self-supervised) |
| 微调数据 | CommonVoice (多语言母语者语音) |
| 输出 | IPA phoneme（espeak 音标集） |
| 模型大小 | ~1.26 GB |
| 许可证 | Apache 2.0 ✅ |
| 论文 | "Simple and Effective Zero-shot Cross-lingual Phoneme Recognition" (Xu, Baevski, Auli) |

**为什么值得评估**：
- 训练数据是 **母语者语音**（CommonVoice + LibriVox），训练目标是通用 phoneme recognition
- 不是 L2 发音评估模型（与 slplab/l2-arctic 本质不同）
- IPA 输出，与 ZIPA 同类，可直接与 ZIPA 对比
- Apache 2.0 许可证清晰，无分发限制

**已知风险**：
- 模型 ~1.26 GB，比 ZIPA 67MB 大 18 倍——但如果 PER 显著更低，可考虑运行时成本 tradeoff
- espeak IPA 音标集与 TIMIT phone set 需要映射表（同 ZIPA 面临的问题）
- 多语言模型可能在英语特化任务上不如单语模型

### 2.2 候选 F：vitouphy/wav2vec2-xls-r-300m-timit-phoneme

| 属性 | 值 |
|------|-----|
| HuggingFace ID | `vitouphy/wav2vec2-xls-r-300m-timit-phoneme` |
| 基座模型 | wav2vec2-xls-r-300m (128 language self-supervised) |
| 微调数据 | TIMIT (80/10/10 split) |
| 输出 | TIMIT phone set（原生，无需映射） |
| 模型大小 | ~1.2 GB |
| 许可证 | Apache 2.0（待确认） |
| 报告 PER | ~8% on TIMIT test |

**为什么值得评估**：
- 直接输出 TIMIT phone set，**无需 IPA→TIMIT 映射**（消除映射损失问题）
- 报告 PER ~8%，如果属实远优于所有现有候选
- 在 TIMIT 上 fine-tuned，直接与我们的 benchmark 数据集匹配

**已知风险**：
- **过拟合风险高**：在 TIMIT 上训练+测试，PER ~8% 可能不泛化到自然连续语流
- TIMIT 是朗读语体（read speech），弱读/闪音/省音较少——模型可能没学到 connected speech 特征
- 即使 PER 很低，也不能证明它对 connected speech 有效——朗读语体接近 canonical 发音

### Phase B：编写适配器脚本（~1.5 小时）

#### B1. 创建通用 wav2vec2 CTC phoneme 推理脚本

创建 `scripts/wav2vec2-ctc-phoneme-research.py`，作为候选 E 和 F 的通用推理适配器。
输出格式必须与 `phonetic-research-adapter.py run` 兼容：

```json
{
  "phones": [
    {"symbol": "sh", "start_ms": 602, "end_ms": 702, "confidence": 0.95},
    {"symbol": "iy", "start_ms": 702, "end_ms": 799, "confidence": 0.88}
  ],
  "phone_set": "timit_phone",
  "time_base": "relative"
}
```

**脚本要求**：

1. 接受命令行参数：
   - `--model <local_model_dir>` — 本地模型目录
   - `--audio <wav_path>` — 输入音频文件
   - `--audio-start-ms <int>` — 音频起始时间
   - `--audio-end-ms <int>` — 音频结束时间

2. 推理逻辑：
   ```python
   import torch, torchaudio, json, sys, argparse
   from transformers import Wav2Vec2ForCTC, Wav2Vec2Processor

   # 1. 加载音频（裁剪到 start_ms..end_ms 范围）
   # 2. 重采样到 16kHz mono
   # 3. 运行 CTC 推理，获取 logits
   # 4. argmax 解码，合并连续相同 token，去掉 blank/padding
   # 5. 将 frame indices 转换为 ms timestamps（相对于 audio_start_ms）
   # 6. 输出 JSON 到 stdout
   ```

3. CTC 解码和时间戳投射逻辑：
   ```python
   # CTC argmax 解码
   predicted_ids = torch.argmax(logits, dim=-1)[0]

   # 获取 processor 的 blank token id
   # 对于 wav2vec2: pad_token_id 通常就是 blank
   blank_id = processor.tokenizer.pad_token_id

   # 合并连续相同 frame，去 blank
   phones = []
   prev_id = -1
   span_start = 0
   for frame_idx, token_id in enumerate(predicted_ids):
       token_id = token_id.item()
       if token_id != prev_id:
           if prev_id != blank_id and prev_id >= 0:
               symbol = processor.tokenizer.decode([prev_id]).strip()
               if symbol:  # 非空 symbol
                   start_ms = round(span_start * duration_ms / num_frames)
                   end_ms = round(frame_idx * duration_ms / num_frames)
                   if end_ms > start_ms:
                       phones.append({
                           "symbol": symbol,
                           "start_ms": start_ms,
                           "end_ms": end_ms
                       })
           span_start = frame_idx
           prev_id = token_id
   # 处理最后一个 span
   if prev_id != blank_id and prev_id >= 0:
       symbol = processor.tokenizer.decode([prev_id]).strip()
       if symbol:
           start_ms = round(span_start * duration_ms / num_frames)
           end_ms = duration_ms
           if end_ms > start_ms:
               phones.append({
                   "symbol": symbol,
                   "start_ms": start_ms,
                   "end_ms": end_ms
               })
   ```

4. **输出必须是单个 JSON object 到 stdout**，不能有其他输出混入 stdout
   （warning/info 输出到 stderr）。

5. 不要使用 GPU（MPS），因为 `phonetic-research-adapter.py run` 的 RSS 测量假设单进程。
   用 `device="cpu"`。如果 CPU 推理过慢（>30 秒/case），可以切换 MPS 但在指标中注明。

#### B2. IPA→TIMIT 映射表（候选 E 专用）

候选 E 输出 espeak IPA，需要映射到 TIMIT phone set 才能与 reference 对比。
创建 `scripts/ipa-to-timit-phone-map.json`：

```json
{
  "_comment": "espeak IPA → TIMIT phone mapping (best-effort, lossy)",
  "mapping": {
    "ʃ": "sh", "iː": "iy", "ɪ": "ih", "ɛ": "eh", "æ": "ae",
    "ɑː": "aa", "ɒ": "aa", "ɔː": "ao", "ʊ": "uh", "uː": "uw",
    "ʌ": "ah", "ə": "ax", "ɜː": "er", "ɝ": "er", "ɚ": "axr",
    "eɪ": "ey", "aɪ": "ay", "ɔɪ": "oy", "aʊ": "aw", "oʊ": "ow",
    "p": "p", "b": "b", "t": "t", "d": "d", "k": "k", "ɡ": "g",
    "tʃ": "ch", "dʒ": "jh", "f": "f", "v": "v", "θ": "th", "ð": "dh",
    "s": "s", "z": "z", "ʒ": "zh", "h": "hh", "m": "m", "n": "n",
    "ŋ": "ng", "l": "l", "ɹ": "r", "r": "r", "w": "w", "j": "y",
    "ɾ": "dx", "ʔ": "q"
  }
}
```

**重要**：这个映射表是有损的。espeak IPA 的符号粒度与 TIMIT phone set 不完全对应
（例如 espeak 可能输出 `ɪ` 和 `i` 两个不同符号但 TIMIT 只有 `ih`/`iy`）。
在 benchmark 报告中必须注明映射损失。

实际操作时：
1. 先在 1-2 条样本上跑候选 E，收集它实际输出的所有 IPA 符号
2. 根据实际输出调整映射表（不要凭空假设 espeak 输出哪些符号）
3. 记录无法映射的符号（unmapped symbols）和映射冲突

### Phase D：选型分析（~1 小时）

#### D1. 全候选对比表

汇总所有有效候选（MFA + ZIPA + 候选 E + 候选 F）的指标到一张表中：

| 指标 | MFA | ZIPA | 候选 E (fb-espeak) | 候选 F (vitouphy) |
|------|-----|------|-------------------|------------------|
| PER (content phones) | 33.8% | 50.0% | ? | ? |
| timeline_valid_ratio | 0.1 | 1.0 | ? | ? |
| token_association | 0.0 | 0.0 | ? | ? |
| 模型大小 | ~200MB | 67.5MB | ~1.26GB | ~1.2GB |
| 推理 RTF | <0.1 | ~0.85 | ? | ? |

| 映射损失 | 无 | 有 | 有 | 无 |

| connected speech 保真 | ❌ canonical | ✅ IPA | ✅ IPA | ⚠️ 待验证 |

#### D2. Connected Speech 保真度定性分析

PER 只是量化指标。对最终选型更重要的是：**候选能否区分弱读 vs 全读发音？**

选取 2-3 条含弱读现象的 case（如 m20-001 "She had your dark suit..."），对每个候选
的输出做定性分析：

- "your" 应该弱读为 /jə/ 而不是 /jɔːr/——候选输出了什么？
- "in" 应该弱读为 /ɪn/ 或 /ən/——候选是否区分？
- "water" 中的 flap /ɾ/（TIMIT: `dx`）——候选是否识别？

记录每个候选对关键语流现象的识别情况，形成定性评分。

#### D3. 候选 F 过拟合检验

如果候选 F 的 PER 很低（<15%），需要额外检验是否过拟合：

1. **检查 TIMIT train/test 泄漏**：候选 F 的训练集是 TIMIT train（80%），我们的 dev
   cases 来自 TIMIT TEST subset——理论上不应有泄漏，但需确认
2. **检查 sentence overlap**：TIMIT SA1/SA2 是所有说话人都读的 dialect sentences——
   训练集中肯定有不同说话人读同一句话的版本。如果 PER 在 SA1/SA2 上特别低但在
   SX/SI 上高，说明句子级过拟合
3. **分析 per-case PER 方差**：如果所有 case 的 PER 都一致地低，过拟合风险小；
   如果 SA1/SA2 特别好而其他差很多，说明问题

#### D4. 最终选型决策

基于上述分析，在以下方案中选择：

**方案 C — MFA boundary + CTC identity 双层**
- MFA 提供 phone boundaries，CTC 模型（ZIPA / 候选 E / 候选 F 中 PER 最优者）提供 phone identity
- 优势：各取所长；劣势：管线复杂度翻倍

**方案 E — 候选 E 独立**
- 如果 fb-espeak PER < 30% 且 connected speech 保真度好
- 优势：Apache 2.0 清晰、Facebook 官方模型可靠；劣势：1.26GB 较大

**方案 F — 候选 F 独立**
- 如果 vitouphy PER < 15% 且过拟合检验通过
- 优势：TIMIT phone set 原生输出、无映射损失；劣势：可能不泛化

**方案 Z — ZIPA 独立（如许可通过）**
- 如果 ZIPA 许可证审查通过且新候选无明显优势
- 优势：67MB 最小模型；劣势：PER 50% 部分因映射损失

**方案 N — No provider selected（合法结论）**
- 如果所有候选都不满足质量门禁
- 不要为了选出 provider 而降低标准
- 记录原因和后续调查方向

**选型优先级**（从高到低）：
1. 许可证清晰（必须条件）
2. Connected speech 保真度（区分弱读 vs 全读）
3. Phone Error Rate
4. 模型大小（<200MB 优先，<500MB 可接受）
5. 推理速度（RTF < 0.5）

## 七、FAQ

### Q: 如果两个新候选都不如 ZIPA 怎么办？
A: 那就回到方案 C（MFA boundary + ZIPA identity），但 ZIPA 许可证审查必须先通过。
   如果 ZIPA 许可证不通过，则 "no provider selected" 是合法结论。

### Q: 如果候选 F 的 PER 极低但疑似过拟合怎么办？
A: 记录过拟合证据。如果 SA1/SA2 PER 显著低于 SX/SI cases，则不能信任整体 PER。
   过拟合的候选可用于 research fixture（`ResearchFixture` precision），但不能标为
   `DetectedInAudio`。

### Q: IPA→TIMIT 映射怎么才算"好"？
A: 完美映射不可能（IPA 符号集 >> TIMIT 39 phones）。目标是：
   - 未映射符号 < 5%（绝大多数 IPA 有对应 TIMIT phone）
   - 映射冲突有文档记录（多个 IPA 映射到同一 TIMIT phone）
   - 在报告中注明映射损失对 PER 的影响

### Q: 可以额外搜索其他候选吗？
A: 可以，但优先完成候选 E 和 F 的 benchmark。如果在搜索过程中发现明显更好的候选
  （例如 Whisper 的 phone-level 输出、SpeechBrain phoneme toolkit），记录到 benchmark
   报告的"后续调查方向"中，但不要在本次研究中启动额外的 benchmark。

### Q: reference-dev-v1.jsonl 和 reference-dev-v1-content-only.jsonl 用哪个？
A: 取决于候选输出是否包含 closure phones：
   - 候选 F（TIMIT phone set）：如果输出含 closures，用 `reference-dev-v1.jsonl`
   - 候选 E（IPA）：映射后通常不含 closures，用 `reference-dev-v1-content-only.jsonl`
   - 在报告中注明用了哪个 reference
