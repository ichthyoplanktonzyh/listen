# Phase 3.19.2 Persistence Execution Design

状态：ACCEPTED FOR IMPLEMENTATION

日期：2026-07-26

## Problem

Application repository interfaces are intentionally synchronous: domain/application tests use local
in-memory SQLite directly, and one application call may own a multi-statement transaction. Axum handlers
are asynchronous but currently invoke those synchronous calls while their future is being polled on a
Tokio worker.

The problem seam is therefore not “SQLite versus another database”. It is where async transport dispatches
potentially blocking application work.

Dependency classification:

- domain/application computation: in-process;
- SQLite: local-substitutable, with in-memory and file adapters already used by tests;
- Tokio blocking pool: runtime implementation detail, not a new external port;
- migrations and repository transactions: synchronous locality that must remain behind application
  interfaces.

## Options

| Option | Depth / locality | Compatibility | Cancellation / latency | Decision |
|---|---|---|---|---|
| Generic transport `BlockingExecutor` using `spawn_blocking` | Small interface hides dispatch, panic mapping, timing and diagnostics; application transactions remain local | Sync tests unchanged | Await cancellation does not stop an already running DB operation, matching rusqlite reality; Tokio workers remain free | **Selected** |
| SQLite actor and command enum | Centralizes connection ownership but creates a second interface mirroring 40+ repository traits | Large migration; weak typed transaction composition | Queue latency explicit, cancellation still cooperative | Rejected for current single-user backend |
| Connection pool + per-call dispatch | Useful only after measured read concurrency demands it | Requires connection configuration and transaction audit | Better parallel reads, more lock/consistency complexity | Deferred behind measurement |
| Repository-internal `block_in_place` | Minimal call-site changes but binds persistence adapter to Tokio runtime | Breaks runtime-independent adapter tests/usage; unsuitable on current-thread runtime | Hides blocking from transport and is easy to misuse | Rejected |
| Handwritten `spawn_blocking` in each handler | Works technically | Duplicates join/error/timing behavior across 217 routes | High drift and poor observability | Rejected |

## Selected Interface

One concrete module, not a trait:

```rust
ApplicationExecutor::execute(|services| -> Result<T, ApplicationError>)
```

The implementation owns:

- cloning the application composition handle;
- dispatch to Tokio's blocking pool;
- conversion of join/panic failure into a stable internal application error;
- operation name and duration diagnostics;
- future slow-operation threshold behavior.

Route callers own only request extraction and result/HTTP mapping. No database types cross this interface.
There is no injected executor adapter because there is only one real runtime behavior; interface-level tests
exercise the concrete module with deterministic closures.

## Migration Rule

- Migrate synchronous application calls by resource-domain route module.
- Do not dispatch provider-native async/network calls through this executor.
- Move owned request values into the closure; never capture Axum request/state objects.
- Delete each old direct `state.services` path as its module migrates.
- An architecture guard makes direct route access to `AppServices` illegal when migration reaches zero.

## Measurement

The deterministic acceptance test uses a single Tokio worker:

1. dispatch a blocking closure that waits on a test barrier;
2. schedule an unrelated async timer/task;
3. prove the async task completes before releasing the blocking closure;
4. release and verify the application result.

This characterizes the failure mode without relying on machine-specific millisecond benchmarks. A later
pool decision requires real corpus load measurements, not synthetic throughput claims.
