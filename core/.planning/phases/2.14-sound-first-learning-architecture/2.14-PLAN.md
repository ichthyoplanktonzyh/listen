## 两条线的关系

| | 文字线（Phase 2.13） | 声音线（本 Phase） |
|---|---|---|
| 数据来源 | Whisper 转录 → 词 → 词典发音 | CTC 模型 → 真实音素序列 |
| 组织层级 | Sentence → Word → Token → Phoneme | Sentence → Prosodic Phrase → Syllable → Phone |
| 时间边界 | 词边界（文字强加于声音） | 韵律边界（声音的自然断点） |
| 学习内容 | "说了什么" | "怎么说的" |
| 两者差异 | — | "为什么听不懂" |

两条线共享 sentence 作为最高作用域边界，数据共存于同一个 lltime.json。

## 理论基础

韵律层级（Nespor & Vogel 1986, Selkirk 1984）：

```
Phone → Syllable → Foot → Prosodic Word → Phonological Phrase → Intonation Phrase
```

- **音节**是语音产出的基本单位（MacNeilage 1998, Levelt et al. 1999）
- **韵律短语**由停顿、末尾延长（final lengthening）、语调重置界定
- 词边界在连续语流中经常消失（连读、弱化、省音）
- 声音线揭示的是这些文字线无法表达的真实发音模式

## Steps

### Step 1: 音节化算法

从 CTC 音素序列推导音节边界。

- 输入：`List<DetectedPhone>`（按时间排序的音素序列）
- 输出：`List<Syllable>`，每个 syllable 包含 onset/nucleus/coda 音素索引
- 算法：响度排列原则（Sonority Sequencing Principle, SSP）
  - 元音为 nucleus（响度最高点）
  - 辅音按响度下降排向两侧
  - Onset Maximization：歧义辅音优先归入下一音节的 onset
- 响度等级（从低到高）：plosive < fricative < nasal < liquid < glide < vowel
- 实现位置：Rust `speech-analysis` crate，纯算法无 ML 依赖
- 测试：TIMIT 样本的音节划分与语言学标注对比

### Step 2: 韵律短语检测

从音素序列的时间特征推导短语边界。

- 边界证据（按可靠度排序）：
  1. **静音段**（silence/pause）：音素间 gap > 阈值（~100ms）
  2. **末尾延长**：短语末音节的 nucleus 时长显著长于句内平均
  3. **音素间距突变**：相邻音素间 gap 的局部峰值
- 输出：`List<ProsodicPhrase>`，每个 phrase 包含 syllable 索引范围 + 边界证据类型
- 不依赖 F0（基频）——CTC 模型不输出 pitch，且 F0 提取需额外工具
- 实现位置：Rust `speech-analysis` crate

### Step 3: Domain 模型与持久化

- `domain` 新增 `Syllable`、`ProsodicPhrase`、`SoundAnalysis` 结构体
- `SoundAnalysis` 挂在 `PhoneticAnalysis` 之下（CTC 分析完成后自动推导）
- SQLite 存储：复用 `phonetic_analysis_results` 的 JSON 字段扩展
- LLTimeline export/import 保留 `sound_analysis`
- API 新增 `GET /v1/tracks/{id}/sound-analysis/{sentence_id}`

### Step 4: Flutter 消费与 UI

- `SubtitleController` 新增 `soundAnalysisBySentence`
- `PhonemeRibbon` 增强：可选按音节分组显示（音节间加视觉分隔）
- 韵律短语边界在 ribbon 上以垂直分隔线标记
- 新增声音线视图模式：ribbon 按韵律短语分段，而非按句子整条显示
- 与文字线的 chunk 对比视图（高级功能，可延后）

### Step 5: 声音线 Finding 关联

- 连读/省音/弱化等语流现象（speech rules）现在可以用声音证据佐证
  - 文字线：规则预测（"did you 可能连读"）
  - 声音线：真实证据（"检测到 /dɪdʒə/ 跨词边界"）
- Finding 的 `evidence_source` 区分 `rule_prediction` vs `audio_detection`
- 在 ribbon 上叠加 finding 标记（底部标记条/角标），点击展开详情

### Step 6: 测试与验收

- 音节化：英语 TIMIT 样本验证 + 手动标注对比
- 韵律短语：停顿检测准确率（precision/recall）
- 端到端：CTC 分析 → 自动推导音节/短语 → ribbon 显示分组 → 跳动
- lltime.json round-trip：export → import 保留 sound_analysis
- 性能：一句话通常 3-8 音节、1-3 韵律短语，无额外性能负担

## Risk & Mitigation

| 风险 | 应对 |
|---|---|
| SSP 音节化对英语不完美（如 /str/ onset） | 允许例外列表（language profile 可扩展） |
| 纯时间特征的韵律短语检测不够准确 | 先做高置信度（停顿），低置信度标为 tentative |
| 用户不理解"声音线"和"文字线"的区别 | UI 层面不暴露术语，用视觉差异（ribbon 分组方式）自然呈现 |
| 多语言适用性 | 音节化和韵律检测的核心原理跨语言通用；语言特异性通过 profile 参数化 |

## Success Criteria

1. CTC 分析完成后，音节边界和韵律短语自动推导可用
2. lltime.json 中 `sound_analysis` 字段可导入导出
3. Ribbon 可按音节分组显示，韵律短语边界可见
4. 声音线与文字线的差异（连读/省音等）在 UI 上可感知
5. 整条链路不依赖 F0 提取或额外 ML 模型
