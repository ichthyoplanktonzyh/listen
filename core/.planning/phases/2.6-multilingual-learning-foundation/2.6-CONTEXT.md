## Background

LLPlayerNext 当前主要服务英语听力学习。已经落地的播放器、字幕资源、时间轴资源、
词汇状态和诊断体系，为多语言学习提供了可复用底座，但很多学习层能力仍然是英语优先：

- `TXT-001` 明确是英语 token 化。
- `subtitle-core` 当前使用 `tokenize_english()`。
- Flutter client 多处请求仍硬编码 `language=en`。
- 词汇状态、字典、lemma、发音和规则型语流提示主要围绕英语实现。
- Chunk / PhoneTimeline 的研究语境当前主要是英语。

Phase 2.6 的目标不是立刻支持世界所有语言，而是建立可持续扩展的多语言学习基础。
首批验收语言明确为：

```text
English + Chinese
```

英语继续作为当前主线，汉语作为第一种真正暴露架构假设的非空格分词语言。

## Product Motivation

产品长期方向是支持主要语言的听力学习，而不是只做英语工具。这里的“多语言”不是
营销意义上的“所有语言”，而是：

- 重要语言优先。
- 每种语言有明确能力矩阵。
- 语言相关能力通过 provider / profile / capability 声明进入系统。
- 没有能力的语言干净降级，不假装完整支持。

更重要的是，多语言学习基础必须以听力能力为核心，而不是以文字符号系统为核心。
真正可交流的语言能力来自学习者对真实声音流的稳定理解；文字、词典、语法、翻译
和字幕是解释层、校准层和复盘层。Phase 2.6 因此不能只建立
`text -> token -> dictionary -> meaning` 的模型，而要让系统能够表达
`audio -> listening units -> meaning candidates -> lexical/text explanation`。

汉语是最适合作为第二语言基线的原因：

- 它不依赖空格分词，能迫使 tokenizer 从英语假设中解耦。
- 它同时需要字、词、短语多粒度学习单位。
- 它有拼音、声调、变调、轻声、儿化等独特发音/声音模式。
- 外国人学汉语的核心困难和英语不同，能检验诊断模型是否足够抽象。

但 Phase 2.6 的架构校验不应只停留在 English + Chinese。英语和汉语负责本阶段真实
实现与验收，Spanish、French、German、Russian 等主流语言应作为 design validation
set，用于压力测试 listening unit、rhythm/prosody、morphology、pronunciation 和
diagnosis 抽象是否合理。

详见同目录 `2.6-LANGUAGE-LISTENING-MODEL.md`。

- `LanguageCode` 与词汇状态语言隔离。

## Current English Assumptions

需要解耦的英语假设：

1. **Tokenizer**
   - 当前 `tokenize_english()` 会把连续汉字当作一个 word token。
   - 汉语需要分词，并且需要保留字级 fallback。

2. **Lexical Unit**
   - 当前学习单位近似等于英语 lemma。
   - 汉语需要支持 char / word / phrase 多粒度学习单位。

3. **Language Hardcoding**
   - 桌面 API client、词汇本、字典查询、来源快照多处固定 `language=en`。
   - 需要从字幕轨、用户选择或媒体资源中传递学习语言。

4. **Dictionary**
   - 当前 provider 主要支持英语。
   - 汉语需要中英释义、拼音、声调、例句、HSK/频率等字段。

5. **Pronunciation**
   - 英语使用 CMUdict / ARPAbet / IPA / 连读弱读规则。
   - 汉语需要拼音、声母韵母、声调、变调和轻声。

6. **Diagnosis**
   - 当前诊断主要围绕“不认识词 / 认识但听不出词”。
   - 汉语还需要表达“认识汉字但不认识词”“声调听不出”“词边界切分失败”等问题。

## Scope

Phase 2.6 聚焦建立语言能力底座：

1. 定义 language learning profile / capability matrix。
2. 定义 language-specific listening model，明确不同语言的听觉单位和听力诊断路径。
3. 引入 language-aware tokenizer。
4. 把学习单位从 `lemma` 扩展为 `LexicalUnit`，并与 `ListeningUnit` 区分。
5. 去除桌面端和 API client 的 `language=en` 硬编码。
6. 接入汉语最小词典 / 拼音 provider。
7. 为汉语建立最小可用学习面板和诊断。
8. 建立英语 + 汉语双语言回归测试，并用主流语言做架构压力测试。

## Non-Goals

- 不在本阶段支持所有语言。
- 不引入完整多语言 ASR / FA / PhoneTimeline 生产能力。
- 不要求汉语一开始拥有英语同等的 ChunkTimeline / Sound Pattern 深度。
- 不重写现有英语词汇资产。
- 不破坏英语当前行为。
- 不把界面语言和学习语言混为一谈。

## Success Criteria

- 英语路径保持不回归。
- 汉语字幕可以被正确分词或以可解释 fallback 方式拆分。
- 文档和 profile 设计能区分 `Token`、`LexicalUnit` 和 `ListeningUnit`。
- English / Chinese / Spanish / French / German / Russian 的听力学习差异不会迫使架构
  出现硬编码特例分支。
- 用户可以在汉语 token / lexical unit 上建立词汇状态、来源快照和词汇本条目。
- 字典查询可按 `zh` provider 返回拼音和基础释义。
- API client 不再固定 `language=en`。
- 当前学习语言来自字幕轨或用户明确选择。
- 文档明确后续语言扩展方式和能力矩阵。
