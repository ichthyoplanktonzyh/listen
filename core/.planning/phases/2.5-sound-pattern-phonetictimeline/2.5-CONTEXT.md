# Phase 2.5 Context: Sound Pattern And PhoneTimeline

更新时间：2026-06-20 23:10 CST

## Background

LLPlayerNext 已经具备三条相关基础线：

1. Milestone 1.9 的规范发音系统：从词典、G2P 和规则引擎生成整句音标、
   词级发音和规则型连续语流提示。
2. Milestone 2 的资源体系：LLTimeline JSON 已支持 `phonemes` /
   `phone_timelines` 扩展位，WordTimeline 已进入 app 消费闭环。
3. 真实语流分析骨架：`PhoneticAnalysisJob`、`DetectedPhone`、`PhoneAlignment`、
   `PhoneticFinding`、模型/任务/结果/反馈持久化和 UI 中心已经存在，但当前 provider
   仍是 deterministic research fixture，不是真实音频模型。

当前产品中的音标显示回答的是：

```text
根据词典和规则，这句话理论上可能怎么发音？
```

Phase 2.5 要开始回答另一个问题：

```text
这段真实音频中，学习者实际听到的声音模式是什么？
```

## Product Motivation

这个阶段的动机不是“多显示一行 IPA”，而是改变听力学习的入口。

传统文字中心路径容易被理解为：

```text
audio -> words -> meaning
```

但真实听力理解更接近：

```text
audio -> sound patterns -> chunks / phrase patterns -> meaning
```

word/text 仍然重要，但它们不是唯一入口。学习者真实卡住的地方，常常不是不知道
`did`、`you`、`want`、`to` 这些词，而是听到 `/dɪdʒə wɑnə/` 时无法把这个声音模式
直接识别为熟悉的语言结构。

因此 Phase 2.5 的产品目标是把“真实声音模式”变成一等学习对象：

```text
/dɪdʒə/ -> did you
/wɑnə/  -> want to
/aɪmənə/ -> I am going to
```

这不是从 word 反推发音，而是从真实发声出发，建立 sound pattern 与意义之间的映射。
word/text 在这里扮演解释层、标注层和对齐层。

## Problem

当前系统有两个明显缺口：

1. **规范发音不等于真实发声**
   - 词典音标、G2P 和规则提示可以解释可能发生什么，但不能证明音频里实际发生了什么。
   - 规则提示必须保持 `possible_by_rule` / `likely_by_context` 语义，不能伪装成音频检测。

2. **真实音素结果还不是资源**
   - `DetectedPhone` 和 phonetic analysis 结果可以持久化，但还没有形成像
     WordTimeline 一样可导入、可激活、可导出、可播放消费的 PhoneTimeline。
   - 当前 app 没有以 sound pattern 为中心的学习视图；音标仍附属于文字字幕。

## Current State

已具备：

- `LLTimelinePhoneTimeline` domain model。
- `PhoneticAnalysisProviderInfo` / `PhoneticAnalysisModelDescriptor`。
- `PhoneticAnalysisJob` 状态机：
  `queued -> extracting -> recognizing_phones -> aligning -> analyzing -> completed`。
- `DetectedPhone`：symbol、phone_set、start/end、confidence、token_index、provider/model。
- `PhoneAlignment` 和 `PhoneticFinding`。
- SQLite migration `0009_phonetic_analysis.sql`。
- `/v1/phonetic-analysis/...` API。
- Flutter `PhoneticAnalysisCenter`。
- research fixture 测试 cancel / retry / partial / feedback 生命周期。

尚未具备：

- 真实 audio -> phone recognizer provider。
- PhoneTimeline 的 candidate / active / archived 生命周期。
- PhoneTimeline import/export 的完整消费闭环。
- 播放器中的 current phone / current sound pattern 高亮。
- 以 sound pattern 为中心的学习 UI。
- 可信模型基准与发布门槛。

## Scope

Phase 2.5 聚焦：

1. 建立真实 phone recognizer provider 的研究基准。
2. 明确 PhoneTimeline 资源契约和 LLTimeline 映射。
3. 将现有 phonetic analysis 结果升级为可管理的 PhoneTimeline candidate。
4. 实现 sound pattern view：
   - 显示真实 detected phones。
   - 对齐 canonical pronunciation 和 words。
   - 标出弱读、省音、闪音、同化、缩约等 finding。
   - 支持点击 phone / pattern 循环播放。
5. 明确所有结果的置信度、provider provenance 和降级语义。

## Non-Goals

- 不把不可靠模型结果标记为 `detected_in_audio`。
- 不把 PhoneTimeline 做成 WordTimeline 的附属文本行。
- 不追求第一版输出完整狭式 IPA。
- 不把大型 Python/PyTorch 模型直接打包进轻量消费端。
- 不自动修改词汇状态；真实语流发现只作为诊断证据。
- 不要求没有 phone provider 的用户也能使用该功能；无 provider 时必须干净降级到
  M1.9 规范发音和规则提示。

## Success Criteria

- 至少完成 Wav2IPA / ZIPA / MFA phone alignment / Allosaurus 或等价候选的对比报告。
- 选出一个可继续工程化的 provider，或明确“暂无可发布 provider”的结论。
- PhoneTimeline 资源契约明确，并能承载 detected phones、alignment、findings 和
  provenance。
- app 能展示一条真实或 fixture PhoneTimeline candidate，并以 sound pattern 视角解释
  它和文字/意义的关系。
- 低置信、模型缺失或许可证不可用时不会误导用户。
