# Phase 2.5 Plan: Sound Pattern And PhoneTimeline

更新时间：2026-06-20 23:10 CST

## Objective

把真实声音模式从“文字字幕的附属解释”升级为一等学习对象：从音频中得到可验证的
DetectedPhone / PhoneTimeline，和文字、规范发音、chunk、意义建立双向映射，并支持
播放高亮、循环和真实语流诊断。

## First Thing To Do

Phase 2.5 第一件事是 **候选 provider benchmark + PhoneTimeline 资源契约**，而不是
直接做漂亮的音标 UI。

原因：

- 如果模型只是把真实语流规范化回字典发音，UI 做得再好也会误导用户。
- 只有资源契约稳定，MFA、Wav2IPA、ZIPA、自研模型和人工修正才能输出同一种
  PhoneTimeline。
- 用户真正需要的是“这段声音听起来是什么模式，并代表什么”，不是单纯看到 IPA 字符串。

## Design Principle

```text
audio
  -> detected phone / sound pattern timeline
  -> alignment to canonical pronunciation and words
  -> connected-speech findings
  -> sound-pattern learning interaction
```

核心原则：

- **Sound pattern first**：真实发声模式是一等对象，word/text 是解释层和对齐层。
- **Evidence over decoration**：音标不是装饰文本，必须关联真实音频范围、置信度和来源。
- **Honest uncertainty**：规则预测、对齐支持和真实音频检测必须分层展示。
- **Resource lifecycle**：PhoneTimeline 需要 candidate / active / archived 生命周期。
- **Production-resource split**：重型模型优先在生产端或研究端运行，轻量消费端读取资源。

## Work Breakdown

### Step 1: Provider Benchmark And Quality Gate

建立小型固定评估集，比较真实音频到 phone / IPA 的候选 provider。

候选：

- MFA phone-level forced alignment。
- Wav2IPA / Wav2Vec2Phoneme Buckeye-style model。
- ZIPA 64M 或等价轻量 phone recognizer。
- Allosaurus 仅作为研究 baseline，不作为默认分发候选。

评估问题：

- 是否保留弱读、省音、闪音、缩约，而不是规范化回字典发音。
- phone timeline 是否单调、位于音频范围内。
- detected phones 能否稳定关联回字幕 token。
- 高置信 finding 的人工精确率是否足够。
- Apple Silicon 本地运行成本和许可证是否可接受。

Exit criteria:

- 形成 provider benchmark 文档。
- 明确可继续工程化的 provider，或明确暂无可发布 provider。
- 未达门槛的 provider 不得进入默认 product path。

### Step 2: PhoneTimeline Resource Contract

将 PhoneTimeline 定义为一等资源，而不是一次性分析结果。

建议核心字段：

- `phone_timeline_id`
- `track_id`
- `parent_word_timeline_id`
- `parent_phonetic_analysis_id`
- `status`: `candidate | active | archived`
- `created_by`: `system | user`
- `provider_id` / `provider_version`
- `model_id` / `model_revision`
- `phone_set`: `ipa | arpabet | provider_specific`
- `precision`: `detected | aligned | approximate`
- `phones_json`
- `alignments_json`
- `findings_json`
- `metrics_json`
- `created_at_ms`

每个 phone 至少包含：

- `symbol`
- `phone_set`
- `start_ms`
- `end_ms`
- `confidence`
- `token_index`
- `word_ref`
- `provider_id`
- `model_revision`

Exit criteria:

- PhoneTimeline 与 `PhoneticAnalysis` 的关系明确。
- LLTimeline import/export 能保留 PhoneTimeline。
- 可以区分 detected phones、forced-aligned phones 和规则/规范发音。

### Step 3: Phonetic Analysis To PhoneTimeline Bridge

复用现有 phonetic analysis 骨架，把 completed analysis 转换为 PhoneTimeline candidate。

工作：

- 保留当前 job/model/feedback 生命周期。
- completed analysis 保存后创建 PhoneTimeline candidate。
- candidate 可 list / activate / archive / delete。
- 低置信或 fixture 结果只能标为 experimental / approximate。

Exit criteria:

- research fixture 也能走完整 PhoneTimeline lifecycle，但 UI 明确标记为 synthetic。
- 真实 provider 接入后不需要改 UI 消费契约。

### Step 4: Sound Pattern View

新增以声音模式为中心的学习视图。

视图结构：

```text
Detected sound pattern
  /dɪdʒə/  /wɑnə/  /ɡoʊ/

Mapped text
  did you  want to  go

Meaning / note
  "did you" question frame, "want to" intention phrase
```

交互：

- 当前播放 phone / sound pattern 高亮。
- 点击 phone 或 pattern 跳转并循环对应音频范围。
- 显示 canonical pronunciation、rule prediction、detected audio 三层来源。
- finding 可展开查看：canonical phones、detected phones、证据、置信度、provider。
- 用户可确认、驳回或忽略 finding。

Exit criteria:

- 用户能从声音模式出发理解它对应的文字和意义。
- 不再只是“句子下方显示一串 IPA”。

### Step 5: Playback Consumption

让播放器本地消费 active PhoneTimeline。

功能：

- current phone lookup。
- current sound pattern range。
- phone-level / pattern-level loop。
- 与 current word 和 current chunk 同步显示。
- 无 active PhoneTimeline 时回退到 canonical pronunciation / rules。

Exit criteria:

- 播放位置更新不依赖 API 高频轮询。
- PhoneTimeline 切换后 UI 和高亮刷新。
- phone 高亮不会破坏现有字幕布局。

### Step 6: Diagnostics And Learning Integration

把真实语流发现接入听力诊断，但保持证据式展示。

用法：

- “认识但听不出”的词可以显示相关 finding：
  - weak form
  - reduction
  - deletion
  - flapping
  - assimilation
  - contraction
- findings 只解释原因，不自动改变词汇状态。
- 低置信 finding 进入实验区，不进入默认诊断结论。

Exit criteria:

- 诊断能回答“我为什么没听出这段声音模式”。
- 用户反馈能保存，为后续校准模型和规则提供资产。

### Step 7: Export, Regression, Closeout

- LLTimeline export 包含 active/candidate PhoneTimeline。
- 导入含 PhoneTimeline 的 LLTimeline 后能恢复 sound pattern view。
- 更新 STATE、requirements/roadmap 必要引用和 changelog。
- 明确下一阶段是否进入人工 PhoneTimeline 修正或模型工程化。

Exit criteria:

- Phase 2.5 可被验收为：真实声音模式资源可生成、可管理、可消费、可解释。
- 如果 provider 未达质量门槛，阶段也可以以“资源契约 + benchmark + no-release decision”
  收口，不强行发布误导性功能。

## Testing

- Provider benchmark:
  - fixed evaluation catalog。
  - detected phone monotonicity。
  - token association coverage。
  - high-confidence finding manual precision。
- Domain:
  - PhoneTimeline serialization。
  - phone range validation。
  - provider/model provenance preservation。
- Persistence:
  - PhoneTimeline lifecycle。
  - PhoneticAnalysis -> PhoneTimeline candidate。
  - user feedback backup/restore。
- API:
  - list / activate / archive / delete PhoneTimeline。
  - import/export round-trip。
  - low-confidence results never become `detected_in_audio`。
- Flutter:
  - Sound Pattern View renders detected/canonical/rule layers.
  - current phone highlight.
  - click-to-loop phone/pattern.
  - findings feedback.
- Regression:
  - no provider -> M1.9 pronunciation still works.
  - no PhoneTimeline -> word/chunk playback still works.
  - research fixture cannot be mistaken for real audio detection.
