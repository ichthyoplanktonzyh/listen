# Milestone 2.1：对齐管线加固

## Summary

本阶段在 Milestone 2.0 Phase 4 客观评估体系收口后进行，目标是系统性修复
强制对齐管线（Rust 管线 + Python 生产管线）在本次代码评审中暴露的正确性缺陷、
分层违反和可维护性债务。它不是一个新功能阶段，而是一次以"不改变对外行为、
只消除静默错误与结构性耦合"为约束的加固。

覆盖三个层次：

1. **正确性（P0/P1）**：消除强制对齐 sidecar 的 `word_index` 错位静默 bug，
   补齐评估脚本的文本一致性校验，统一被三处复制的 Python tokenizer。
2. **架构（P1）**：把 DTW→forced_align→pause_refinement→activate 编排从
   `api-http` 下沉到 `application` 层，让 Rust 管线与 Python 生产管线共享同一
   编排契约。
3. **可维护性（P2/P3）**：拆分 `application`（~2770 行）和
   `persistence-sqlite`（~3940 行）两个巨型单文件；清理评估脚本的重复计算和
   单调性级联策略的不确定性。

本阶段不引入新运行时依赖，不修改 LLTimeline JSON v1 schema，不新增数据库迁移。

## Background — 问题来源

本阶段的内容来自一次针对 `feature/forced-alignment-research` 分支的代码评审，
以及 `.planning/codebase/CONCERNS.md` 中长期记录的架构债务。问题按优先级整理如下，
每条含根因、触发条件和精确代码位置（评审时行号，实现时以实际为准）。

### 🔴 P0｜align-cli.py 跳词导致 word_index 错位（静默 bug）

**根因**：Python 侧与 Rust 侧对"词列表索引"的语义不一致。

- `scripts/forced-align/align-cli.py:92-93`：`_tokenize_words` 中
  `if not normalized: continue` 直接跳过 normalize 成空的词，**不输出占位**；
  输出循环（`213` 行）的 `word_index` 取**过滤后**词序下标（从 0 重新计数）。
- `crates/speech-analysis/src/forced_align.rs:88-96,134-142`：`merge_alignments`
  用 `rows`（该 sentence 所有 `WordTiming` 行按 `token_index` 排序，**不过滤**）
  的 enumerate 下标 `word_pos` 去查 `by_word.get(&(word_pos as u32))`。
- `crates/api-http/src/transcription.rs:909-913`：传给 Python 的 `words` 含所有
  `SubtitleTokenKind::Word` token，不去除会被 normalize 成空的词。

**后果**：某词 normalize 成空（CJK 字符、纯数字外的非拉丁词、特殊符号）后，
其后所有词的 Python `word_index` 比 Rust `word_pos` 递减偏移，对齐时间戳写到
错误 token 行，甚至句子越界被静默丢弃。纯英语 TIMIT 不触发（171/171 matched），
新闻视频含专有名词、数字、外来语时**必然触发**。

**文档层 bug**：`forced_align.rs:30` 注释声称 Python `word_index` 等同于
`asr_timing::extract_word_timings` 的索引方案——但 Python 做了 normalize 过滤，
两者不等价。契约在文档层就已经失真。

### 🟡 P1｜evaluate 脚本缺 normalized_text 一致性校验

**根因**：词配对只比时间戳位置，不比词内容。

- `scripts/evaluate-word-timelines.py:92-93`：`word_key` 只用
  `(sentence_id, token_index)`。
- `196-209`：`matched_pairs` 命中 key 即配对，**完全不比较 normalized_text**。
- `66`：evaluate 的归一化是内联 `text.strip().casefold()`，**不去标点、不转
  `'`→`'`**，与 pipeline/benchmark 的 `normalize_word` 不同。

**后果**：当 gold 与 candidate 的某 `(sentence_id, token_index)` 配对成功但
词内容不一致（典型：P0 的 word_index 错位把错误词写到了该位置），evaluate 会
**静默计算这对错误配对的误差**，污染 MAE 等评估指标。两条管线的 tokenizer 一旦
漂移，比对会静默失效。

### 🟡 P1｜Python 三处 tokenizer 复制 + 归一化分歧

**根因**：

- `scripts/timeline-production/production_pipeline.py:27` 的 `WORD_RE` 与
  `scripts/benchmark-datasets.py:23` 的 `WORD_RE` **正则不同**（单撇号段 vs
  多段 + 前后撇号）。
- 两者 `normalize_word`（`53`/`43` 行）逐字符相同；evaluate（`66` 行）是第三套
  更弱的归一化；`align-cli.py:78-84` 是第四套 MMS_FA 字典字符过滤。

**后果**：`don't've`、`o'clock`、`'em` 这类词在不同脚本里的 `token_index`
分配可能不同。gold 是 Python 生成的、candidate 是 Rust 生成的，两者 word 匹配
依赖 `(sentence_id, token_index)` 一致——现在 171/171 能对上某种程度是巧合 +
相同归一化逻辑，一旦某条路径改 tokenizer，比对就静默错位。

### 🟡 P1｜强制对齐编排锁死在 api-http 层（分层违反）

**根因**：

- DTW→forced_align→pause_refinement→activate 整条生产管线编排全部硬编码在
  `crates/api-http/src/transcription.rs:556-628`。
- `crates/application/src/lib.rs` 全文 grep `forced_align` 仅命中 `2577` 行的一个
  **测试函数名**，application 层**没有任何编排方法**。
- CONVENTIONS §1 明文规定"`application` 是编排枢纽，HTTP handler 不直接调用
  `speech-analysis` 模块函数"——当前实现违反该硬规则。

**后果**：这套管线无法被 Python 生产引擎路径复用。项目已在 2.0 拆成"本地重装
生产引擎 + 轻量消费端"两条路线，但最核心的时间轴精炼逻辑被锁死在 Rust HTTP
handler 里，Python 的 `production_pipeline.py` 走的是完全独立的 WhisperX 路径。
两条线会越走越远。`try_apply_forced_alignment`（`transcription.rs:824-875`）
含 spawn Python 进程的副作用和研究态的 venv 路径查找，混在生产 handler 里。

### 🟢 P2｜巨型单文件 crate

**根因**：`CONVENTIONS` 鼓励子模块拆分（api-http 已拆出 transcription/phonetic/
m18/speech_jobs），但 application 和 persistence 没动。

- `crates/application/src/lib.rs`：~2770 行，单个 `impl AppServices` 块约 1280 行。
- `crates/persistence-sqlite/src/lib.rs`：~3940 行，9 个 `impl XxxRepository` 块。
- `crates/api-http/src/lib.rs`：~2680 行（已部分拆分，本阶段保持现状）。

**后果**：代码导航困难，合并冲突概率高。2.0 Phase 5（人工校对 UI）和 Phase 6
（消费端集成）都要频繁改 application 和 persistence，届时债务会显著拖慢。

### 🟢 P3｜整洁性与算法策略待评估

- `scripts/evaluate-word-timelines.py:212-226,286-301`：`stats()` 对每个 offset
  列表重复调用（`lead_lag_bias_*` 复算 mean，`gold_metrics` 每个 error 列表被
  stats 6 次），数据量大时不必要。
- `crates/speech-analysis/src/forced_align.rs:335-376`：monotonicity 检查采用
  **级联拒绝**——一个词对齐违反单调性，会让后续词回退到 DTW，即使后续词本身对齐
  良好。对真实 forced alignment 可能过于激进，少量坏对齐会级联拉高 MAE。是否调整
  算法需用 TIMIT gold 做消融后定夺。

## Product Goals

完成后：

1. 在含 CJK、专有名词、数字、外来语的语料上，强制对齐不再出现静默的
   word_index 错位——被跳过的词有显式占位，时间戳不会落到错误 token。
2. 客观评估脚本能发现 gold 与 candidate 的词内容错位（而不只是时间戳差异），
   tokenizer 漂移会被显式告警而非静默吞掉。
3. Python 的 `tokenize`/`normalize_word` 只有一份实现，三处脚本共用。
4. Rust 管线和 Python 生产管线通过 `application` 层共享同一套对齐增强编排
   契约；api-http 不再直接调用 `speech-analysis` 模块函数。
5. `application` 和 `persistence-sqlite` 按域拆分为可独立导航的子模块，
   单文件不超过 ~1000 行量级。

## Core Contracts

### word_index 占位契约（对应 ADR 0011）

sidecar 输出协议仍保持 ADR 0010 的顶层 `timings[]` 形状，只给单条 timing
扩展可选 `skipped` 字段：

```json
{
  "timings": [
    {"segment_index": 0, "word_index": 0, "text": "hello", "start_ms": 100, "end_ms": 300},
    {"segment_index": 0, "word_index": 1, "skipped": true},
    {"segment_index": 0, "word_index": 2, "text": "world", "start_ms": 400, "end_ms": 600}
  ]
}
```

- `word_index` = 该 segment 内**未过滤**词 token 的 0-based 下标，与 Rust 侧
  `WordTiming` 行按 `token_index` 排序后的 enumerate 下标一一对应。
- 被跳过的词输出：

```json
{
  "timings": [
    {
      "segment_index": 0,
      "word_index": 1,
      "skipped": true
    }
  ]
}
```

- skipped timing **不输出** `text`/`start_ms`/`end_ms`；Rust 反序列化使用默认值
  保持向后兼容。
- Rust `merge_alignments` 遇 `skipped:true` 对该词回退到原 DTW 时间。
- **向后兼容**：Rust 容忍无 `skipped` 字段的旧输出（视为全部非跳过）。

### WordTimelinePipeline 编排契约

```text
WordTimelinePipeline::refine_track_timings(
    audio_wav_path: PathBuf,
    sentences: &[SubtitleSentence],
    dtw_timings: Vec<WordTiming>,        // 来自 asr_timing 提取
    venv: Option<ForcedAlignVenv>,       // 探测结果，None 则跳过 sidecar
) -> RefineResult {
    // 1. 保存 DTW 快照（candidate）
    // 2. 若 venv 存在：try_apply_forced_alignment（spawn sidecar + merge）
    //    保存 forced-align 快照（candidate）
    // 3. pause_refinement
    // 4. 保存 active 快照并激活
    // 返回每步的 timeline_id 链（provenance 父子关系）
}
```

- 编排方法在 application 层，依赖通过入参注入（audio 路径、venv 探测结果、
  provenance），不把 `TranscriptionRepository` 塞进 `AppServices`。
- api-http 调用方负责探测 venv、提供 wav 路径、构造 provenance、触发 SSE。
