## 2. 核心决策

### 决策 1：编排下沉到 application 层，而非新增编排 crate

**背景**：DTW→forced_align→pause_refinement→activate 编排当前硬编码在
`api-http/src/transcription.rs:556-628`，违反 CONVENTIONS §1"application 是编排
枢纽"。项目已拆成"本地重装生产引擎（Python）+ 轻量消费端（Rust）"两条路线，
但最核心的时间轴精炼逻辑被锁死在 Rust HTTP handler，Python 生产管线走完全独立的
WhisperX 路径，两条线无法共享对齐增强。

**决定**：

- 在 `application` crate 内新增 `WordTimelinePipeline` 编排方法（不新建 crate）。
- 编排方法组合 `speech-analysis` 的 `extract_word_timings_from_json` +
  `forced_align` + `pause_refinement`，以及 `AppServices` 的 timeline 写入/激活。
- api-http 收敛为薄封装：取 wav 路径 + 构造 provenance + 调用编排 + 触发 SSE。

**影响**：

- Rust 管线与 Python 生产管线未来可通过同一契约（sidecar HTTP 或直接调 Rust 库）
  共享编排。
- 符合 CONVENTIONS §1，CONCERNS 的"api-http 直接耦合 speech-analysis"债务消除。
- 编排逻辑可被独立测试，不必通过 E2E 间接验证（补 CONCERNS §3 的 P1 缺口）。

### 决策 2：编排依赖通过入参注入，不扩大 AppServices 职责

**背景**：`TranscriptionRepository`（`application/src/lib.rs:235`）当前不在
`AppServices` 字段内，转录 job 的 repo 由 api-http 层 `TranscriptionCoordinator`
自己持有。编排下沉时若把 `TranscriptionRepository` 塞进 `AppServices`，会扩大
`AppServices` 职责边界，且 `TranscriptionRepository` 与"时间轴精炼"是不同的关注点。

**决定**：

- `WordTimelinePipeline::refine_track_timings` 的依赖通过**入参注入**：
  - `audio_wav_path: PathBuf`
  - `sentences: &[SubtitleSentence]`
  - `dtw_timings: Vec<WordTiming>`（来自 `asr_timing` 提取）
  - `venv: Option<ForcedAlignVenv>`（探测结果，None 跳过 sidecar）
- `AppServices` 字段**不**新增 `TranscriptionRepository`。
- provenance（job_id / provider_id / runtime_version / model_id / ...）也作为入参
  传入，由 api-http 调用方从 job 构造。

**影响**：编排方法保持纯函数式的依赖关系，便于测试；`AppServices` 职责不膨胀；
api-http 仍负责"job 上下文 → 入参"的装配。

### 决策 3：word_index 占位契约（对应 ADR 0011）

**背景**：`align-cli.py` 跳过 normalize 成空的词时，输出下标是过滤后词序，
而 Rust `merge_alignments` 期望未过滤下标，导致错位（详见 PLAN 的 P0 章节）。

**决定**：Python 侧对跳过词输出占位 `{"word_index": <原始下标>, "skipped": true}`，
保持 `word_index` = 未过滤下标。Rust `merge_alignments` 识别占位并对该词回退到
DTW 时间。详细决策记录见
[`ADR 0011`](../../docs/decisions/0011-word-index-contract-for-forced-alignment-sidecar.md)。

**影响**：契约向后兼容（Rust 容忍无 `skipped` 字段的旧输出）；`word_index` 永远
与 Rust `token_index` 对齐；未来换 Rust-native/ONNX aligner 时沿用此契约。

### 决策 4：巨型文件按"独立域优先"拆分，跨域耦合留到最后

**背景**：`application/src/lib.rs`（~2770 行）的 `impl AppServices` 块存在两类真实
跨域耦合，限制拆分的独立性：

- vocabulary ↔ lexical 硬耦合：`update_word_profile`/`import_vocabulary`/
  `update_word_learning_content`/`import_external_vocabulary` 尾部都写 lexical repo；
  共享 helper `lexical_from_word`/`lexical_source_from_word`。
- chunk → phrase_candidates 依赖：chunk 域 5 个 detect 方法都调
  pronunciation/lexical 域的 `phrase_candidates`。

**决定**：

- 拆分按"零摩擦 → 独立域 → 耦合域"顺序：persistence 先行（零跨域摩擦）→
  application 第一层（trait/DTO/error 纯搬运 + `pub use`）→ application 第二层
  （media→progress→pronunciation→dictionary→word_timeline→subtitle，最后处理
  vocabulary↔lexical 与 chunk→phrase_candidates）。
- 跨域编排方法（如 `update_word_profile`）留在 lib.rs 作为"编排层"，或归入主域
  模块并接受对其他域 repo 的直接字段访问（Rust 允许 `impl AppServices` 多文件多块，
  lexical.rs 已证明可行）。
- 共享 helper 抽到 `util.rs`，所有子模块 `use crate::util::*`。

**影响**：每步可独立 `cargo test` 验证；跨域耦合被显式识别而非在拆分中意外断裂；
对外部 crate 完全透明（`use application::{...}` 路径不变）。

### 决策 5：本阶段不更新 STATE.md（激活阶段约束）

**背景**：MAINTENANCE §3.3 规定 STATE.md 在 phase 完成时更新。本阶段当前仅产出
规划文档，无代码落地。

**决定**：本阶段创建 PLAN/CONTEXT/ADR 文档，更新 CONCERNS/CONVENTIONS，但**不**
更新 STATE.md，**不**新增 CHANGELOG 条目（CHANGELOG 仅在实际实现提交时追加）。
STATE.md 的 M2.0 Phase 4 客观评估状态不动，2.1 实现排在 Phase 4 收口之后。

## 4. 风险与缓解

| 风险 | 缓解 |
|---|---|
| word_index 占位改 sidecar 协议，旧输出不兼容 | Rust 容忍无 `skipped` 字段的旧输出（向后兼容）；Python 单测覆盖跳词 |
| 编排下沉改 api-http 行为，可能破坏 DTW fallback | 保留 sidecar 缺失/失败回退 DTW 的行为；编排方法对每步失败显式回退；回归测试覆盖三条路径（缺失/失败/正常）|
| 拆分引入回归 | 每搬一个 `impl` 块 / 一个域即 `cargo test`；persistence 集成测试不受影响；application 第一层是纯搬运 |
| vocabulary↔lexical 耦合在拆分中断裂 | 该耦合在决策 4 中显式识别，跨域编排方法留 lib.rs 或归主域；共享 helper 集中到 util.rs |
| Python 共享 tokenizer 改变既有 token_index 分配 | WORD_RE 统一为更宽容版本前，对比三脚本在 TIMIT 上的 token_index 是否变化；若变化需评估对历史 gold 的影响 |
| 评审行号随 M2.0 Phase 4 推进漂移 | PLAN 的代码位置以"评审时行号 + 函数名"双重定位，实现时以实际为准 |

## 5. 评审亮点（本阶段需保持的设计）

加固不是推倒重来。本次评审确认了以下设计应保持，本阶段不得削弱：

1. `forced_align.rs` 的 per-word 降级 + 单调性 + 句窗校验 + 9 个边界测试用例。
2. LLTimeline JSON v1 契约 + versioned resource + active/candidate/archived 状态机。
3. 评估指标的可解释性（tail_lag / lead_lag_bias / suspicious_words）。
4. TIMIT 转换器的 `make_non_overlapping_words` 主动修复 gold 词重叠。
5. 错误处理纪律（library crate 不用 unwrap；Python 脚本统一 `raise SystemExit` +
   明确 exit code）。
6. ADR 体系（0001-0010）记录关键技术决策。
