# Phase 2.23 Plan: Architecture Debt Paydown

状态：PLANNED（建档 2026-07-02，未开工）

## Objective

把 2026-07-02 架构审核确认的五个累积债务点（见 `2.23-CONTEXT.md` A1-A5）
收口为可测量的工程结果：

```text
文档事实源修复
  -> main.dart 收缩为 composition root、UI 状态单轨化   # 3.x Flutter 工作前置
  -> speech-analysis 热点机械拆分 + 拆分触发规则入法      # 算法线静默窗口内
  -> Dart 模型层建立 contract-driven 解析安全网
  -> 巨型测试文件机械拆分
```

定位更新（2026-07-02）：speech-analysis 算法线（2.19/2.20/2.21）已搁置，
主线转入 Phase 3.x 英语听力学习闭环。本 phase 因此是 **3.x 开工前的工程
底座**：Flutter 侧（Step 3/4）直接服务 3.x 的 practice UI 工作，Rust 侧
（Step 2/5）利用算法线静默窗口零冲突地完成。

阶段原则（不可违反）：

- 不改产品行为、不改 API contract、不改 SQLite schema、不改算法语义。
- 每步拆分前后，同一组测试命令的结果必须一致（允许仅因模块路径变化而
  更新的 `use` / import 语句和测试文件位置）。
- 验收全部用可测量指标（行数、grep 计数、测试数），禁止"大体完成"式收口。

### Step 2: `sound_analysis.rs` 机械拆分 + 拆分触发规则（P1，对应 A2）

目标：把 3383 行单文件拆为按子域组织的模块目录，**公共 API 与行为零变化**。
算法线（2.19/2.20/2.21）已于 2026-07-02 搁置，本步落在静默窗口内执行——
零并行冲突，算法线重启时直接在干净的模块边界上继续迭代。

拆分方式（沿用 2.3.5 的 mechanical decomposition 原则）：

- `crates/speech-analysis/src/sound_analysis.rs` →
  `crates/speech-analysis/src/sound_analysis/` 模块目录，
  `mod.rs` 保留公共 re-export，**对外 API 路径不变**
  （`speech_analysis::sound_analysis::*` 的现有引用零修改）。
- 按当前代码的自然子域切分，建议切法（开工时按实际函数聚类微调，
  切法变化需回填本 PLAN）：
  - `tokens.rs` — RhythmToken substrate、WordTimeline timing 接入、
    timing source / audio-backed 判定（W1 honesty 逻辑）。
  - `anchors.rs` — information anchors、prominence 打分、
    information-structure prior（W6）。
  - `nuclei.rs` — phrase-scoped nucleus 选择与 abstain 逻辑。
  - `grouping.rs` — weak groups、compression spans。
  - `boundaries.rs` — phrase boundaries、pause / pre-boundary
    lengthening / pitch reset evidence。
  - `references.rs` — A/B/C references 装配（B 侧规则引擎仍留在
    `connected_speech_rules`，此处只做装配）。
  - `hotspots.rs` — listening hotspots。
  - `quality.rs` — quality / signal sources / provenance 字符串
    （`generated_from` 等常量集中于此，**字符串值一字不改**）。
- 单元测试随各子域就近拆到对应模块的 `#[cfg(test)]`，或建
  `sound_analysis/tests.rs`；测试逻辑与断言不改。

**拆分触发规则入法**（防止复发）：

- `AGENT.md` Architecture Rules 新增一条：
  单个 `.rs` / `.dart` 实现文件超过约 1500 行、或一个文件承载多于一个
  明确子域时，必须先拆模块再继续在其中加新功能；机械拆分不需要
  单独立 phase。
- 明确 crate 级拆分（`speech-analysis` 拆成多 crate）**仍然 defer**：
  module boundary 够用，等子域间出现独立发布/依赖需求再议。

Acceptance gate：

- `sound_analysis/` 下无单文件 > 1500 行；`mod.rs` 只含声明与 re-export。
- `cargo test -p speech-analysis --quiet` 通过且测试数 ≥ 基线（152）。
- `cargo test --workspace --quiet` / `./scripts/validate-contracts.sh` 通过。
- `git diff` 中不存在 `generated_from` / signal-source / evidence-class
  字符串值的变化（可用 `git diff -G'generated_from'` 抽查）。
- AGENT.md 含拆分触发规则。

### Step 3: `main.dart` 收缩 + UI 状态单轨化（P1，对应 A1）

目标：`main.dart` 收缩为 composition root（app 装配、顶层 layout、dialog
wiring），业务动作全部进 controller；结束 "controller + 内联 setState"
双轨制，明确唯一的 UI 状态模式。

这是本 phase 风险最高的一步，必须切成可独立验证的小刀，每刀一个 commit、
每刀跑 `flutter analyze` + `flutter test`：

1. **状态模式定调（2026-07-02 已决，无需再议）**：
   - 核实结论：`state/store.dart`（`Store<T>` 细粒度选择器容器）与
     `state/builder.dart`（`StoreBuilder`）不是死雏形——
     `PlayerController` / `LearningController` / `SubtitleController`
     三大控制器已在使用，且有 `store_test.dart` / `builder_test.dart`
     测试覆盖。**定调：controller + Store 转正为唯一 UI 状态模式**，
     写入 `codebase/ARCHITECTURE.md` Flutter 节；main.dart 迁出的状态
     一律进 controller + Store，不新增第三种模式，不引入新依赖
     （provider/riverpod 等，引入需 ADR——默认不引入）。
2. **Media/Session action 抽离**：open media、session 恢复、播放进度
   保存等 wiring 移入 `PlayerController` 扩展或新
   `MediaSessionController`（2.18 PLAN 已预留此名）。
3. **Resource action 抽离**：字幕资源 / timeline 资源 / LLTimeline
   挂载等面板动作从 main.dart 内联闭包移入对应 controller 或新
   `ResourceActionsCoordinator`；面板 widget 通过 controller 接口触发。
4. **内联 `_sidePanel()` 等重复布局**：2.22 已删死代码 `SidePanel`，
   本步把 main.dart 中超过一屏的内联布局方法提为 `widgets/layout/`
   下真实使用的 widget（避免再造死代码：先建 widget、同 commit 内
   替换调用点）。
5. **setState 收敛**：main.dart 中剩余 setState 应只服务纯布局/可见性
   切换；业务数据变更一律走 controller notify。

硬指标（开工时如与实际函数聚类冲突，可在本 PLAN 回填调整，但必须
留下调整理由，不许静默放宽）：

- `main.dart` ≤ 1500 行（基线 3601）。
- `grep -c setState apps/desktop/lib/main.dart` ≤ 30（基线 107）。
- `codebase/ARCHITECTURE.md` Flutter 节写明 controller + Store 为唯一
  UI 状态模式；main.dart 迁出的状态全部落在该模式内，无第三种模式。

Acceptance gate：

- 上述三项硬指标达成。
- 新抽 controller 有单元测试（沿用现有 controller test 风格）。
- `flutter analyze` 无问题；`flutter test` 通过数 ≥ 基线。
- 手工 smoke：按 `2.22-FRONTEND-E2E-QA.md` 的 P0 路径过一遍
  （本 phase 不改行为，smoke 目的是证明"没改坏"）。

**Step 3 完成回填（2026-07-03）**：
