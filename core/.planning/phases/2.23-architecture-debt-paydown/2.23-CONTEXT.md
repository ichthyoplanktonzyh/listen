# Phase 2.23 Context: Architecture Debt Paydown

> 建档：2026-07-02
> 来源：2026-07-02 全库架构审核（对照 `AGENT.md` / `ARCHITECTURE.md` 声明逐条验证代码事实）

## 触发背景

2026-07-02 做了一次独立架构审核，逐条验证 `.planning/codebase/ARCHITECTURE.md` 与
`AGENT.md` 的架构声明。结论：**Rust 分层、契约守卫、证据分级纪律全部成立**，
但暴露出五个正在累积的债务点。它们各自都被历史 phase "承认过"，但没有
收敛到一个带硬性验收的 phase 里，存在"永远 defer"的风险。

## 审核确认成立的部分（本 phase 不动）

- 依赖方向单向：`domain` 零依赖叶子；`diagnosis-core` / `subtitle-core` /
  `speech-analysis` 只依赖 domain（后者加 subtitle-core）。
- `api-http` 全 crate 无 `speech_analysis` 引用；route/OpenAPI 双向 parity 测试
  和 `validate-contracts.sh` 作为防漂移守卫有效。
- `persistence-sqlite` 与 `dictionary-provider` 均反向依赖 `application`
  （实现其 trait），`api-http` 为 composition root——教科书式端口-适配器。
- Rust 约 350 个测试，Flutter 147 passed；contract / schema / benchmark role
  各有独立防漂移测试。

## 与相邻 phase 的关系

- **Phase 2.18**（代码架构重构）：A1/A2 是它 closeout 里明确记录的剩余债务，
  本 phase 是其延续，不是新方向。
- **Phase 2.3.5**（Rust 巨型单文件拆分）：A2/A5 沿用其"只做 mechanical
  decomposition，不改行为、不改 contract"的阶段原则。
- **Phase 2.19/2.20/2.21**（speech-analysis 算法线）：2026-07-02 方向决策后
  整体搁置，主线转入 Phase 3.x 学习闭环，闭环完成后再重启算法线。本 phase 的
  A2 拆分**只动文件组织，不动算法语义**，正好落在算法线静默窗口内——零并行
  冲突，且算法线重启时直接继承干净的模块结构。
- **Phase 3.x**（学习闭环，当前主线）：3.0.1 的下一切片是 Flutter practice
  controller/UI。A1（main.dart 收缩、状态单轨化）是其直接前置——新 practice UI
  不应继续堆在 god file 和 setState 双轨制上。因此 Flutter 侧步骤（Step 3）
  优先级提升为 P0，先于 Rust 侧拆分执行。
- **Phase 2.22**（用户工作流语义）：SM-01（status 缩范围）已部分完成，
  A1 的 typed 状态收敛是其自然延续；2.22 defer 的 SM 项不在本 phase 复活，
  除非与 main.dart 收缩直接重叠。
- **route manifest**：2.18 明确 defer、parity 测试兜底，本 phase 继续不做。

## 阶段原则

1. **不改产品行为、不改 API contract、不改 SQLite schema、不改算法语义。**
   本 phase 是 2.3.5 式的机械治理 + 文档事实源修复。
2. 每步用现有测试基线做安全网，拆分前后测试结果必须一致。
3. 所有验收标准必须是可测量的（行数、grep 计数、测试通过数），
   避免 2.22 复盘发现的"已收口属高估"问题重演。
4. 文档修复先行——它最便宜，且直接决定后续会话读到的事实是否可信。
